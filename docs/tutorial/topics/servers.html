Servers & Hosting — interview study guide

Every PrintArtZ page is served by something, and slow AI image jobs have to run somewhere too. This guide walks from what a server actually is, through serverless vs. long-running processes, background job queues, scaling, and how you choose a host — in interview Q&A form with real context. Click any question to expand.

A server is any program that waits for requests and sends back responses — and, loosely, the machine that program runs on. It's not a special kind of computer; it's a role. Your laptop becomes a server the moment you run something that listens on a port for incoming connections.

The counterpart is the client: the program that initiates the request. When you open PrintArtZ, your browser is the client and the machine running the Next.js app is the server. The two talk over a network using an agreed protocol (HTTP for the web). The whole web is built on this client–server model: many clients, each asking a shared server for pages, data, or actions.

A useful clarification for interviews: “server” describes behaviour, not hardware. The same box can be a client for one interaction (calling Supabase) and a server for another (answering your browser).

The web is fundamentally request/response: the client sends one request, the server sends back exactly one response, and (in classic HTTP) the connection's job for that exchange is done. The client always starts the conversation — a server never spontaneously pushes to a plain HTTP client.

1. Client resolves the domain to an IP (DNS lookup)
2. Client opens a TCP connection (often over TLS for HTTPS)
3. Client sends an HTTP request:  GET /gallery HTTP/1.1  + headers
4. Server processes it (maybe queries Supabase)
5. Server sends an HTTP response: status + headers + body (HTML/JSON)
6. Browser renders the body

For PrintArtZ, visiting the gallery is a GET; submitting the create form is a POST whose body carries the prompt. Because each request is independent, the server needs some way (a cookie/token) to know who is asking — which is why authentication rides along in headers on every request.

HTTP (HyperText Transfer Protocol) is the text-based request/response language of the web. A request has a method (the verb), a path, headers (metadata like auth and content type), and an optional body. A response has a status code, headers, and a body.

The common methods: GET reads data, POST creates/submits, PUT/PATCH update, DELETE removes. GET should be safe (no side effects) and, like PUT/DELETE, idempotent (repeating it has the same effect), whereas POST is not.

Status codes cluster by first digit: 2xx success (200 OK, 201 Created), 3xx redirect (301, 304 Not Modified), 4xx the client's fault (400 bad request, 401 unauthenticated, 403 forbidden, 404 not found, 429 too many requests), and 5xx the server's fault (500 internal error, 503 unavailable). Knowing that 4xx = “you” and 5xx = “me” is worth stating plainly in an interview.

An IP address identifies a machine on a network (e.g. 93.184.216.34). A port is a numbered channel on that machine, so one server can run many services at once without them colliding. The pair “IP + port” is a unique endpoint a client connects to.

Some ports are conventional: 80 for HTTP, 443 for HTTPS, 5432 for PostgreSQL (what Supabase runs), 6379 for Redis, and 3000 for a local Next.js dev server. When you visit https://site.com the browser silently uses 443.

DNS ties this together: humans use domain names (printartz.com), and DNS translates them to IPs so requests can be routed. It's the phone book of the internet — you remember the name, DNS finds the number.

A web server (nginx, Apache, Caddy) specializes in speaking HTTP: accepting connections, serving static files (HTML, CSS, images), handling TLS, and forwarding dynamic requests onward. It's fast and dumb by design.

An application server runs your code to produce dynamic responses — a Node.js process running Next.js, for instance, deciding what HTML to render based on the logged-in user and database. In many setups the web server sits in front as a reverse proxy and passes dynamic requests back to the app server, while serving static assets itself.

In modern managed platforms this split is largely hidden from you: Vercel serves PrintArtZ's static assets from its CDN edge and runs your dynamic Next.js code in serverless functions, so you don't hand-configure nginx — but the two roles are still there under the hood.

Stateless means the server keeps no memory of previous requests between them — each request must carry everything needed to understand it. HTTP has no built-in notion of “this is the same user as a moment ago.”

So how do you stay logged in? The client re-sends proof of identity on every request, typically a cookie or a token in the Authorization header. The server validates it fresh each time. That's exactly how PrintArtZ's Supabase auth works: a session token accompanies each request and the server re-checks it.

This is a feature, not a limitation. Because no request depends on server-side memory, you can put many identical servers behind a load balancer and any of them can handle any request — the foundation of horizontal scaling.

HTTPS is just HTTP running inside a TLS encrypted tunnel. TLS gives you three things: encryption (eavesdroppers on the network see gibberish), integrity (tampering is detected), and authentication (a certificate proves you're really talking to printartz.com, not an impostor).

At connection time there's a handshake: the server presents a certificate signed by a trusted Certificate Authority, the two sides agree on keys, and from then on the traffic is encrypted. Modern hosts like Vercel provision and renew these certificates automatically, so HTTPS “just works” without you managing keys.

The interview-worthy point: because auth tokens ride in headers on every request, HTTPS is non-negotiable — without it, anyone on the network could read a user's session token and impersonate them.

A traditional server is a process that stays running 24/7, listening on a port, ready to handle requests the instant they arrive. You provision a machine — a physical box, a virtual machine (VM), or a container — start your app, and it stays up whether one person or a thousand are using it.

Because the process is always alive, it can hold things in memory between requests (caches, open database connections, in-progress work) and it can run for as long as it likes — a five-minute job is no problem. The trade-off is that you pay for it to sit there even when idle, and you are responsible for keeping it healthy, patched, and scaled.

Examples: a Node.js app on an AWS EC2 VM, a Docker container on Render, or a background worker on Railway. This is the model PrintArtZ will use for its image-generation worker.

“Serverless” doesn't mean there are no servers — it means you don't manage them. You upload a single function; the platform runs it on demand when a request arrives, spins it down when idle, and bills you only for the milliseconds it actually executed. There's no machine for you to provision, patch, or keep alive.

// A Vercel/Next.js route handler = a serverless function
export async function POST(req) {
  const { prompt } = await req.json();
  // ...do work, return a response...
  return Response.json({ ok: true });
}

Each PrintArtZ API route and server-rendered page deploys as one of these functions. The platform handles scaling automatically: ten simultaneous visitors just cause ten function instances to run. The catch is that instances are short-lived and stateless, and they have a hard execution time limit — which shapes how you design slow features.

When a serverless function hasn't run recently, there's no instance ready, so the platform must spin one up: allocate a sandbox, load your code, and initialize the runtime before your handler even begins. That startup delay — often tens to hundreds of milliseconds — is a cold start.

Once warm, an instance can be reused for subsequent requests (a warm start) and responds instantly, until it goes idle and is torn down again. Cold starts hurt most for infrequently-hit endpoints and for latency-sensitive user actions.

Mitigations include keeping functions small (less to load), avoiding heavy top-level initialization, choosing lighter runtimes (edge runtimes start faster than full Node), and, on some platforms, paying to keep instances warm. For PrintArtZ this is a minor concern for page loads, but it's one more reason a long AI job doesn't belong in a request-triggered function.

Serverless instances are ephemeral: any one can be created or destroyed at any moment, and two requests from the same user may hit entirely different instances. So you cannot rely on in-memory state surviving between requests — no storing a user's session in a local variable, no in-process job progress, no local file that persists.

Anything that must persist has to go to an external, shared store: a database (Supabase), a cache (Redis), or object storage for files. State lives outside the function, and the function is a pure, disposable worker that reads and writes that shared state.

This is actually the same discipline that makes horizontal scaling work. It's liberating once you internalize it — but it means features that feel like they need “memory,” such as tracking a long-running generation, must be modelled as rows in a database, not variables in a process.

Serverless platforms cap how long a single function may run — commonly around 10–60 seconds on typical plans (Vercel's exact limit depends on plan and runtime). If your handler exceeds it, the platform kills it mid-execution and the user gets a timeout, with no clean way to resume.

This is the crux of PrintArtZ's architecture. AI image generation can take much longer than a request should stay open — potentially many seconds to minutes depending on the model and queue. Trying to generate an image synchronously inside the create-request function risks hitting the timeout and wastes a held-open connection.

The correct pattern is to make the request fast: the function validates input, records a “pending” job, enqueues it, and immediately returns a job id. The actual slow work runs elsewhere — in a separate long-running worker — and the UI polls or subscribes for the result. That's why PrintArtZ plans a dedicated worker plus a queue rather than doing everything in the serverless request.

Serverless

Zero server management, auto-scales to zero and to spikes, pay-per-use so cheap when idle. But: cold starts, statelessness, and a hard execution time limit make long or stateful jobs a poor fit.

Long-running server

Runs indefinitely, holds in-memory state and pooled connections, ideal for slow jobs and steady heavy load. But: you pay while idle, and you own scaling, patching, and uptime.

They're not either/or — mature systems combine them. PrintArtZ's plan is exactly this hybrid: serverless Next.js on Vercel for the fast, spiky, request/response web layer, and a long-running worker for the slow, unbounded AI generation jobs. Use serverless for short request-scoped work; use a dedicated process for anything long, stateful, or continuous.

Regional (Node.js) functions run in a specific data-center region on a full Node runtime — they can use any npm package and talk directly to your database, but they live in one place, so users far away pay extra latency. Edge functions run on a lightweight runtime distributed across many locations worldwide, executing physically close to the user for very low latency and fast cold starts.

The catch is that the edge runtime is restricted: no full Node APIs, tighter limits, and you generally shouldn't open a raw database connection from dozens of edge locations. Edge shines for lightweight, latency-sensitive work — auth checks, redirects, personalization, geolocation.

For PrintArtZ, edge is a fine fit for things like middleware auth gating, while data-heavy routes that hit Supabase are better as regional functions placed in the same region as the database to minimize round-trip time.

Some work is too slow to finish inside a single web request. If a user clicks “Generate” and the request tries to do the whole AI job inline, they stare at a spinner for a long time, the connection is held open the entire time, and on serverless you risk hitting the execution time limit and losing the work entirely.

The fix is to decouple accepting the work from doing the work. The request does the minimum — validate, save a “pending” record, enqueue the task — and returns immediately (typically 202 Accepted with a job id). A separate process picks the task up and does the heavy lifting; the UI checks back for the result.

This keeps the web layer fast and responsive, survives long-running tasks comfortably, and lets you retry failures without the user re-submitting. It's the backbone of PrintArtZ's image pipeline.

A job queue is a durable list of tasks waiting to be processed. Producers (your web app) push jobs onto it; consumers (workers) pull jobs off and execute them. It sits between the two so they don't have to run at the same speed or even be online at the same time.

The queue buffers spikes: if a hundred users hit “Generate” at once, the requests all return instantly and the jobs simply line up, to be worked through as capacity allows. It also decouples failure — if a worker crashes mid-job, the job can be requeued rather than lost.

PrintArtZ's create endpoint becomes a producer that enqueues an “generate image” job; one or more workers are the consumers that actually call the AI model and store the result. The queue is the shock absorber between a spiky front end and slow, limited-capacity generation.

Redis is an in-memory data store — extremely fast key/value storage often used for caching, counters, and, crucially, as the backing store for queues. Because it's in-memory it's quick enough to coordinate lots of small operations like pushing and popping jobs. PrintArtZ plans to use Upstash, a serverless/hosted Redis that fits the serverless model (pay-per-use, connects over HTTP/TLS).

BullMQ is a Node.js job-queue library built on top of Redis. It gives you the high-level pieces you'd otherwise hand-roll: adding jobs, workers that process them, automatic retries with backoff, delayed/scheduled jobs, concurrency control, and progress events.

// Producer (in the Next.js create route)
await imageQueue.add("generate", { prompt, userId });

// Worker (separate long-running process)
new Worker("images", async (job) => {
  const url = await callAIModel(job.data.prompt);
  await saveResult(job.data.userId, url);
}, { connection: redis, concurrency: 3 });

So the layering is: Redis is the storage engine, BullMQ is the queue framework using it, and your worker is the code that runs each job.

A worker is a long-running process whose whole job is to pull tasks off the queue and execute them. It's not triggered by a web request — it loops continuously, blocking until a job is available, processing it, then reaching for the next one. It reports progress and results back (to Redis and/or the database).

Because it needs to run for as long as a job takes and stay alive between jobs, a worker can't be a serverless function — it belongs on a long-running host. PrintArtZ's worker would run on something like Render, Railway, or a Fly.io/AWS container: a persistent process next to the queue.

You can run several workers (or one worker with concurrency > 1) to process multiple jobs in parallel, and scale that number up or down based on queue depth. This separation — spiky serverless web tier, steady worker tier — is what lets each part scale on its own terms.

Jobs fail for transient reasons — the AI API times out, hits a rate limit, or the network blips. Retries mean the queue automatically re-runs a failed job a configured number of times before giving up, so a momentary glitch doesn't lose the user's request.

Naively retrying immediately can make things worse (hammering an already-struggling API), so you use exponential backoff: wait a little before the first retry, then longer before each subsequent one. BullMQ supports this with a couple of options.

await imageQueue.add("generate", data, {
  attempts: 4,
  backoff: { type: "exponential", delay: 2000 }, // 2s, 4s, 8s...
});

After the final failed attempt the job lands in a dead-letter/failed set where you can inspect and manually replay it. For PrintArtZ this means a flaky model call gets retried transparently, and the user's job is marked “failed” only after genuine, repeated failure.

Idempotency means running an operation multiple times has the same effect as running it once. It matters because queues generally guarantee at-least-once delivery, not exactly-once: a job can be delivered twice if a worker crashes after finishing the work but before acknowledging it. Without care, a user could be charged a credit twice or get two duplicate images.

You make a job idempotent by giving each unit of work a stable id and checking whether it's already been done before doing it again — e.g. a unique key on the result row, or a “this job id already produced output” guard. Then a duplicate delivery becomes a harmless no-op.

async function handle(job) {
  if (await alreadyDone(job.id)) return; // safe replay
  const url = await callAIModel(job.data.prompt);
  await saveResultOnce(job.id, url);     // unique on job.id
}

The interview soundbite: “design workers assuming any job may run more than once.” For PrintArtZ, keying results and credit-deductions on the job id prevents double-charging and duplicate art on retries.

Since the initial request returns before the work is done, the front end needs a way to learn the result later. There are three common approaches, in rough order of sophistication:

  • Polling: the browser asks GET /jobs/:id every few seconds until status flips to done. Simplest to build and totally serverless-friendly; costs a few extra requests.
  • Real-time subscription: the client subscribes and the server pushes an update when the row changes. Supabase Realtime can broadcast a database change to the browser, so when the worker writes the finished image the UI updates instantly with no polling.
  • Webhook / callback: for server-to-server flows, the worker calls back a URL when done — less relevant for updating a live browser.

For PrintArtZ, the worker writes the completed image and status into Supabase, and the create page either polls that job row or listens via Supabase Realtime to swap the spinner for the finished art.

Vertical scaling (“scale up”) means making one machine more powerful — more CPU, RAM, or faster disks. It's simple (no code changes) and often the right first move, but it hits a ceiling: there's a biggest machine you can buy, it's a single point of failure, and cost rises steeply at the top end.

Horizontal scaling (“scale out”) means running more machines/instances and spreading load across them with a load balancer. It scales far beyond one box and adds redundancy — if one instance dies, others carry on — but it requires your app to be stateless so any instance can serve any request.

Serverless is horizontal scaling taken to its extreme and automated: the platform simply runs as many function instances as demand requires. PrintArtZ's web tier scales out automatically on Vercel, while the worker tier scales by adding more worker processes when the queue gets deep.

A load balancer sits in front of a pool of identical servers and distributes incoming requests across them, so no single instance is overwhelmed. Clients connect to the load balancer's address; it decides which backend actually handles each request (round-robin, least-connections, and so on).

Beyond spreading load, it provides health checking and failover: it stops routing to an instance that fails its health checks and sends traffic only to healthy ones, so a single crashed server doesn't take the site down. It often also terminates TLS and can do sticky sessions if needed.

On managed platforms like Vercel this is invisible — the platform's routing layer load-balances across your function instances automatically. You'd configure one explicitly when running your own VMs or containers behind, say, an AWS Application Load Balancer.

If a server stores per-user state in its own memory (a session, a shopping cart, upload progress), then that user must keep hitting the same instance, or their state vanishes. That's called a “sticky” dependency, and it fights against load balancing and against instances being freely added or destroyed.

A stateless server keeps no such per-request memory: everything shared lives in an external store (database, Redis, object storage) that all instances reach. Now any instance can serve any request, you can add or kill instances at will, and a crash loses nothing important.

This is why HTTP's statelessness and serverless's ephemerality push you in the same healthy direction. PrintArtZ keeps sessions in tokens, data in Supabase, jobs in Redis — so both the web functions and the workers are interchangeable and disposable.

Caching means storing the result of expensive work so you can serve it again without redoing it. It appears at every layer: the browser caches assets, a CDN caches responses near users, the app caches computed values (often in Redis), and the database caches query plans and pages. The art is knowing what's safe to cache and for how long (and how to invalidate it when data changes).

A CDN (Content Delivery Network) is a globally distributed set of edge servers that cache your static assets — images, CSS, JS, and even pre-rendered pages — physically close to users. A visitor in Tokyo gets files from a nearby edge node instead of an origin server across the world, dramatically cutting latency and offloading the origin.

Vercel serves PrintArtZ's static assets and cacheable pages from its global CDN automatically, and generated images stored in object storage are typically served through a CDN too, so the gallery loads fast everywhere.

A health check is a lightweight endpoint (e.g. GET /healthz) that reports whether an instance is fit to serve traffic. A load balancer or orchestrator polls it periodically; if an instance stops responding or reports unhealthy, it's pulled out of rotation and traffic reroutes to healthy instances.

There's a useful distinction between a liveness check (“is the process alive? if not, restart it”) and a readiness check (“is it ready to take traffic yet? e.g. finished warming up, database reachable”). Together they let the platform restart what's stuck and route only to what's ready.

For PrintArtZ's worker tier on a container host, a health check lets the platform automatically restart a worker that has hung or crashed, so jobs keep getting processed without manual intervention — a core piece of self-healing reliability.

A single point of failure (SPOF) is any component whose failure takes down the whole system. Typical culprits: one app server, one database with no replica, one region, or one shared dependency like the queue's Redis. Reliability engineering is largely about hunting these down and adding redundancy.

The general remedy is redundancy plus failover: run multiple app instances behind a load balancer; run the database with a standby replica that can be promoted; deploy across multiple availability zones or regions; and make external dependencies resilient (retries, timeouts, circuit breakers) so one slow service doesn't cascade.

Managed services absorb a lot of this: Vercel spreads functions across infrastructure, Supabase offers replication/backups, and Upstash runs Redis with durability options. You still design the app so that a transient dependency failure degrades gracefully — e.g. a failed AI call retries via the queue rather than crashing the request.

Different tiers absorb spikes differently. The web tier on Vercel scales out automatically — more visitors just spawn more serverless instances — and the CDN absorbs most static and cacheable traffic without touching your code at all. So page loads and the gallery handle bursts well by default.

The bottleneck is generation, because it's slow and constrained by the AI provider's rate limits. Here the queue is the pressure valve: a surge of “Generate” clicks all return instantly and simply pile up as jobs, to be processed at a sustainable rate. You protect the system with rate limiting (per-user caps, returning 429) and by tuning worker concurrency so you don't exceed the model's limits.

If sustained demand is high, you scale the worker tier out (more workers) and watch queue depth as your key metric. The database is protected with connection pooling and caching of hot reads. The theme: let elastic tiers auto-scale, and buffer the inelastic slow work behind a queue.

These are cloud service models that differ by how much the provider manages for you. Think of it as a spectrum from “here's a bare machine” to “here's a finished product.”

  • IaaS (Infrastructure as a Service): you rent raw compute — e.g. an AWS EC2 virtual machine. You get an OS and total control, but you install runtimes, configure the web server, secure it, and handle scaling. Maximum flexibility, maximum responsibility.
  • PaaS (Platform as a Service): you give the platform your code and it handles the servers, OS, scaling, and deploys — e.g. Vercel, Render, Railway, Heroku. Far less ops work; less low-level control.
  • SaaS (Software as a Service): you just use finished software over the web — e.g. Gmail, or Supabase's managed database. No infrastructure concerns at all.

PrintArtZ leans on PaaS and SaaS deliberately: Vercel (PaaS) hosts the app, Supabase (managed/SaaS) hosts the database and auth, Upstash (managed) hosts Redis — so a small team ships features instead of running servers.

A container packages your application together with everything it needs to run — code, runtime, libraries, system dependencies — into one portable unit that behaves the same everywhere. It solves the classic “works on my machine” problem: the same container image runs identically on your laptop, in CI, and in production.

Docker is the most popular tool for building and running containers. You write a Dockerfile describing how to assemble the image, build it once, and run that image anywhere a container runtime exists.

Containers are lighter than full virtual machines because they share the host's OS kernel rather than each running a whole guest OS — so they start in seconds and pack densely onto a host. For PrintArtZ, the long-running worker is a natural fit to ship as a container to Render/Railway/Fly.io: reproducible, easy to deploy, and easy to scale by running more copies.

Environments are separate, isolated copies of your system for different stages of the lifecycle. Development is your local machine for building and experimenting. Staging is a production-like environment for final testing with realistic data. Production is the live system real users touch.

Separating them means you can break things safely in dev/staging without affecting real users or real data, and you can validate a change in a production-like setting before it goes live. Each environment gets its own configuration and secrets via environment variables — separate database URLs, API keys, and so on — so test activity never pollutes production.

Vercel supports this cleanly: every pull request gets a preview deployment with its own URL, and merging to the main branch promotes to production. PrintArtZ would keep separate Supabase projects/keys per environment so a preview never writes to live user data.

Vercel is built by the team behind Next.js, so it's the most frictionless home for a Next.js app — the framework's features (server components, route handlers, image optimization, ISR, middleware) map directly onto Vercel's platform with essentially zero configuration. You push to Git and it builds and deploys.

Practically, you get automatic HTTPS, a global CDN for static assets and cacheable pages, serverless (and edge) functions for dynamic code, preview deployments per pull request, and automatic scaling — all the infrastructure concerns handled. For a small team that means shipping product instead of managing servers.

The one thing it deliberately does not host well is a long-running process, because its compute is serverless with an execution time limit. That's precisely why PrintArtZ pairs Vercel (web) with a separate worker host (generation) — using each platform for what it's best at.

The worker needs to be a long-running process that stays alive to poll the queue and to churn through jobs that can take a long time. Vercel's serverless compute is the opposite: short-lived, request-triggered, and capped by an execution time limit — a bad fit for a process that must run continuously and for minutes at a stretch.

So the worker belongs on a host that offers persistent processes/containers: Render (background workers), Railway, Fly.io, or a container on AWS. You ship the worker as a small Node service (ideally a Docker image), point it at the same Upstash Redis and Supabase, and let it run.

This split is the whole architectural point: Vercel handles the fast, elastic, spiky web layer; a dedicated worker host handles the slow, steady, unbounded generation work. Each scales and is billed on its own terms.

Supabase is a managed platform built around PostgreSQL, bundling the database with auth, storage, auto-generated APIs, and realtime subscriptions. Choosing it means you don't run the database yourself — no provisioning, patching, backups, replication, or failover to babysit.

Self-hosting Postgres gives you total control and can be cheaper at very large scale, but it's real operational work: you're on the hook for security updates, backups you can actually restore, connection limits, monitoring, and high availability. For a small team, that's time not spent on the product.

For PrintArtZ the managed choice is compelling because Supabase's auth integrates with the app, its storage can hold generated images, and its realtime feature lets the UI learn the instant a worker finishes a job — several needed pieces from one managed service, all speaking plain Postgres underneath so you're not locked into anything exotic.

PaaS

Push code, platform runs it. Handles servers, scaling, TLS, deploys, previews. Fast to ship, low ops burden. Less low-level control, potential platform lock-in, and cost can climb at high scale.

IaaS (EC2)

Rent bare VMs with full control over OS, networking, and runtime. Cheapest per-unit at scale and maximally flexible, but you own provisioning, security patching, scaling, and uptime.

The honest trade-off is engineering time vs. control and unit cost. A small team moving fast — like PrintArtZ — almost always wins with PaaS/managed services, accepting a higher per-unit price to avoid running infrastructure. You'd reach for IaaS when you have specialized needs (custom networking, GPUs, unusual runtimes) or scale large enough that the ops investment pays for itself.

Serverless is wrong when the workload fights its core constraints. Pick a VM/container instead when you need: long-running or unbounded execution (a job past the time limit — PrintArtZ's generation); a persistent process that stays up (queue workers, websocket servers, schedulers); in-memory state or warm connections that must survive between requests; predictable, steady high load where always-on compute is cheaper than per-invocation billing; or special hardware like GPUs.

Serverless remains the better choice for the opposite profile: bursty, short, stateless request/response work where you want zero ops and automatic scaling — exactly PrintArtZ's web pages and API routes.

The mature answer is that it isn't a religious choice. Modern systems mix both, and PrintArtZ is a textbook example: serverless Vercel for the web tier, a long-running container worker for generation, with a queue connecting them. Match each workload to the compute model that fits its shape.
