PostgreSQL — interview study guide

PostgreSQL is the relational database behind PrintArtZ — hosted on Supabase, accessed through Prisma, and holding tables like User, ProjectRequest, and GenerationJob. This guide walks from raw SQL basics to indexes, transactions, and the trade-offs of Postgres vs other databases, in interview Q&A form with real SQL and full, spoken-aloud answers. Click any question to expand.

A relational database stores data in tables (also called relations): rows are records and columns are typed attributes. The "relational" part comes from the fact that tables can reference each other — a row in one table can point at a row in another via a key — which lets you model real relationships (a user has many project requests) without duplicating data. You query and manipulate this data with SQL (Structured Query Language).

PostgreSQL (usually just "Postgres") is a free, open-source, highly standards-compliant relational database that has been developed for over 30 years. It's known for correctness, a rich type system (including JSONB, arrays, and full-text search), strong transactional guarantees (ACID), and extensibility. PrintArtZ runs Postgres via Supabase — a hosted platform that wraps a real Postgres instance with auth, storage, and an API layer.

Nearly everything you do to data maps to four verbs, together known as CRUD — Create, Read, Update, Delete. In SQL these are INSERT, SELECT, UPDATE, and DELETE.

-- Create
INSERT INTO "User" (email, name) VALUES ('amit@example.com', 'Amit');

-- Read
SELECT id, email FROM "User" WHERE name = 'Amit';

-- Update
UPDATE "User" SET name = 'Amit K.' WHERE email = 'amit@example.com';

-- Delete
DELETE FROM "User" WHERE email = 'amit@example.com';

An important interview point: SQL is a declarative language. You describe what data you want, not how to fetch it; the database's query planner figures out the most efficient execution strategy. (Note: in Postgres a table created with a capitalized name like User must be quoted, because unquoted identifiers are folded to lowercase — Prisma quotes them for you.)

SELECT reads rows from one or more tables. You choose columns after SELECT, the source after FROM, filter rows with WHERE, sort with ORDER BY, and cap the number of rows with LIMIT.

SELECT id, status, created_at
FROM "GenerationJob"
WHERE status = 'PENDING'
ORDER BY created_at DESC
LIMIT 20;

A subtle but classic interview detail is the logical order of evaluation, which differs from the written order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. This explains why you can't use a column alias defined in SELECT inside a WHERE clause — WHERE runs before SELECT — but you can use it in ORDER BY.

A primary key is the column (or set of columns) that uniquely identifies each row in a table. It enforces two rules at once: the values must be unique and can never be NULL. Every well-designed table should have one, because it gives each row a stable, unambiguous identity that other tables and your application code can reference.

CREATE TABLE "User" (
  id    TEXT PRIMARY KEY,     -- e.g. a cuid/uuid
  email TEXT NOT NULL UNIQUE
);

Keys come in two flavours worth naming in an interview: a natural key is a real-world unique value (like an email), while a surrogate key is a synthetic id with no business meaning (an auto-incrementing integer, a UUID, or a cuid). Most modern schemas — including PrintArtZ via Prisma — prefer surrogate keys because business values can change, but an internal id should never have to.

NULL represents the absence of a value — "unknown" or "not applicable" — and it is not the same as 0 or an empty string. The trap is that NULL uses three-valued logic: any comparison with NULL yields UNKNOWN, not true or false. So WHERE price = NULL matches nothing; you must write WHERE price IS NULL.

-- ❌ never matches, even for NULL rows
SELECT * FROM job WHERE finished_at = NULL;

-- ✅ correct
SELECT * FROM job WHERE finished_at IS NULL;

-- COALESCE substitutes a fallback for NULL
SELECT COALESCE(name, 'Anonymous') FROM "User";

NULL also silently affects aggregates (COUNT(column) skips NULLs while COUNT(*) counts every row) and can produce surprising results in NOT IN subqueries. Being fluent about NULL behaviour is a common way interviewers separate people who have really used SQL from those who have only read about it.

Both filter rows, but at different stages. WHERE filters individual rows before grouping, so it cannot reference aggregate functions. HAVING filters groups after GROUP BY has aggregated them, so it can use aggregates like COUNT() or SUM().

SELECT user_id, COUNT(*) AS jobs
FROM "GenerationJob"
WHERE status = 'DONE'          -- pre-filter rows
GROUP BY user_id
HAVING COUNT(*) > 5;           -- filter aggregated groups

A good rule of thumb: use WHERE to throw away rows you never want to count, and HAVING only when your condition depends on the aggregated result. Filtering early with WHERE is also usually cheaper, because fewer rows reach the grouping step.

All three remove data, but at very different levels and costs.

  • DELETE removes rows one by one, honouring a WHERE clause, firing triggers, and being fully transactional (you can ROLLBACK it). It's the everyday, surgical option.
  • TRUNCATE empties an entire table almost instantly by discarding the underlying storage rather than scanning rows. It's much faster for wiping a whole table but can't be filtered.
  • DROP TABLE deletes the table itself — data and its schema/definition — not just the rows.
DELETE FROM "GenerationJob" WHERE status = 'FAILED'; -- some rows
TRUNCATE "GenerationJob";                            -- all rows, fast
DROP TABLE "GenerationJob";                           -- table gone

In interviews, the headline is: DELETE is row-level DML you can filter and roll back; TRUNCATE and DROP are heavier, structural operations.

Choosing the right type is part of correct schema design — it enforces valid data and affects storage and performance. The everyday Postgres types are:

  • Numbers: INTEGER/BIGINT for whole numbers, NUMERIC(p,s) for exact decimals (money!), REAL/DOUBLE PRECISION for floating point.
  • Text: TEXT (unbounded) and VARCHAR(n). In Postgres these perform identically — TEXT is idiomatic unless you truly need a length cap.
  • Boolean: BOOLEAN (true/false).
  • Dates/times: TIMESTAMPTZ (timestamp with time zone — almost always the right choice), DATE, TIME.
  • Identity: UUID, or SERIAL/GENERATED … AS IDENTITY for auto-increment.
  • Semi-structured: JSONB, arrays, and ENUM types (PrintArtZ uses an enum for GenerationJob.status).

A classic warning: never store money in floating-point types, because 0.1 + 0.2 isn't exactly 0.3 in binary floats — use NUMERIC for exact arithmetic.

A foreign key is a column that references the primary key of another table, creating an enforced link between them. It guarantees referential integrity: the database will reject a row that points to a non-existent parent, so you can never end up with a GenerationJob whose userId doesn't correspond to a real User.

CREATE TABLE "GenerationJob" (
  id      TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES "User"(id) ON DELETE CASCADE,
  status  TEXT NOT NULL
);

The ON DELETE clause defines what happens to children when the parent is removed: CASCADE deletes the children too, RESTRICT blocks the delete, and SET NULL nulls the reference. This is how PrintArtZ models "a user has many project requests and jobs" while keeping the data consistent.

Constraints are rules the database enforces on every write, so bad data can't get in regardless of which application or script is writing. Two of the most common:

  • NOT NULL requires the column to always have a value — e.g. a User must have an email.
  • UNIQUE forbids duplicate values in a column (or combination of columns) — no two users can share the same email.
CREATE TABLE "User" (
  id    TEXT PRIMARY KEY,
  email TEXT NOT NULL UNIQUE,
  name  TEXT               -- nullable: optional
);

The key mental model: a primary key is effectively NOT NULL + UNIQUE combined. Other constraints worth knowing are CHECK (custom rule, e.g. price >= 0) and DEFAULT (a fallback value when none is supplied). Enforcing rules in the database is safer than only checking them in application code, because the database is the last line of defence.

Normalization is the process of organizing tables to reduce redundancy and avoid update anomalies — the practical goal being "store each fact in exactly one place." Instead of copying a user's email into every one of their jobs, you store the user once and reference them by id. The main forms build on each other:

  • 1NF: atomic column values (no comma-separated lists in a single cell), and a key.
  • 2NF: every non-key column depends on the whole primary key (matters for composite keys).
  • 3NF: non-key columns depend only on the key, not on each other (no transitive dependencies).

Why it matters: if the same fact is duplicated in many rows, an update can leave copies inconsistent (an "update anomaly"). Normalization prevents that. The counterpoint interviewers like to hear is that read-heavy or analytical systems sometimes denormalize on purpose — duplicating data to avoid expensive joins — trading storage and write-complexity for read speed.

A one-to-many relationship (one user has many jobs) is modeled by putting a foreign key on the "many" side pointing back at the "one" side — the GenerationJob.user_id column. That's the most common relationship in an app schema.

A many-to-many relationship (a post has many tags, a tag belongs to many posts) can't be captured with a single foreign key. You introduce a join table (also called a junction or bridge table) that holds one row per pairing:

CREATE TABLE post_tag (
  post_id TEXT REFERENCES post(id) ON DELETE CASCADE,
  tag_id  TEXT REFERENCES tag(id)  ON DELETE CASCADE,
  PRIMARY KEY (post_id, tag_id)   -- composite key prevents duplicates
);

The composite primary key on both columns is what stops the same pairing being inserted twice. A one-to-one relationship is just a one-to-many with a UNIQUE constraint on the foreign key.

A migration is a versioned, ordered change to the database structure — creating a table, adding a column, adding an index. Rather than clicking around a GUI, you capture each change as a script committed to source control, so every environment (local, staging, production) can be brought to the same schema deterministically.

PrintArtZ uses Prisma, an ORM where you declare the schema in a schema.prisma file and run prisma migrate to generate and apply SQL. Prisma also generates a fully typed client, so queries are type-checked in TypeScript.

// schema.prisma
model User {
  id    String  @id @default(cuid())
  email String  @unique
  jobs  GenerationJob[]
}

The value proposition: the ORM maps rows to typed objects and prevents SQL injection via parameterized queries, while migrations give you a repeatable, reviewable history of how the schema evolved.

Because a normalized schema splits related data across tables, a JOIN is how you recombine them in a single query. You tell the database how rows in one table line up with rows in another — usually by matching a foreign key to a primary key.

SELECT u.email, j.status, j.created_at
FROM "User" u
JOIN "GenerationJob" j ON j.user_id = u.id
WHERE j.status = 'DONE';

Here each output row pairs a user with one of their completed jobs. Without joins you'd have to run one query for users and another for jobs and stitch them together in application code — which is exactly the inefficient pattern the "N+1 problem" describes. The ON clause is the join condition; getting it wrong (or omitting it) produces a Cartesian product where every row is paired with every other.

The join type decides what happens to rows that have no match on the other side.

INNER JOIN

Returns only rows that have a match in both tables. Users with zero jobs are excluded. This is the default and most common.

LEFT JOIN

Returns all rows from the left table, plus matches from the right — filling NULL where there's no match. Great for "all users and their jobs, even users with none."

-- Every user, with a job count that may be 0
SELECT u.email, COUNT(j.id) AS job_count
FROM "User" u
LEFT JOIN "GenerationJob" j ON j.user_id = u.id
GROUP BY u.email;

RIGHT JOIN is the mirror image (all rows from the right table); it's rarely used because you can just swap the table order and use LEFT. FULL OUTER JOIN keeps unmatched rows from both sides. A neat interview trick: a LEFT JOIN with WHERE right.id IS NULL finds rows that have no match — e.g. users who have never created a job.

Aggregate functions collapse many rows into a single summary value: COUNT(), SUM(), AVG(), MIN(), MAX(). GROUP BY lets you compute those summaries per group instead of over the whole table.

SELECT status, COUNT(*) AS n, MAX(created_at) AS latest
FROM "GenerationJob"
GROUP BY status;

This returns one row per distinct status, with the count and most-recent timestamp for each. The golden rule that trips people up: every column in the SELECT must either appear in the GROUP BY or be wrapped in an aggregate — otherwise the database wouldn't know which value from the group to show. As covered earlier, use HAVING (not WHERE) to filter on the aggregated results.

A subquery is a query nested inside another. It lets you use the result of one query as input to another, and shows up in three main positions:

-- 1) In WHERE (a set to test against)
SELECT * FROM "User"
WHERE id IN (SELECT user_id FROM "GenerationJob" WHERE status = 'FAILED');

-- 2) In FROM (a derived table)
SELECT status, n FROM
  (SELECT status, COUNT(*) AS n FROM "GenerationJob" GROUP BY status) t
WHERE n > 10;

-- 3) In SELECT (a scalar value per row)
SELECT u.email,
       (SELECT COUNT(*) FROM "GenerationJob" j WHERE j.user_id = u.id) AS jobs
FROM "User" u;

A correlated subquery (like #3) references the outer query and runs once per outer row, which can be slow — often a JOIN or a window function is a better rewrite. The EXISTS form is usually preferred over IN for "does a related row exist?" because it can short-circuit on the first match and behaves correctly around NULLs.

Both stack the results of two queries on top of each other (they must have compatible columns). The difference is duplicate handling: UNION removes duplicate rows, which forces the database to sort or hash the combined result to detect them. UNION ALL keeps every row, including duplicates, and is therefore significantly faster.

SELECT email FROM active_users
UNION ALL          -- cheaper; use when you know there are no dupes
SELECT email FROM trial_users;

The practical takeaway for interviews: reach for UNION ALL by default and only pay for UNION's de-duplication when you genuinely need distinct rows. Note this is different from a JOIN — UNION combines rows vertically (more rows), while a JOIN combines them horizontally (more columns).

All three count, but subtly differently — a favourite interview detail because it exposes NULL awareness.

  • COUNT(*) counts every row in the group, NULLs included.
  • COUNT(column) counts only rows where that column is not NULL.
  • COUNT(DISTINCT column) counts the number of distinct non-NULL values.
SELECT
  COUNT(*)                 AS total_jobs,
  COUNT(finished_at)       AS finished_jobs,   -- skips NULL finished_at
  COUNT(DISTINCT user_id)  AS users_with_jobs
FROM "GenerationJob";

So on a jobs table, COUNT(*) tells you total jobs, COUNT(finished_at) tells you how many have completed, and COUNT(DISTINCT user_id) tells you how many unique users are represented — three different business questions from one scan.

An index is a separate, sorted data structure the database maintains alongside a table to find rows quickly. The analogy interviewers love is the index at the back of a book: instead of reading every page (a "full table scan") to find a topic, you jump straight to the right page. Without an index, finding WHERE email = 'x' means scanning every row; with one, the lookup is near-instant.

CREATE INDEX idx_job_user_id ON "GenerationJob"(user_id);
CREATE UNIQUE INDEX idx_user_email ON "User"(email);

Indexes are automatically created for primary keys and UNIQUE constraints. You typically add them to foreign-key columns and to columns you frequently filter, join, or sort on — for PrintArtZ, indexing GenerationJob.user_id makes "fetch this user's jobs" fast. The cost, covered in the next question, is that indexes aren't free.

The default index type in Postgres is a B-tree (balanced tree): a sorted, multi-level structure that supports fast equality and range lookups (=, <, >, BETWEEN, ORDER BY) in logarithmic time. Postgres also offers specialized types — GIN for JSONB/arrays/full-text, GiST for geometric/range data, and Hash for equality-only.

Indexes help reads that select a small fraction of a large table. They hurt in several cases:

  • Every INSERT/UPDATE/DELETE must also update the index, so write-heavy tables pay a tax.
  • Indexes consume storage and memory.
  • On low-cardinality columns (few distinct values, like a boolean) or when a query returns most of the table, the planner will often ignore the index and do a sequential scan anyway, because reading the table directly is cheaper than bouncing between index and table.

So indexing is a deliberate trade-off — index the columns your real queries filter and join on, not every column reflexively.

A composite (multi-column) index covers several columns in a defined order. It behaves like a phone book sorted by last name, then first name: you can look up efficiently by "last name" or by "last name + first name," but not by "first name" alone.

CREATE INDEX idx_job_user_status
  ON "GenerationJob"(user_id, status, created_at);

This is the leftmost prefix rule: the index helps queries filtering on user_id, on user_id + status, or all three — but a query filtering only on status can't use it effectively. So the ideal order puts the most selective, most frequently-filtered columns first. A well-ordered composite index can also serve an ORDER BY for free and even become a covering index (answering a query entirely from the index without touching the table).

EXPLAIN shows the query plan — the strategy the planner intends to use — without running the query: which indexes (if any) it will use, the join methods, and its estimated row counts and costs. EXPLAIN ANALYZE actually executes the query and reports the real timing and row counts, so you can compare estimates against reality.

EXPLAIN ANALYZE
SELECT * FROM "GenerationJob" WHERE user_id = 'abc';

The single most important thing to look for is Seq Scan vs Index Scan. A "Seq Scan" on a big table in a query you expected to be indexed usually means a missing or unusable index. A large gap between estimated and actual rows suggests stale statistics (fixed with ANALYZE). This is the primary tool for diagnosing slow queries — in an interview, saying "I'd run EXPLAIN ANALYZE first" signals you debug with evidence rather than guessing.

The N+1 problem is a classic ORM performance bug. You run 1 query to fetch a list (say N users), then loop over the results and fire 1 more query per item to fetch related data (each user's jobs) — ending up with N+1 round-trips to the database. For 100 users that's 101 queries where a single join would do.

// ❌ N+1: one query, then one per user
const users = await prisma.user.findMany();
for (const u of users) {
  u.jobs = await prisma.generationJob.findMany({ where: { userId: u.id } });
}

// ✅ Prisma eager-loads related rows in one efficient batch
const users = await prisma.user.findMany({ include: { jobs: true } });

The fix is eager loading — fetch the related data up front with a JOIN or a single batched query (Prisma's include/select, or a raw SQL join). It's insidious because it looks fine on 5 rows in development and quietly falls over in production. Recognizing and naming N+1 is a very common interview signal for someone who has done real backend work.

  • Select only needed columns — avoid SELECT * so less data is read and transferred, and covering indexes can kick in.
  • Filter early and specifically so the planner can use indexes and touch fewer rows.
  • Avoid functions on indexed columns in WHERE (e.g. WHERE lower(email) = … can't use a plain index on email) — or add an expression index for it.
  • Paginate with keyset pagination (WHERE id > last_id LIMIT 20) instead of large OFFSET values, which still scan and discard all skipped rows.
  • Batch writes and fix N+1 patterns to cut round-trips.
  • Keep statistics fresh (autovacuum/ANALYZE) so the planner makes good choices; add a materialized view for expensive, repeated aggregations.

The disciplined workflow is always the same: measure with EXPLAIN ANALYZE, find the real bottleneck, change one thing, and measure again.

A transaction is a group of one or more statements that execute as a single, all-or-nothing unit of work. The canonical example is a bank transfer: debit one account and credit another must both succeed or both fail — you can never leave money vanished in between. Postgres guarantees this through the ACID properties:

  • Atomicity: all statements commit together or none do; a failure rolls the whole thing back.
  • Consistency: a transaction moves the database from one valid state to another, respecting all constraints.
  • Isolation: concurrent transactions don't step on each other; each behaves as if it ran alone (to a degree set by the isolation level).
  • Durability: once committed, the data survives crashes and power loss (written to durable storage via the write-ahead log).

ACID guarantees are a major reason to choose a relational database like Postgres for data you can't afford to corrupt — such as user accounts, quotas, and billing in PrintArtZ.

BEGIN starts a transaction, COMMIT makes all its changes permanent and visible to others, and ROLLBACK discards every change since BEGIN as if it never happened.

BEGIN;
  UPDATE account SET balance = balance - 100 WHERE id = 1;
  UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;   -- both updates land together; ROLLBACK to undo both

Outside an explicit transaction, each statement in Postgres runs in its own implicit "autocommit" transaction. In application code you usually don't write this raw SQL — you wrap logic in the ORM's transaction API. For example, PrintArtZ can decrement a user's remaining quota and insert a GenerationJob inside one Prisma $transaction([...]) call, so a user never gets charged a credit without a job actually being created (or vice-versa).

Isolation levels control how much concurrent transactions can "see" of each other's in-progress work — trading strictness for concurrency. The SQL standard defines four, and each prevents more anomalies as you go up:

  • Read Uncommitted: can see others' uncommitted changes ("dirty reads"). Postgres treats this the same as Read Committed — it never allows dirty reads.
  • Read Committed (Postgres default): only sees committed data, but the same query run twice in one transaction can return different results ("non-repeatable read").
  • Repeatable Read: a snapshot fixed at transaction start, so re-reads are stable.
  • Serializable: the strictest — transactions behave as if they ran one after another, preventing all anomalies at the cost of possible serialization failures you must retry.
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
  -- ... critical work ...
COMMIT;

The anomalies to name are dirty reads, non-repeatable reads, and phantom reads. The pragmatic answer is that Read Committed is the sensible default for most web apps, and you raise the level only for specific operations that need stronger guarantees.

A deadlock is a standoff where two transactions each hold a lock the other needs, so neither can proceed. Transaction A locks row 1 and wants row 2; transaction B has locked row 2 and wants row 1 — they wait forever. Postgres automatically detects this cycle and kills one transaction (raising a deadlock error) so the other can continue.

-- Tx A: locks row 1, then waits for row 2
-- Tx B: locks row 2, then waits for row 1  -> deadlock

Prevention strategies: always acquire locks in a consistent order (e.g. always update rows by ascending id) so cycles can't form; keep transactions short to shrink the window; touch fewer rows; and be ready to retry a transaction that fails with a deadlock or serialization error, since a retry usually succeeds. Related concept: SELECT … FOR UPDATE takes a row lock deliberately to prevent lost updates when you read-then-write.

Postgres uses MVCC — Multi-Version Concurrency Control. Instead of readers and writers blocking each other, an UPDATE doesn't overwrite a row in place; it writes a new version and keeps the old one around. Each transaction sees a consistent snapshot of the data as of a point in time, so readers never block writers and writers never block readers — a big concurrency win.

The trade-off is that outdated row versions ("dead tuples") accumulate and must be cleaned up. This is the job of VACUUM (and autovacuum, which runs automatically): it reclaims space from dead tuples and updates the planner's statistics. If autovacuum can't keep up on a very write-heavy table, you can see "bloat" and degraded performance — which is why understanding MVCC and vacuuming matters for anyone operating Postgres at scale.

JSONB lets you store JSON documents inside a column with a decomposed binary format that supports indexing and fast key lookups (unlike plain JSON, which is stored as text). This gives Postgres a "NoSQL inside SQL" capability — flexible, schemaless fields living alongside your strongly-typed relational columns.

-- store flexible metadata; query into it with -> and ->>
SELECT id FROM "GenerationJob"
WHERE params ->> 'model' = 'gpt-image-1';

-- a GIN index makes JSONB containment queries fast
CREATE INDEX idx_job_params ON "GenerationJob" USING GIN (params);

It's ideal for data whose shape varies or evolves — API responses, an AI request's parameters, feature flags, or event payloads. The caution: don't dump everything into JSONB. Data you filter, join, or constrain on should be real typed columns so you keep integrity and query performance; reserve JSONB for the genuinely fluid parts.

A CTE (Common Table Expression), written with WITH, is a named temporary result set that makes complex queries readable by breaking them into logical steps — and it can even be recursive (great for tree/hierarchy traversal).

WITH recent AS (
  SELECT * FROM "GenerationJob" WHERE created_at > now() - interval '7 days'
)
SELECT user_id, COUNT(*) FROM recent GROUP BY user_id;

Window functions perform calculations across a set of rows related to the current row without collapsing them like GROUP BY does — so you keep every row and get an aggregate/ranking alongside it.

-- rank each user's jobs by recency, keeping all rows
SELECT id, user_id,
       ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn
FROM "GenerationJob";

Functions like ROW_NUMBER(), RANK(), LAG(), and running SUM() OVER (…) are the go-to tools for "top N per group," running totals, and period-over-period comparisons — the kind of analytics that are awkward or impossible with plain aggregates.

Opening a Postgres connection is relatively expensive, and each connection consumes memory on the server — Postgres uses a process per connection, so it doesn't scale to thousands of them. A connection pool keeps a set of ready connections and hands them out to application requests, dramatically reducing overhead and protecting the database from being overwhelmed.

This matters intensely for serverless deployments. PrintArtZ's Next.js app runs functions that can spin up many concurrent instances, each wanting a database connection — without pooling you'd exhaust Postgres' connection limit almost immediately. Supabase provides PgBouncer, a lightweight external pooler, in front of Postgres.

# Prisma: pooled URL for the app, direct URL for migrations
DATABASE_URL="postgres://...@...pooler.supabase.com:6543/postgres?pgbouncer=true"
DIRECT_URL="postgres://...@...supabase.com:5432/postgres"

A key interview nuance: in transaction pooling mode, features that rely on session state (like prepared statements) need care — which is exactly why the config disables prepared statements (pgbouncer=true) and uses a separate DIRECT_URL for migrations.

Both are mature, popular, free relational databases, and for many CRUD apps either is fine. The distinctions worth knowing:

PostgreSQL

Strong standards compliance; richer types (JSONB, arrays, ranges), full-text search, and extensions (PostGIS); advanced features like CTEs and window functions matured earlier; excellent for complex queries and data integrity.

MySQL

Historically prized for simplicity and raw read speed on simple queries; huge in the LAMP/web ecosystem; very widely hosted. Some advanced SQL features arrived later than in Postgres.

The modern consensus is that Postgres has become the default choice for new projects that value correctness, a rich feature set, and complex querying — which is why PrintArtZ uses it. MySQL remains a solid, well-understood option, especially where a team already knows it or an ecosystem (like WordPress) expects it.

PostgreSQL

Free and open-source, no licensing cost, huge community, runs anywhere and on every cloud. Feature-rich and increasingly enterprise-grade; you self-manage or use a hosted provider like Supabase.

Oracle

Commercial, expensive per-core licensing, but with deep enterprise features (advanced partitioning, RAC clustering, tuning tools) and vendor support that large regulated organizations rely on.

The essence: Oracle is a heavyweight commercial database chosen by big enterprises for its ecosystem, support contracts, and specialized high-end features, while Postgres delivers most of that capability with no license fee and no lock-in. For a startup or side project like PrintArtZ, the cost and flexibility make Postgres the obvious pick; Oracle tends to appear where legacy systems or corporate procurement demand it.

This is one of the most common system-design questions. SQL/relational databases use a fixed schema, tables with relationships, strong ACID transactions, and a powerful join-based query language. NoSQL is an umbrella term; the document type (MongoDB) stores flexible, schemaless JSON-like documents and scales horizontally with ease.

Choose SQL when…

Data is structured and relational, integrity/transactions matter (accounts, payments, quotas), you need complex ad-hoc queries and joins, and the schema is reasonably stable. This describes most business apps — including PrintArtZ.

Choose NoSQL when…

The schema is highly variable or evolving fast, you need massive horizontal write scale, data is naturally document- or key-value-shaped, and you can relax strict consistency for availability and speed.

The mature, senior-sounding answer avoids dogma: pick based on the data's shape and the access patterns, not hype — and note that Postgres blurs the line with JSONB, giving you schemaless flexibility within a transactional relational engine, which is often the best of both worlds for an app like PrintArtZ.

SQL injection happens when user input is concatenated directly into a query string, letting an attacker inject their own SQL. The fix is to never build queries by string concatenation and instead use parameterized queries (prepared statements), where user values are sent separately from the query text and can never be interpreted as SQL.

// ❌ vulnerable — user input becomes part of the SQL
db.query(`SELECT * FROM "User" WHERE email = '${input}'`);

// ✅ parameterized — input is data, not code
db.query('SELECT * FROM "User" WHERE email = $1', [input]);

The reassuring part for PrintArtZ is that using an ORM like Prisma parameterizes queries by default, so ordinary use is safe. The risk resurfaces only if you drop down to raw SQL ($queryRawUnsafe with interpolation) — so the rule is: use the query builder, and if you must write raw SQL, always pass values as parameters. Defence-in-depth adds least-privilege database roles so even a breach is contained.
