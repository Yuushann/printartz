ORMs & Prisma — interview study guide

Prisma is the ORM PrintArtZ uses to talk to its PostgreSQL database (hosted on Supabase). This guide goes from what an ORM even is, up to the N+1 problem, connection pooling, and Prisma's engine-free driver-adapter architecture — in interview Q&A form with real schema, client, and SQL code. Click any question to expand.

ORM stands for Object-Relational Mapping. It's a layer that lets you work with your relational database using the objects and types of your programming language instead of writing raw SQL strings. A row in a table becomes an object; a table becomes a class or model; a column becomes a property.

The core problem it solves is the “object-relational impedance mismatch”: your code thinks in terms of objects, references, and inheritance, while the database thinks in terms of tables, rows, and foreign keys. Without an ORM you spend a lot of code hand-writing SQL, then manually mapping the flat result rows back into nested objects and back again on save.

With an ORM you write something like db.user.findMany() and get back typed User objects. It handles building the SQL, sending it over the connection, and turning the result set into language-native values. In PrintArtZ, Prisma is the ORM that maps our PostgreSQL tables (User, ProjectRequest, GenerationJob) to typed TypeScript objects.

The mapping is a set of consistent conventions. A table maps to a model/class, a row maps to an instance/object, a column maps to a field/property, and a foreign-key relationship maps to a reference or collection on the object (e.g. a user “has many” project requests).

-- database (PostgreSQL)
CREATE TABLE "User" (
  id    TEXT PRIMARY KEY,
  email TEXT UNIQUE NOT NULL
);

// application (TypeScript, via Prisma)
const user = await prisma.user.findUnique({ where: { id } });
user.email; // typed string, mapped from the email column

Instead of reading row["email"] from an untyped result set and hoping the column exists, you get user.email as a first-class typed property. The ORM owns the translation in both directions: reading rows into objects, and writing objects back into INSERT/UPDATE statements.

The biggest wins are productivity and safety. You write less boilerplate — no manual result mapping, no string concatenation to build queries. With a typed ORM like Prisma you also get compile-time type safety and autocomplete: if you rename a column in the schema, TypeScript flags every query that used the old name before you ever run the code.

ORMs also give you protection against SQL injection by default, because values are sent as parameters rather than spliced into the query string. And they smooth over some database portability — the same query code can target Postgres or MySQL with minimal changes.

The honest counterpoint an interviewer wants to hear: ORMs add an abstraction layer that can hide what SQL is actually running, can generate inefficient queries if used naively (the N+1 problem), and make very complex analytical queries awkward. The mature position is “ORM for the 95% of ordinary CRUD, drop to raw SQL for the tricky 5%.”

It's the fundamental friction between two different data models. Object-oriented code represents data as objects that can be nested, hold references to other objects, and use inheritance. Relational databases store data as flat rows in normalized tables, linked only by foreign keys, with no notion of nesting or inheritance.

Concrete examples of the mismatch: a many-to-many relationship in objects is just two lists pointing at each other, but in SQL it needs a separate join table. An object graph can be deeply nested, but a query returns a flat, possibly duplicated result set that must be “re-hydrated” into that graph. Inheritance has no direct SQL equivalent, so it must be faked (single-table, joined-table, etc.).

An ORM's whole job is to absorb this friction so you can mostly think in objects. Understanding that the mismatch never fully disappears — it's just managed — is what separates using an ORM well from using it blindly.

ORM

Fast to write, type-safe, autocompletion, injection-safe by default, portable across databases, easy CRUD. Can hide the real SQL, risks N+1 and over-fetching, weaker for complex analytics, adds a dependency and learning curve.

Raw SQL

Total control and maximum performance, expresses any query the database supports, no abstraction to fight. But it's verbose, error-prone, needs manual result mapping, and requires discipline to parameterize against injection.

These aren't mutually exclusive. In PrintArtZ we use Prisma for day-to-day CRUD and reach for prisma.$queryRaw only when a query is genuinely awkward in the query API — a common, pragmatic pattern in real codebases.

These are the two classic ORM design patterns. In Active Record (Rails, Laravel Eloquent), the model object is the row and carries its own persistence methods — you call user.save() on the object itself. It's convenient but couples your domain objects tightly to the database.

In Data Mapper (Java's Hibernate, TypeORM's repository mode), a separate mapper/repository handles persistence, keeping the domain objects ignorant of the database — repository.save(user). It's more decoupled and testable but more ceremony.

Prisma doesn't fit neatly into either. It uses a generated query builder / client where you call methods on a central client object, e.g. prisma.user.create(...), and the results are plain typed JavaScript objects with no attached methods. This “results are just data” approach avoids the surprises of objects that secretly hit the database when you touch a property.

Prisma is a modern, TypeScript-first ORM (technically a “next-generation ORM”) for Node.js. It has three main pieces you'll mention in an interview: Prisma Schema — a single declarative file that defines your data models; Prisma Client — an auto-generated, fully type-safe query builder; and Prisma Migrate — a migration system that turns schema changes into SQL migration files.

The workflow is: you edit schema.prisma, run prisma generate to (re)build the client, and run prisma migrate to sync the database. PrintArtZ uses Prisma against a PostgreSQL database hosted on Supabase, with models for User, ProjectRequest, and GenerationJob.

The schema is the single source of truth. It has three kinds of blocks: a datasource (which database and its connection URL), a generator (what to generate — usually the client), and one or more model blocks (your tables).

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

generator client {
  provider        = "prisma-client-js"
  previewFeatures = ["driverAdapters"]
}

model User {
  id        String   @id @default(cuid())
  email     String   @unique
  createdAt DateTime @default(now())
  requests  ProjectRequest[]
}

Note the schema is database-agnostic in shape but provider-aware: attributes like @id, @unique, and @default(now()) compile down to the right SQL constraints for Postgres. This one file drives both the generated client's types and the migrations.

Each model maps to a table; each line inside is a field. A field has a name, a type, optional modifiers (? for nullable, [] for a list/relation), and attributes prefixed with @. Here are two real PrintArtZ models:

model ProjectRequest {
  id        String   @id @default(cuid())
  prompt    String
  status    String   @default("pending")
  userId    String
  user      User     @relation(fields: [userId], references: [id])
  job       GenerationJob?
  createdAt DateTime @default(now())
}

model GenerationJob {
  id         String         @id @default(cuid())
  requestId  String         @unique
  request    ProjectRequest @relation(fields: [requestId], references: [id])
  imageUrl   String?
  finishedAt DateTime?
}

String/DateTime/Boolean/Int are scalar fields that become columns. Fields typed as another model (user, request) are relation fields — they don't create their own column; the @relation attribute points at the actual foreign-key column (userId). A ? makes it nullable/optional (a not-yet-finished job has no finishedAt).

prisma generate reads your schema.prisma and generates the Prisma Client — actual TypeScript/JavaScript code tailored to your exact models. This is the key idea: the client isn't a generic library, it's code generated from your schema, so it knows your models, fields, and relations by name.

import { PrismaClient } from "@prisma/client";
const prisma = new PrismaClient();

// autocompletes .user, .projectRequest, .generationJob
// and knows every field's type
const u = await prisma.user.findUnique({ where: { email } });

Because the types come from the schema, TypeScript catches mistakes at compile time — a typo'd field, a wrong where key, or forgetting a required field on create all fail the build. You must re-run generate whenever the schema changes (the migration commands do it for you), which is why it's wired into most projects' postinstall script.

Prisma exposes a consistent set of methods per model. The most common are findMany, findUnique, create, update, and delete:

// CREATE
const req = await prisma.projectRequest.create({
  data: { prompt: "A neon cat poster", userId: user.id },
});

// READ
const one  = await prisma.projectRequest.findUnique({ where: { id } });
const many = await prisma.projectRequest.findMany({
  where: { status: "pending" },
});

// UPDATE
await prisma.projectRequest.update({
  where: { id }, data: { status: "processing" },
});

// DELETE
await prisma.projectRequest.delete({ where: { id } });

Every method takes a single options object (where, data, select, include, etc.) and returns a typed result. There are also convenience methods like upsert (update or create), createMany, updateMany, and count.

Each new PrismaClient() opens its own connection pool to the database. If you create a client per request — or, in Next.js dev mode, if hot-reloading re-imports your module repeatedly — you can quickly exhaust the database's connection limit and see “too many connections” errors.

// lib/prisma.ts — one shared instance
import { PrismaClient } from "@prisma/client";

const globalForPrisma = globalThis as unknown as {
  prisma?: PrismaClient;
};

export const prisma =
  globalForPrisma.prisma ?? new PrismaClient();

if (process.env.NODE_ENV !== "production")
  globalForPrisma.prisma = prisma;

The pattern caches the instance on globalThis in development so hot reloads reuse it, while production gets a single module-level instance. PrintArtZ imports this shared prisma everywhere rather than instantiating new clients — a classic Next.js + Prisma gotcha interviewers like to probe.

A one-to-many relation (one User has many ProjectRequests) is expressed by putting a list field on the “one” side and a relation field plus a foreign-key scalar on the “many” side. Prisma uses the two together to know how the tables connect.

model User {
  id       String           @id @default(cuid())
  requests ProjectRequest[]          // the "many" side
}

model ProjectRequest {
  id     String @id @default(cuid())
  userId String                       // FK column
  user   User   @relation(fields: [userId], references: [id])
}

Only the “many” side (ProjectRequest) gets an actual userId column in the database — that's where the foreign key lives. The requests field on User is “virtual”: it doesn't add a column, it just tells Prisma how to fetch the related rows when you ask for them.

Prisma supports two styles. The implicit style: put a list of each model on the other, and Prisma silently creates and manages the join table for you.

model Post { id String @id; tags Tag[] }
model Tag  { id String @id; posts Post[] }
// Prisma manages a hidden "_PostToTag" join table

The explicit style: you define the join table yourself as its own model. You need this when the relationship itself carries data (e.g. addedAt, a role, an ordering), which is common in real schemas.

model PostTag {
  postId String
  tagId  String
  post   Post @relation(fields: [postId], references: [id])
  tag    Tag  @relation(fields: [tagId], references: [id])
  @@id([postId, tagId])   // composite primary key
}

Under the hood a many-to-many is always a join table with two foreign keys — implicit just hides the bookkeeping. Interviewers like to hear you know both and when explicit is required.

Both shape what a query returns, but they work oppositely. include keeps all scalar fields of the model and adds related records on top. select is exclusive — it returns only the fields you list, and nothing else.

// include: full ProjectRequest PLUS its related job
const withJob = await prisma.projectRequest.findUnique({
  where: { id },
  include: { job: true },
});

// select: ONLY these two fields, nothing more
const slim = await prisma.projectRequest.findUnique({
  where: { id },
  select: { id: true, status: true },
});

You can't use include and select at the top level of the same query. To fetch relations while also narrowing fields, nest a select inside — e.g. select: { id: true, job: { select: { imageUrl: true } } }. Preferring select to fetch only what you need is a simple, effective way to avoid over-fetching.

Filtering goes in the where object, which supports rich operators. Sorting uses orderBy. Prisma translates these into the equivalent SQL WHERE and ORDER BY clauses.

const results = await prisma.projectRequest.findMany({
  where: {
    status: { in: ["pending", "processing"] },
    prompt: { contains: "poster", mode: "insensitive" },
    createdAt: { gte: new Date("2026-01-01") },
    user: { email: { endsWith: "@infoblox.com" } }, // filter on relation
  },
  orderBy: { createdAt: "desc" },
});

Operators include equals, not, in, lt/lte/gt/gte, contains/startsWith/endsWith, and boolean combinators AND/OR/NOT. You can even filter a model by conditions on its related records, as with the nested user filter above.

Prisma offers two pagination styles. Offset pagination uses skip + take — simple and lets you jump to any page, but gets slow on large tables (the database still scans the skipped rows) and can show duplicates/gaps if data changes between pages.

// Offset — page 3, 20 per page
const page = await prisma.projectRequest.findMany({
  skip: 40, take: 20, orderBy: { createdAt: "desc" },
});

Cursor pagination uses a stable field (usually the id) to say “give me the next N after this row.” It stays fast at any depth and is stable under inserts, which is why it's preferred for infinite scroll and large datasets.

// Cursor — next 20 after the last id seen
const next = await prisma.projectRequest.findMany({
  take: 20,
  skip: 1,                    // skip the cursor row itself
  cursor: { id: lastSeenId },
  orderBy: { id: "asc" },
});

This is a subtle but important point. When you use include, Prisma historically did not emit a single big SQL JOIN; instead it ran separate queries (one for the parent rows, one per included relation) and stitched the results together in memory. This avoids the row-duplication and data-transfer blow-up that large joins cause with one-to-many relations.

More recent Prisma versions add a relation join strategy on PostgreSQL — you can opt in with relationLoadStrategy: "join" to have it use a single query with lateral joins and JSON aggregation, or keep "query" (the multi-query default). Crucially, either way it's a fixed, small number of queries, not one query per parent row — so include does not itself cause an N+1 problem. The N+1 trap comes from looping and querying inside the loop, which we cover in the Advanced tab.

Prisma lets you create or connect related records in a single create/update call by nesting create, connect, connectOrCreate, etc. inside data. The whole nested write runs in one implicit transaction, so it's atomic.

// Create a request AND its generation job together
const req = await prisma.projectRequest.create({
  data: {
    prompt: "Retro travel poster of Mars",
    user: { connect: { id: user.id } },   // link existing user
    job:  { create: { requestId: "" } },  // create related job
  },
  include: { job: true },
});

connect links to an existing row via a unique field, create makes a new related row, and connectOrCreate does whichever applies. This replaces what would otherwise be several separate inserts plus manual foreign-key wiring — and because it's atomic, you never end up with a request whose job failed to save.

A migration is a versioned, ordered change to your database schema — a SQL script that transforms the database from one state to the next (add a table, add a column, change a type, add an index). Migrations are the database equivalent of source-controlled code changes.

We need them because a schema evolves over time and must change consistently across every environment — your laptop, CI, staging, and production — and across every teammate's machine. Committing migration files to git gives you a reproducible history: anyone can rebuild the exact schema by replaying the migrations in order, and you have a record of what changed, when, and why.

prisma migrate dev

Diffs the schema, generates a named SQL migration file, applies it, and records it in the _prisma_migrations history table. Keeps a reviewable, replayable audit trail. The right tool for anything shared or heading to production.

prisma db push

Directly pushes the schema state into the database with no migration file and no history. Fast for prototyping and throwaway/dev databases, but you lose the audit trail and can't cleanly reproduce the change elsewhere.

Rule of thumb: use db push while rapidly iterating on a schema alone, and switch to migrate dev once the schema stabilizes and the change needs to reach teammates or production. In production you run the pre-generated migrations with prisma migrate deploy, which applies pending migrations without trying to generate new ones.

Prisma keeps two things in sync. On disk, each migration is a folder under prisma/migrations/ containing a timestamped name and a migration.sql file — these are committed to git. In the database, a special table called _prisma_migrations records which migrations have already been applied (name, checksum, timestamp).

prisma/
  schema.prisma
  migrations/
    20260110090000_init/
      migration.sql
    20260212143000_add_generation_job/
      migration.sql

When you run migrate deploy, Prisma compares the folders against the _prisma_migrations table and applies only the ones not yet recorded, in order. The checksum lets it detect if a migration file was edited after being applied — a “drift” it will warn you about, because editing already-applied migrations breaks reproducibility.

Seeding is populating the database with an initial, known set of data — reference data (categories, roles), a demo admin user, or realistic sample rows for local development and tests. It makes fresh environments usable immediately and gives tests a predictable starting state.

// prisma/seed.ts
import { PrismaClient } from "@prisma/client";
const prisma = new PrismaClient();

async function main() {
  await prisma.user.upsert({
    where: { email: "demo@printartz.app" },
    update: {},
    create: { email: "demo@printartz.app" },
  });
}
main().finally(() => prisma.$disconnect());

You point Prisma at the script via a prisma.seed entry in package.json, then run prisma db seed (it also runs automatically after migrate reset). Using upsert keyed on a unique field makes seeds idempotent — re-running them doesn't create duplicates.

A transaction groups several database operations so they all succeed or all fail together (the “A” — atomicity — in ACID). If any step throws, everything rolls back, so you never leave the data half-updated. Prisma offers two forms of $transaction.

The array form runs a fixed batch of independent operations atomically:

const [job, updated] = await prisma.$transaction([
  prisma.generationJob.create({ data: { requestId: id, imageUrl } }),
  prisma.projectRequest.update({
    where: { id }, data: { status: "done" },
  }),
]);

The interactive form takes a callback and lets you run logic — reads, branching, then writes — inside one transaction, which you need when a later write depends on an earlier read:

await prisma.$transaction(async (tx) => {
  const req = await tx.projectRequest.findUnique({ where: { id } });
  if (req?.status !== "pending") throw new Error("already taken");
  await tx.projectRequest.update({
    where: { id }, data: { status: "processing" },
  });
});

In PrintArtZ, marking a request done and writing its generation job together is a natural transaction — you never want one without the other.

The danger is data loss and downtime: a naive rename can be interpreted as “drop the old column, add a new empty one.” The professional approach for a live system is the expand-and-contract pattern, done over multiple deploys.

Expand: add the new column, and deploy code that writes to both old and new (backfill existing rows via a data migration). Migrate reads: switch the app to read from the new column once it's fully populated. Contract: in a later migration, drop the old column once nothing references it.

The key idea is that each intermediate state keeps the currently-running code working, so you never have a moment where the deployed app and the database schema disagree. For a solo dev on a throwaway database you can just let Prisma recreate it, but interviewers want to hear the zero-downtime version for production.

The N+1 problem is the single most-asked ORM performance question. It happens when you fetch a list of N records (1 query), then loop over them and trigger a separate query for each one's related data — resulting in N additional queries, hence “N+1”. Because ORMs make single-object access feel free, it's easy to write this by accident.

// ❌ N+1: 1 query for requests, then 1 per request for its job
const requests = await prisma.projectRequest.findMany();
for (const r of requests) {
  const job = await prisma.generationJob.findUnique({
    where: { requestId: r.id },   // fires a query every iteration
  });
}

The fix is to let the ORM fetch the related data up front in a bounded number of queries using include (or select):

// ✅ Prisma fetches jobs in one batched extra query, not N
const requests = await prisma.projectRequest.findMany({
  include: { job: true },
});

So ORMs cause N+1 by making per-item lazy access effortless, and solve it by offering eager loading (include) and query batching. The lesson: watch for queries inside loops, and enable query logging so you can see how many statements really run.

Reach for raw SQL when the query API can't express what you need efficiently: complex aggregations and window functions, recursive CTEs, database-specific features (Postgres full-text search, JSONB operators), heavy analytical reports, or a hot query you've hand-tuned. Prisma supports this without forcing you off the ORM.

// Parameterized — safe against SQL injection
const rows = await prisma.$queryRaw`
  SELECT status, COUNT(*)::int AS n
  FROM "ProjectRequest"
  WHERE "createdAt" >= ${since}
  GROUP BY status
`;

Use the tagged-template form ($queryRaw / $executeRaw) so interpolated values become bound parameters — never build the string by concatenation, which reopens SQL injection. The trade-off is you lose full type inference (you type the result yourself) and portability, so keep raw SQL to the few places it earns its keep.

Opening a Postgres connection is relatively expensive, and Postgres caps the total number (often ~100). A connection pool keeps a set of connections open and hands them out to queries as needed, so you amortize the setup cost and stay under the limit. Prisma Client maintains its own pool per instance for a normal long-lived server.

The problem appears in serverless / edge environments (like Vercel functions, which PrintArtZ deploys to): each invocation may spin up its own instance with its own pool, and hundreds of concurrent invocations can blow past Postgres's connection limit instantly. The solution is an external pooler like PgBouncer that sits in front of the database and multiplexes many client connections onto a small set of real ones.

Supabase provides exactly this — a pooled connection string (transaction mode, via PgBouncer). PrintArtZ uses Supabase's pooled URL for the app's runtime queries and the direct connection only for migrations, which is the standard Prisma-on-serverless setup. In PgBouncer transaction mode you also disable prepared statements (or use Prisma's pooling-aware settings), because a connection isn't pinned to one client across statements.

Historically, Prisma Client didn't talk to the database directly. It shipped a separate query engine — a Rust binary bundled with your app — that received query instructions, generated the SQL, managed the connection pool, and returned results. That gave consistent behavior across databases but meant a large native binary that was awkward on serverless and edge runtimes.

The newer approach is driver adapters plus an engine-free (queryable) client: Prisma runs the query logic in JavaScript/WASM and connects through a standard Node database driver via an adapter, instead of the Rust binary managing the connection.

import { PrismaPg } from "@prisma/adapter-pg";
import { PrismaClient } from "@prisma/client";

const adapter = new PrismaPg({ connectionString: process.env.DATABASE_URL });
const prisma  = new PrismaClient({ adapter });

The benefits: no heavy native binary to deploy, it runs on edge/serverless runtimes, and it uses battle-tested drivers (and their pooling) directly — e.g. the pg driver for PostgreSQL. PrintArtZ uses this engine-free client with the pg driver adapter against Supabase, which is why the schema enables the driverAdapters preview feature.

Think of it as a spectrum of abstraction. Raw SQL is the lowest level — maximum power and control, most verbose, manual mapping. A query builder like Knex sits in the middle: it gives you a fluent, programmatic API that maps almost one-to-one to SQL (knex("users").where("id", id).select()) — no hand-written strings, but you're still thinking in SQL terms with no object mapping or relation graph. An ORM like Prisma is the highest level: you think in models and relations, and it generates the SQL and hydrates objects for you.

Query builder (Knex)

Thin, transparent layer over SQL; predictable output; great when you want SQL control without string-building. No model layer, no relation loading, less type safety.

ORM (Prisma)

Models, relations, migrations, strong types, eager loading. More magic and abstraction; occasionally you fight it for exotic queries.

They coexist well: use the ORM for the bulk of the app and its raw-SQL escape hatch (or a query builder) for the rare complex query. Prisma even bundles a typed raw layer (Prisma's $queryRaw) so you rarely need a separate builder.

Prisma

Schema-first via schema.prisma; generates a fully type-safe client; excellent DX, autocomplete, and migrations. Not a traditional class-based ORM — results are plain data. Newer, so a few advanced SQL features need the raw escape hatch.

TypeORM

Class/decorator-based (@Entity), supports both Active Record and Data Mapper, popular with NestJS. Very flexible but historically less reliable type inference and a rougher migration experience.

Sequelize is the older, mature, JavaScript-first option with a huge install base; it works well but its TypeScript support was bolted on later and feels less first-class. The short interview answer: pick Prisma when you want best-in-class TypeScript safety and DX (why PrintArtZ uses it), TypeORM when you want decorator-based entities or a NestJS-native fit, and Sequelize for mature, plain-JS projects. All three ultimately generate SQL against the same databases; the difference is developer experience and type safety.

  • N+1 queries: querying inside a loop; fix with include/select eager loading.
  • Over-fetching: pulling every column and relation when you need two fields; use select to fetch only what you need.
  • Missing indexes: filtering or sorting on unindexed columns; add @@index (or @unique) in the schema for hot query paths.
  • Unbounded reads: findMany() with no take/pagination on a big table; always cap and paginate.
  • Connection exhaustion: new client per request or no pooler on serverless; use a singleton and PgBouncer.
  • Chatty writes: many individual writes in a loop; batch with createMany or wrap in $transaction.

The professional habit: turn on query logging (new PrismaClient({ log: ["query"] })) or use EXPLAIN ANALYZE to see the SQL the ORM actually emits, then fix the measured hot path rather than guessing.

SQL injection happens when user input is concatenated into a query string so it can change the query's structure. ORMs prevent this by default because the query API sends values as bound parameters — the SQL text and the data travel separately, so input like "'; DROP TABLE ..." is treated as a literal string value, never as SQL.

// Safe: value is parameterized automatically
await prisma.user.findMany({ where: { email: userInput } });

// Safe raw: tagged template binds ${userInput} as a parameter
await prisma.$queryRaw`SELECT * FROM "User" WHERE email = ${userInput}`;

// ❌ UNSAFE: building the string yourself reopens injection
await prisma.$queryRawUnsafe(
  `SELECT * FROM "User" WHERE email = '${userInput}'`
);

So you're safe as long as you stay in the query API or use the tagged-template raw form. The place people slip is $queryRawUnsafe / $executeRawUnsafe with concatenated input — the “Unsafe” suffix is a deliberate warning. If you must use it, validate/whitelist the input (e.g. for a dynamic column name) rather than trusting it.
