Web Fundamentals — interview study guide

Before any framework, a full-stack developer needs a solid mental model of how the web actually works — what a browser does, how HTTP moves data, and how the pieces of a page fit together. This guide walks from absolute basics to advanced, in interview Q&A form with real requests and snippets, and ties back to how PrintArtZ's browser and server talk. Click any question to expand.

The web is built on a client–server relationship. A client is the program that requests something — almost always a web browser, but also a mobile app or a script. A server is a program running on a machine somewhere that listens for requests and sends back responses (HTML pages, JSON data, images, and so on).

The key idea is that they are separate programs, often on separate machines, communicating over a network using an agreed protocol (HTTP). The client never runs the server's code and the server never runs the client's code; they only exchange messages. This separation is what lets one server serve millions of different browsers, and lets a browser talk to many different servers.

In PrintArtZ, your browser is the client and the Next.js backend is the server. When you generate art, the browser (client) sends a request to /api/generate and the server does the heavy lifting and returns a result.

This is the classic interview question because it touches every layer. Walking through https://printartz.com:

  • DNS lookup: the browser translates the domain name into an IP address by asking DNS servers, because the network routes by IP, not by name.
  • TCP connection: the browser opens a TCP connection to that IP on port 443 (the standard three-way handshake) so data can travel reliably.
  • TLS handshake: because it's HTTPS, the client and server negotiate encryption and verify the server's certificate, establishing a secure channel.
  • HTTP request: the browser sends an HTTP request (e.g. GET /) over that encrypted connection.
  • Server responds: the server processes it and returns an HTTP response — a status code plus headers plus the HTML body.
  • Render: the browser parses the HTML, fetches linked CSS/JS/images (more requests), builds the page, and runs JavaScript to make it interactive.

A strong answer names DNS → TCP → TLS → HTTP → render in order and can explain why each step exists.

DNS (Domain Name System) is the internet's phone book. Humans remember names like printartz.com, but computers route packets using numeric IP addresses like 93.184.216.34. DNS is the distributed system that maps one to the other.

When you request a domain, your machine asks a chain of DNS servers — a resolver, then root, TLD (.com), and finally the domain's authoritative server — until it gets the IP. Results are cached at many levels (your OS, your browser, your ISP) with a TTL, so repeat lookups are near-instant. Without DNS, we'd have to memorize IPs, and sites couldn't change servers without breaking every link.

An IP address identifies a machine on the network. A port identifies a specific program/service on that machine — like an apartment number within a building. Web servers conventionally use port 80 for HTTP and 443 for HTTPS.

A domain is the human-friendly name that DNS resolves to an IP. So https://printartz.com means: use HTTPS (implying port 443), resolve printartz.com to an IP via DNS, and connect to that IP on port 443. During local development you'll often see http://localhost:3000 — localhost is your own machine (IP 127.0.0.1) and 3000 is the port the dev server listens on.

The browser's rendering engine goes through a pipeline. It parses the HTML into the DOM tree, and parses CSS into the CSSOM (style rules). It combines them into a render tree of what's visible, computes layout (the size and position of every box), and then paints pixels to the screen, often compositing layers for performance.

Along the way it discovers linked resources — stylesheets, scripts, images, fonts — and issues more HTTP requests to fetch them. JavaScript can modify the DOM, which may force the browser to re-run layout (reflow) and paint again. Understanding this is why front-end performance advice exists: minimizing render-blocking CSS/JS and avoiding layout thrash keeps the first paint fast.

TCP (Transmission Control Protocol) is the transport layer HTTP rides on. It provides a reliable, ordered byte stream: it establishes a connection with a handshake, retransmits lost packets, and guarantees data arrives in order. HTTP itself doesn't worry about lost packets because TCP handles it.

TLS (Transport Layer Security) is the encryption layer that turns HTTP into HTTPS. After the TCP connection is up, the TLS handshake negotiates keys and verifies the server's certificate (proving you're really talking to printartz.com and not an impostor). From then on all HTTP traffic is encrypted, so no one on the network can read passwords, session cookies, or the images you generate.

A CDN (Content Delivery Network) is a geographically distributed network of cache servers that sit in front of your origin server. When a user requests a static asset (an image, a CSS bundle, a pre-rendered page), the CDN serves it from an edge location physically close to the user instead of making the request travel to a distant origin.

This does two things: it cuts latency (the data travels a shorter distance) and it offloads traffic from the origin, improving scalability and resilience. DNS often points the domain at the CDN, which then decides whether to serve a cached copy or forward to origin. For PrintArtZ, generated images and static assets are ideal CDN candidates, while personalized, logged-in pages usually bypass the cache and hit the server.

HTTP (HyperText Transfer Protocol) is the request–response protocol the web speaks. The client sends a request describing what it wants; the server sends back a response. It is stateless — each request is independent and the server remembers nothing between them by default (which is why we need cookies/tokens for sessions).

A raw request and response are just text with a structured shape:

GET /api/gallery HTTP/1.1
Host: printartz.com
Accept: application/json
Cookie: session=abc123

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store

{ "items": [ { "id": 1, "title": "Sunset" } ] }

The request has a method, a path, headers, and an optional body; the response has a status line, headers, and a body.

Methods describe the intent of a request. The common ones map to CRUD-style operations:

  • GET — retrieve data; must not change anything on the server. Fetching the gallery is a GET.
  • POST — create something new or trigger an action. Submitting the PrintArtZ create form hits POST /api/generate.
  • PUT — replace a resource entirely with the payload you send.
  • PATCH — partially update a resource (change just some fields).
  • DELETE — remove a resource.

These are conventions, not enforced rules, but following them makes an API predictable and lets caches, proxies, and browsers behave correctly (for example, a browser will happily re-send a GET but warns before re-sending a POST).

The first digit of a status code tells you the category:

  • 2xx — Success: 200 OK, 201 Created (after a POST), 204 No Content.
  • 3xx — Redirection: 301 (moved permanently), 302/307 (temporary), 304 Not Modified (use your cached copy).
  • 4xx — Client error: the request was wrong. 400 bad request, 401 unauthenticated, 403 forbidden, 404 not found, 429 too many requests.
  • 5xx — Server error: the server failed. 500 internal error, 502 bad gateway, 503 service unavailable.

The interview-worthy distinction: 4xx is the client's fault, 5xx is the server's fault. If PrintArtZ returns 401 from /api/generate, your session is missing; a 500 means the server code threw.

Headers are key–value metadata attached to a request or response — they describe the message rather than being the message itself. They tell each side how to interpret the body, how to cache, who's asking, and more.

Common request headers: Content-Type (format of the body being sent), Accept (formats the client can handle), Authorization (credentials/token), Cookie (stored session data), User-Agent (the client software). Common response headers: Content-Type (format of the returned body), Cache-Control (how/whether to cache), Set-Cookie (store this cookie), and CORS headers like Access-Control-Allow-Origin. When PrintArtZ posts JSON it sends Content-Type: application/json so the server knows to parse the body as JSON.

A method is idempotent if making the same request multiple times has the same effect as making it once. GET, PUT, and DELETE are idempotent; POST is not. Deleting record 5 twice leaves the record deleted either way, but POSTing an order twice may create two orders.

This matters for reliability. Networks fail and clients retry, so idempotent operations can be safely retried automatically. Non-idempotent ones (like POST /api/generate, which spends a quota credit) need protection against duplicates — for example an idempotency key or a disabled submit button — so a flaky connection doesn't accidentally charge the user twice.

HTTPS is HTTP over TLS — the same protocol, but the connection is encrypted. With plain HTTP, everything travels in cleartext, so anyone between the browser and server (on public Wi-Fi, at an ISP) can read or tamper with passwords, cookies, and page content. HTTPS encrypts the traffic and, via the server's certificate, proves the server's identity.

Today HTTPS is effectively mandatory: browsers mark HTTP pages "Not Secure," many web features (service workers, geolocation, secure cookies) only work over HTTPS, and SEO favors it. In practice you get a free certificate (e.g. Let's Encrypt) or your host/CDN provides one. Any real deployment of PrintArtZ must be HTTPS-only so session cookies can't be sniffed.

HTTP/1.1 uses one request at a time per connection; a slow response blocks the ones behind it (head-of-line blocking), so browsers open many parallel connections as a workaround.

HTTP/2 introduced multiplexing: many requests and responses share one connection concurrently, plus header compression and server push. This dramatically reduces overhead when a page needs dozens of assets. HTTP/3 goes further by running over QUIC (built on UDP instead of TCP), which removes TCP-level head-of-line blocking and makes connection setup faster, especially on lossy or mobile networks. You rarely configure this by hand — modern hosts and CDNs negotiate the best version automatically — but knowing the progression (and why each version exists) is a common senior-level question.

The three core web languages have a clean division of labor, often described as content, presentation, and behavior:

  • HTML is the structure and content — headings, paragraphs, forms, images. It's the skeleton and its meaning (semantics).
  • CSS is the presentation — colors, spacing, layout, typography, responsiveness. It's the styling on top of the structure.
  • JavaScript is the behavior — responding to clicks, fetching data, updating the page dynamically.

Keeping them separate (separation of concerns) makes a site easier to maintain and more accessible: a page should still be meaningful with just HTML, look right with CSS, and become interactive with JS. Frameworks like React blur these lines by co-locating them per component, but the underlying roles are the same.

The DOM (Document Object Model) is the browser's live, in-memory tree representation of the HTML document. Each element, attribute, and piece of text becomes a node in the tree, and JavaScript can read and modify that tree through an API like document.querySelector, element.textContent, or element.addEventListener.

const btn = document.querySelector("#generate");
btn.addEventListener("click", () => {
  document.querySelector("#status").textContent = "Working...";
});

The crucial point: the DOM is not the HTML source text — it's a live object model built from it. When JS changes the DOM, the browser re-renders to match. This is exactly what libraries like React manage for you, but under the hood everything is DOM manipulation.

Semantic HTML means using elements that describe their meaning rather than generic containers — <header>, <nav>, <main>, <article>, <button>, <h1> instead of wrapping everything in <div> and <span>.

It matters for three reasons: accessibility (screen readers rely on semantics to let users navigate — a real <button> is focusable and keyboard-operable for free), SEO (search engines understand structure better), and maintainability (the markup documents itself). A common interview red flag is a "div soup" of clickable divs; using the right element is almost always the better answer.

Every element is a rectangular box made of four concentric layers, from inside out: content (the text/image), padding (space inside the border), border, and margin (space outside the border, separating it from neighbors).

The catch that trips people up is which parts count toward a declared width. With the default box-sizing: content-box, width is only the content, so padding and border are added on top, making the element wider than you asked. Most codebases set box-sizing: border-box, which makes width include padding and border — far more intuitive.

* { box-sizing: border-box; }
/* now width: 200px is the full visible width */

When multiple rules target the same element, CSS resolves the conflict by specificity — a weighting of how targeted the selector is. Roughly, from weakest to strongest: element/tag selectors (p) < class/attribute/pseudo-class selectors (.btn, :hover) < ID selectors (#main) < inline style="". A higher-specificity rule beats a lower one regardless of order.

If two rules have equal specificity, the one declared later wins (the cascade). !important overrides normal specificity entirely and is best avoided because it starts an escalation war. The practical takeaway: prefer low, consistent specificity (mostly classes) so styles stay predictable and easy to override.

JavaScript runs on a single thread, so it can only do one thing at a time. Synchronous code runs line by line, each statement blocking the next until it finishes. If a slow operation ran synchronously — like waiting for a network request — the entire page would freeze, unable to respond to clicks.

Asynchronous code avoids that. Operations like network requests or timers are started and then handed off; JavaScript continues running, and a callback (or a Promise's .then/await) runs later when the result is ready. This is why fetching from PrintArtZ's API doesn't freeze the UI:

console.log("1: before");
const res = await fetch("/api/gallery"); // pauses this function, not the page
console.log("3: after data");
// meanwhile the UI stayed responsive

The event loop is what lets single-threaded JavaScript handle asynchronous work without blocking. Synchronous code runs on the call stack. When you start an async operation (a timer, a fetch), the browser handles it in the background; when it completes, its callback is placed in a queue.

The event loop's job is simple: whenever the call stack is empty, take the next queued callback and run it. There are two queues with priority — the microtask queue (Promise callbacks) is drained fully before the next macrotask (like setTimeout). That's why a resolved Promise's .then runs before a setTimeout(…, 0) scheduled earlier:

console.log("A");
setTimeout(() => console.log("D"), 0);   // macrotask
Promise.resolve().then(() => console.log("C")); // microtask
console.log("B");
// order: A, B, C, D

Responsive design is building one layout that adapts to any screen size — phone, tablet, desktop — rather than shipping separate sites. It relies on fluid units (percentages, rem, fr, vw), flexible layouts (Flexbox and Grid), and media queries that apply different CSS at different breakpoints.

.grid { grid-template-columns: 1fr; }
@media (min-width: 720px) {
  .grid { grid-template-columns: 1fr 1fr; }
}

A common best practice is mobile-first: write the base styles for small screens, then use min-width media queries to enhance for larger ones. You also need <meta name="viewport" content="width=device-width, initial-scale=1"> in the HTML so mobile browsers don't pretend to be desktop-width — which is exactly why this study guide includes that tag.

An API (Application Programming Interface) is a defined contract that lets one program talk to another without knowing its internals. A web API is the set of endpoints a server exposes for clients to call. It's the "menu" of operations the client can request.

A REST API is a popular style for web APIs. Its core ideas: everything is a resource identified by a URL (/api/artworks/42), you act on resources using HTTP methods (GET to read, POST to create, etc.), it's stateless (each request carries everything it needs), and it typically exchanges JSON. So GET /api/artworks lists artworks and POST /api/artworks creates one — the URL names the thing, the method names the action.

JSON (JavaScript Object Notation) is a lightweight, text-based format for structured data. It supports objects, arrays, strings, numbers, booleans, and null — enough to represent almost any data — and it's human-readable.

{
  "id": 42,
  "title": "Neon City",
  "public": true,
  "tags": ["cyberpunk", "night"]
}

It won because it's simple, compact, and maps directly onto data structures in nearly every language (in JS, JSON.parse and JSON.stringify convert to and from objects). Being sent as Content-Type: application/json, it replaced the heavier, more verbose XML for most APIs. PrintArtZ's endpoints send and receive JSON.

fetch is the built-in browser API for making HTTP requests from JavaScript (the modern replacement for the old XMLHttpRequest, the "AJAX" object). It returns a Promise, so you use await or .then. A POST that sends JSON and reads JSON back looks like this:

const res = await fetch("/api/generate", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ prompt: "a fox in autumn" }),
});
if (!res.ok) throw new Error("Request failed: " + res.status);
const data = await res.json();
console.log(data.imageUrl);

Note two gotchas interviewers like: you must JSON.stringify the body yourself and set Content-Type, and fetch only rejects on network failure — an HTTP 404 or 500 still resolves, so you must check res.ok or res.status yourself.

There are three places to put data in a request, each with a purpose:

  • Path params identify which resource — they're part of the URL structure: GET /api/artworks/42 (artwork 42).
  • Query params refine or filter a request — appended after ?: GET /api/artworks?style=anime&page=2&sort=newest. They're ideal for optional filtering, sorting, searching, and pagination.
  • Request body carries the payload for create/update operations (POST/PUT/PATCH) — usually a JSON object, as in the generate prompt above.

Rule of thumb: path = identity, query = options/filters on a GET, body = the substantive data you're sending. You wouldn't put a large prompt in a query string (length limits, it appears in logs); you wouldn't put a filter in the body of a GET.

AJAX (Asynchronous JavaScript And XML) is the technique of requesting data from the server in the background and updating part of the page without a full reload. It's what made web apps feel like apps instead of a series of full-page navigations. The name is historical — the "XML" part is now almost always JSON.

The original AJAX API was XMLHttpRequest; today fetch is the modern, Promise-based way to do the same thing. So "using fetch to load data and update the DOM" is AJAX. In PrintArtZ, clicking Generate fires an async request and the page updates in place with the result — a textbook AJAX flow.

A well-designed API signals outcomes primarily through status codes, and includes a machine-readable error body for detail. Return the right code for the situation — 400 for invalid input, 401/403 for auth problems, 404 for missing resources, 429 when rate-limited, 5xx for server failures — and a consistent JSON shape:

HTTP/1.1 429 Too Many Requests
Content-Type: application/json

{ "error": "quota_exceeded", "message": "Daily limit reached", "retryAfter": 3600 }

The client should branch on the status: show a validation message for 400, redirect to login on 401, show "try again later" on 429/5xx, and never assume success. Meaningful codes plus a structured body let the UI respond precisely instead of showing one generic "something went wrong."

Because HTTP forgets everything between requests, the server needs the client to re-send a proof of identity on each request. The classic mechanism is a cookie. On login, the server responds with Set-Cookie: session=abc123; the browser stores it and automatically attaches Cookie: session=abc123 to every subsequent request to that site.

The server looks up that session id to know who you are and whether you're still authenticated. This is exactly how PrintArtZ keeps you signed in — the session cookie rides along on the request to /api/generate, so the server can check your identity and remaining quota without you re-entering your password each time.

All three store data in the browser, but they differ in lifetime, size, and whether they're sent to the server:

Cookies

Small (~4KB). Automatically sent to the server on every matching request. Have expiry, and security flags (HttpOnly, Secure, SameSite). Ideal for session/auth tokens.

localStorage / sessionStorage

Larger (~5–10MB). Never sent to the server automatically — JS reads them explicitly. localStorage persists until cleared; sessionStorage is wiped when the tab closes. Good for UI preferences and drafts.

The key interview point: use cookies for auth (especially HttpOnly so JavaScript can't read them, defending against XSS token theft), and Web Storage for non-sensitive client-only state. Never store a secret token in localStorage if an HttpOnly cookie is an option.

The same-origin policy is a fundamental browser security rule: scripts on one origin can't freely read data from a different origin. An origin is the combination of scheme + host + port — so https://printartz.com and https://api.other.com are different origins, and so is http:// vs https:// of the same host.

Without this policy, a malicious site you visit could use your logged-in cookies to silently read your email or bank data from other tabs. The policy isolates origins so a page can only script its own origin's data. It's the backdrop for CORS — which exists precisely to let servers opt in to safe cross-origin sharing.

CORS (Cross-Origin Resource Sharing) is the controlled exception to the same-origin policy. By default, browser JavaScript on origin A is blocked from reading responses from origin B. CORS lets server B explicitly allow specific other origins by sending response headers like Access-Control-Allow-Origin: https://printartz.com.

A crucial nuance: CORS is enforced by the browser, not the server, and it protects the user, not the data — the request often still reaches the server, but the browser withholds the response from the page if the headers don't permit it. For non-simple requests (e.g. a POST with JSON and custom headers), the browser first sends a preflight OPTIONS request to check permission. Because PrintArtZ's frontend and API share an origin, it avoids CORS entirely — a common reason to keep the API under the same domain.

Caching avoids re-downloading things that haven't changed. The server drives it with response headers. Cache-Control sets the policy: max-age=31536000, immutable tells the browser to reuse an asset for a year without asking, while no-store forbids caching (right for personalized API responses).

For validation, the server can send an ETag (a fingerprint of the content). On the next request the browser sends If-None-Match: <etag>; if nothing changed the server replies 304 Not Modified with no body, saving bandwidth. The standard production pattern is hashed filenames for static assets (app.9f2c.js) cached forever — when content changes, the filename changes, so there's never a stale-cache problem. Personalized pages, by contrast, use no-store so one user never sees another's data.

A session cookie should be hardened with three flags:

  • HttpOnly — the cookie is invisible to JavaScript (document.cookie can't read it), so an XSS injection can't steal the session token.
  • Secure — the cookie is only sent over HTTPS, never plain HTTP, so it can't be sniffed in transit.
  • SameSite — controls whether the cookie is sent on cross-site requests. Lax or Strict largely neutralizes CSRF attacks by not attaching the cookie to requests initiated from other sites.
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax; Max-Age=1209600

Together these defend against the two classic session attacks — token theft via XSS and forged requests via CSRF — which is why PrintArtZ's login cookie should set all three.

REST

Multiple endpoints, one per resource; the server defines the response shape. Simple, cacheable via HTTP, ubiquitous. Can lead to over-fetching (too much data) or under-fetching (needing several round-trips).

GraphQL

A single endpoint where the client asks for exactly the fields it needs in one query. Great for complex, nested data and varied clients. Costs more setup, and HTTP caching is trickier because it's typically one POST.

Rule of thumb: REST is the pragmatic default and fits PrintArtZ's handful of clear endpoints well; GraphQL shines when many different clients need many different slices of a deeply related data graph and round-trips are a real cost.

SPA (Single-Page App)

The server sends one shell; JavaScript renders views and swaps them client-side via fetch. Fast, app-like in-page navigation after load, but a heavier initial JS download and extra care needed for SEO and first paint.

MPA (Multi-Page App)

Each navigation loads a fresh HTML page from the server. Simple, great SEO and first paint, less JS — but full reloads feel less fluid and share less state across pages.

Modern frameworks like Next.js blur the line: they server-render each page (MPA-like first paint and SEO) then hydrate into an SPA-like experience for subsequent navigation — giving you both benefits, which is the model PrintArtZ follows.

Session cookies

The server stores session state and gives the browser an opaque id in an HttpOnly cookie, sent automatically. Easy to revoke (delete server-side), well-protected from XSS, but requires server/session storage and needs CSRF defenses.

Tokens (JWT)

A signed, self-contained token the client stores and sends in an Authorization: Bearer header. Stateless and great across services/APIs and mobile, but hard to revoke before expiry, and risky if stored where JS (and thus XSS) can read it.

A common, balanced choice for a web app like PrintArtZ is session-style auth via a hardened HttpOnly cookie; token-in-header auth is more natural for public APIs, mobile clients, and service-to-service calls. This is a pointer, not the whole story — see the dedicated security/auth material for depth.

Server-side rendering (SSR)

Server sends fully-formed HTML per request. Fast first paint, strong SEO, works before JS loads. Costs server work each request and a hydration step to become interactive.

Client-side rendering (CSR)

Server sends a near-empty shell; the browser fetches data and builds the DOM with JS. Cheap, snappy in-app navigation, but slower first paint and weaker SEO on its own.

The trade-off comes down to who does the work and when. Content that needs SEO and a quick first paint (landing pages, galleries) favors SSR; highly interactive, authenticated dashboards can lean CSR. PrintArtZ's user-specific pages are server-rendered on demand because they depend on the logged-in user and database, then hydrate for interactivity.
