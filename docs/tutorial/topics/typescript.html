TypeScript — interview study guide

TypeScript is the language PrintArtZ is written in end to end — the React frontend, the Next.js API routes, the Prisma database layer, and the shared zod schemas all speak it. This guide goes from absolute basics to advanced, in interview Q&A form with real code and the kind of full, spoken-aloud answer an interviewer expects. Click any question to expand.

TypeScript is a superset of JavaScript developed by Microsoft that adds an optional static type system on top of the language. Any valid JavaScript is already valid TypeScript, so adoption can be gradual — you add types where they help.

The problem it solves: JavaScript is dynamically typed, so a whole class of mistakes — calling a function with the wrong arguments, reading a property that doesn't exist, assuming a value is a string when it's undefined — only surface at runtime, often in production. TypeScript catches these at compile time in your editor, before the code ever runs.

The other huge win is tooling: because the compiler knows the shape of your data, you get accurate autocomplete, inline documentation, safe rename/refactor across a whole codebase, and go-to-definition. On a project like PrintArtZ, where a value flows from a Prisma model through an API route into a React component, types let you change one thing and immediately see everywhere that breaks.

Browsers and Node.js don't understand TypeScript directly. A compiler (tsc, or a faster tool like SWC/esbuild that Next.js uses) transpiles the .ts/.tsx files down to plain JavaScript, stripping out all the type annotations in the process.

// input.ts
const name: string = "PrintArtZ";
// output.js (types erased)
const name = "PrintArtZ";

The critical consequence is type erasure: types exist only during development and compilation — they are completely gone at runtime. That means you can't check a TypeScript type with if (x is MyType) at runtime; the type simply doesn't exist anymore. This is why input coming from outside your program (a form body, an API response) still needs a real runtime validator like zod, which PrintArtZ uses on its API routes.

TypeScript has the core JavaScript primitives — string, number, boolean, null, undefined, bigint, symbol — plus arrays, objects, and tuples. You annotate a value with a colon followed by the type.

let title: string = "Rainforest poster";
let copies: number = 30;
let isPublic: boolean = false;
let tags: string[] = ["science", "grade-4"];
let point: [number, number] = [10, 20]; // tuple

Note that TypeScript uses lowercase string/number/boolean for the primitive types. The capitalized String/Number refer to the wrapper object types and you almost never want them. In practice you rarely write these annotations explicitly for locals because of inference (see the next question).

Type inference means TypeScript figures out the type on its own from the value you assign, so you don't have to write it. This keeps code clean while still fully typed.

let count = 5;          // inferred as number
const label = "poster"; // inferred as the literal "poster"
const nums = [1, 2, 3]; // inferred as number[]

The idiomatic style is to let inference do the work for locals and return values, and only add explicit annotations where inference can't help or where you want a contract: function parameters (which have no value to infer from) and the public shape of exported functions and data. Adding a return-type annotation to exported functions is a good habit — it makes the function's contract explicit and prevents an accidental internal change from silently altering the return type.

any is the escape hatch that turns type checking off for a value. A value typed any can be assigned anything, called, indexed, or passed anywhere with no complaints — it effectively opts that variable out of the type system.

let data: any = fetchSomething();
data.foo.bar();     // no error, may crash at runtime
const n: number = data; // no error either

It's discouraged because any is contagious: it spreads through everything it touches and silently disables the very safety you adopted TypeScript for. Most serious projects enable the noImplicitAny compiler flag so the compiler flags places where a type is silently any. When you genuinely don't know a type, reach for unknown instead — it's the safe version.

Both can hold a value of any type, but they behave oppositely when you try to use that value.

any

Disables checking. You can do anything to it with no errors — property access, calls, assignment to any type. Unsafe: pushes bugs to runtime.

unknown

The type-safe top type. You can hold anything, but you must narrow it (typeof/instanceof/validation) before you use it. Safe.

function handle(input: unknown) {
  // input.trim();          // ❌ compile error — must narrow first
  if (typeof input === "string") {
    input.trim();           // ✅ now known to be a string
  }
}

Rule of thumb: use unknown for values entering your program from the outside (JSON responses, JSON.parse output, thrown errors in a catch) and narrow them. This is exactly the pattern PrintArtZ uses when a request body arrives as unknown and is then validated by a zod schema into a properly typed object.

strict is a single flag in tsconfig.json that enables a family of stricter checks at once — most importantly strictNullChecks, noImplicitAny, and strictFunctionTypes. It's the setting that makes TypeScript actually deliver on its promise, and it's on by default in new Next.js projects like PrintArtZ.

// tsconfig.json
{ "compilerOptions": { "strict": true } }

The most impactful piece is strictNullChecks: with it on, null and undefined are no longer silently assignable to every type. A string can't secretly be null, so you must handle the empty case explicitly. This eliminates the infamous "cannot read property of undefined" crash by forcing you to deal with it at compile time. Starting a project without strict largely defeats the purpose of adopting TypeScript.

These three are easy to confuse but mean distinct things.

  • undefined is a real value — the absence of a value. A variable can literally hold it.
  • void is the return type of a function that doesn't return anything meaningful (it may return undefined, but you're not supposed to use it).
  • never is the type of something that never happens — a function that always throws or never terminates, or a branch that logically can't be reached.
function log(msg: string): void { console.log(msg); }
function fail(msg: string): never { throw new Error(msg); }

never is genuinely useful for exhaustiveness checking: if you handle every case of a union in a switch, the default branch narrows to never, and assigning it to a never-typed variable makes the compiler error the day someone adds a new case they forgot to handle.

You annotate each parameter after a colon and the return type after the parameter list. Parameters almost always need annotations because there's no value to infer them from; the return type can often be inferred but is good to state explicitly on exported functions.

function makeSlug(title: string, id: number): string {
  return title.toLowerCase().replace(/\s+/g, "-") + "-" + id;
}

// arrow function, same idea
const double = (n: number): number => n * 2;

You can also describe the whole function as a type, which is handy for callbacks and props: type Formatter = (input: string) => string;. This is the shape PrintArtZ uses for event handlers passed into React components.

A parameter is made optional with a ?, which makes its type include undefined. A default value makes it optional too, and infers the type from the default.

function generate(prompt: string, copies?: number) {
  const n = copies ?? 1;   // handle the undefined case
  // ...
}

function greet(name: string = "there") {
  return `Hi ${name}`;
}

An important rule: optional parameters must come after required ones. Also note that copies?: number means the type is number | undefined, so with strict mode on the compiler forces you to handle the missing case — often with the nullish-coalescing operator ?? as shown.

You describe an object's shape by listing its properties and their types. Properties can be optional (?) or readonly, which prevents reassignment after creation.

type Poster = {
  readonly id: string;   // can't be reassigned
  title: string;
  copies: number;
  description?: string;  // optional
};

const p: Poster = { id: "abc", title: "Volcano", copies: 30 };
// p.id = "xyz";  // ❌ error — id is readonly

readonly is a compile-time guarantee only (it's erased at runtime), but it's excellent for expressing intent — for example marking a database record's id and createdAt as immutable so no code accidentally overwrites them. There's also ReadonlyArray<T> / readonly T[] for arrays you don't want mutated.

Both describe the shape of an object and are interchangeable most of the time. The differences are at the edges.

interface

Object/class shapes. Supports extends and declaration merging (reopening to add members). Slightly better error messages. Preferred for public API contracts and classes.

type

A named alias for any type — unions, intersections, tuples, primitives, mapped/conditional types. More flexible; cannot be merged. Preferred for unions and computed types.

interface User { id: string; name: string; }
interface Admin extends User { role: "admin"; }

type Status = "idle" | "loading" | "done";  // only type can do this
type WithId<T> = T & { id: string };

A pragmatic answer for an interview: "I use interface for object shapes that might be extended or implemented, and type when I need unions, intersections, or anything computed. The most important thing is being consistent within a codebase." PrintArtZ leans on type because much of its typing is derived from zod schemas and Prisma, which produce union and mapped types.

An index signature lets you type an object whose keys aren't known ahead of time — a dictionary/map-like object where any string key maps to a value of some type.

type ScoreBoard = { [playerName: string]: number };
const scores: ScoreBoard = { amit: 10, sam: 7 };
scores["newPlayer"] = 3; // allowed

Use it for genuinely open-ended maps. When the set of keys is actually a known, finite set, prefer the Record utility type (e.g. Record<Status, string>) or a plain object type — it's more precise and catches typos. A caveat with index signatures under strict settings: reading an arbitrary key can yield undefined, so enable noUncheckedIndexedAccess if you want the compiler to force you to handle missing keys.

A union (|) means a value is one of several types. An intersection (&) means a value is all of several types combined into one shape.

type Id = string | number;          // union: either
type Draggable = { onDrag(): void };
type Resizable = { onResize(): void };
type Widget = Draggable & Resizable; // intersection: both

Unions model "this could be an error message or a result," which is everywhere in real apps. Intersections model "combine these capabilities" and are how you merge object types. A mental shortcut: for unions the set of allowed values is the union of the two; for intersections the set of required members is the union, so the allowed values shrink.

A literal type is a type whose only allowed value is one specific constant — like the string "loading" rather than any string. Combined with unions, they express a fixed set of options.

type Status = "idle" | "loading" | "success" | "error";
let s: Status = "loading";
// s = "done"; // ❌ error — not one of the allowed literals

This is one of TypeScript's most beloved features because it replaces loose strings and "magic constants" with a checked, autocompleting set. Note that const variables get literal types inferred (const x = "a" is type "a") while let widens to string; you can force literals on object properties with as const. PrintArtZ types a generation job's status this way so an invalid status is a compile error.

Narrowing is how TypeScript reduces a broad type (like a union) to a more specific one within a block of code, based on checks you write. Type guards are those checks. The compiler follows your control flow and updates the type accordingly.

function format(value: string | number) {
  if (typeof value === "string") {
    return value.toUpperCase(); // narrowed to string here
  }
  return value.toFixed(2);      // narrowed to number here
}

The built-in guards are typeof (for primitives), instanceof (for classes), the in operator (does an object have this property), and truthiness/equality checks. Narrowing is what makes union types practical — you handle each possibility in its own branch where the type is precise, and the compiler guarantees you covered them.

When a check is too complex for the built-in guards, you write a function that returns a type predicate — the special return type arg is Type. If it returns true, TypeScript narrows the argument to that type at the call site.

type Poster = { kind: "poster"; copies: number };

function isPoster(x: unknown): x is Poster {
  return typeof x === "object" && x !== null && (x as any).kind === "poster";
}

if (isPoster(data)) {
  data.copies; // ✅ narrowed to Poster
}

Type predicates are powerful but come with a responsibility: TypeScript trusts your boolean logic — if the runtime check is wrong, you've lied to the compiler and reintroduced unsafety. For validating external data, a schema library like zod is safer because its guard is derived from the same schema that describes the type.

A discriminated (or "tagged") union is a union of object types that all share a common literal property — the discriminant — whose value is unique per member. Checking that one property lets TypeScript narrow to the exact member, giving you fully typed access to that member's fields.

type Result =
  | { status: "success"; url: string }
  | { status: "error"; message: string }
  | { status: "loading" };

function render(r: Result) {
  switch (r.status) {
    case "success": return r.url;      // url exists here
    case "error":   return r.message;  // message exists here
    case "loading": return "…";
  }
}

It's a best practice because it makes "impossible states impossible" — you can't have an error with a url, or a success without one. Paired with a never check in the default branch, the compiler forces you to update every switch when a new variant is added. This exact pattern models the state of PrintArtZ's image-generation request (loading → success/error) far more safely than separate booleans like isLoading and hasError.

Optional chaining ?. safely reads a property that might be null/undefined, short-circuiting to undefined instead of throwing. It's a runtime feature and is completely safe.

const email = session?.user?.email ?? "guest";

The non-null assertion ! tells the compiler "trust me, this is not null/undefined here," removing null and undefined from the type. It is purely a compile-time claim — it generates no runtime check and will crash if you're wrong.

const el = document.getElementById("root")!; // asserts non-null

The advice interviewers want to hear: prefer real narrowing (an if check) or ?? over !. Reserve ! for cases where you genuinely know more than the compiler and can't easily prove it — overusing it quietly reintroduces the null crashes strict mode was meant to prevent.

Generics let you write a function, type, or class that works over many types while preserving the relationship between inputs and outputs. Think of a type parameter (usually written <T>) as a placeholder the caller fills in.

function identity<T>(value: T): T {
  return value;
}
const a = identity("hi");  // T = string, returns string
const b = identity(42);    // T = number, returns number

The alternative — using any — would work but throw away the type: identity(42) would return any, and you'd lose autocomplete and safety on the result. Generics give you reusability and full type information, which is why they're everywhere in libraries (Array<T>, Promise<T>, React's useState<T>).

By default a type parameter could be anything, so you can't safely access properties on it. A constraint with extends says "T must at least have this shape," which lets you use the guaranteed members while still being generic.

function longest<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b;
}
longest([1, 2], [1, 2, 3]); // ok — arrays have length
longest("ab", "abc");       // ok — strings have length
// longest(3, 5);           // ❌ number has no length

A very common pattern is constraining a key to be a real key of an object using K extends keyof T, which the built-in Pick and a typed get function both rely on. Constraints are how you make generics precise instead of "anything goes."

Types and interfaces take type parameters too, letting you build reusable container shapes. This is how you'd model a standard API envelope so every endpoint's response is typed consistently.

type ApiResponse<T> = {
  data: T;
  error: string | null;
  timestamp: number;
};

type PosterResponse = ApiResponse<Poster>;
type PosterListResponse = ApiResponse<Poster[]>;

You can also give type parameters defaults (type Box<T = string> = { value: T }) so callers can omit them. This kind of generic envelope is exactly how PrintArtZ keeps its API-route return shapes uniform while varying only the payload type.

A generic component lets one component work with any item type while keeping the render callback fully typed. The type parameter flows from the items prop into the renderItem callback.

type ListProps<T> = {
  items: T[];
  renderItem: (item: T) => React.ReactNode;
};

function List<T>({ items, renderItem }: ListProps<T>) {
  return <ul>{items.map((it, i) => <li key={i}>{renderItem(it)}</li>)}</ul>;
}

// usage — T is inferred as Poster, so `p` is typed
<List items={posters} renderItem={(p) => p.title} />

The payoff is inference: because you pass posters: Poster[], TypeScript infers T = Poster and the renderItem parameter is known to be a Poster with full autocomplete — no casting. Note that in .tsx files you sometimes write <T,> with a trailing comma to disambiguate the generic from a JSX tag.

Combining a generic with keyof lets you write a fully type-safe property accessor: the returned type is exactly the type of the property you asked for, and asking for a non-existent key is a compile error.

function getProp<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const poster = { id: "1", title: "Volcano", copies: 30 };
const t = getProp(poster, "title");  // typed as string
const c = getProp(poster, "copies"); // typed as number
// getProp(poster, "nope");          // ❌ not a key of poster

Here T[K] is an indexed access type — "the type of property K on T." This trio of features (generic + keyof + indexed access) is the backbone of type-safe helpers and libraries, and it's a strong signal in interviews that you understand how TypeScript's type-level features compose.

Utility types are generics TypeScript ships that transform existing types so you don't repeat yourself. The ones you'll use daily:

  • Partial<T> — makes all properties optional (great for update/patch objects).
  • Required<T> — makes all properties required.
  • Pick<T, K> — keeps only the listed keys.
  • Omit<T, K> — removes the listed keys.
  • Record<K, V> — an object type with keys K and values V.
  • Readonly<T> — makes all properties readonly.
type Poster = { id: string; title: string; copies: number };

type PosterUpdate = Partial<Omit<Poster, "id">>; // edit anything but id
type PosterPreview = Pick<Poster, "id" | "title">;
type CountByStatus = Record<"idle" | "done", number>;

The point is that these keep one type as the single source of truth: change Poster and every derived type updates automatically, so a preview or update type can never drift out of sync with the model.

These come in complementary pairs — knowing when to pick which is the point.

Pick<T, K>

Allowlist: start from nothing, keep only the keys you name. Best when you want a small subset of a big type.

Omit<T, K>

Denylist: start from everything, remove the keys you name. Best when you want "all but a few" (e.g. drop server-only fields).

Partial<T>

All properties optional. Perfect for PATCH/update payloads and default-merging config objects.

Required<T>

All properties required. Useful after you've filled in defaults and want to guarantee nothing is missing downstream.

In PrintArtZ, a form's draft state is naturally a Partial<CreateInput> while it's being filled, and the validated result is the full CreateInput — the utility types express that transition precisely.

keyof T produces a union of the property names of a type. typeof value (in a type position) captures the type of an existing runtime value so you can reuse it as a type. They're often combined.

const config = { theme: "dark", copies: 30, public: true };

type Config = typeof config;        // { theme: string; copies: number; public: boolean }
type ConfigKey = keyof Config;      // "theme" | "copies" | "public"

The typeof-plus-keyof combo is especially handy with as const objects — for example deriving a union of allowed values from a constant array of options, so your constant data and your types can never disagree. This keeps a single source of truth: the runtime object is the type.

A mapped type builds a new object type by iterating over the keys of another type and transforming each one — it's a "for each key" at the type level. This is actually how utility types like Partial and Readonly are implemented.

// How Partial is defined internally:
type Partial<T> = { [K in keyof T]?: T[K] };

// A custom one: make every property nullable
type Nullable<T> = { [K in keyof T]: T[K] | null };

// Modifiers: - removes optional/readonly
type Concrete<T> = { [K in keyof T]-?: T[K] };

You can add or remove ? and readonly modifiers (with +/-) and even remap keys with an as clause. Mapped types are how you write reusable transformations over shapes instead of hand-writing each variant — a strong advanced-level topic to demonstrate.

A conditional type chooses between two types based on a relationship, using the ternary-like T extends U ? X : Y syntax at the type level. They let types make decisions.

type ElementType<T> = T extends (infer U)[] ? U : T;

type A = ElementType<string[]>; // string
type B = ElementType<number>;   // number (not an array, so T)

The infer keyword shown above lets you extract a type from within another — here pulling the element type out of an array. Conditional types power many built-ins (ReturnType<T>, Awaited<T>, Exclude<T, U>) and when applied to a union they distribute over each member. They're the most advanced everyday feature; being able to read and reason about them signals real fluency.

Both are examples of TypeScript's superpower on a full-stack app: one source of truth generates the type. With zod you write a runtime schema once and infer the static type from it, so the validator and the type can never disagree.

import { z } from "zod";

const CreateInput = z.object({
  prompt: z.string().min(1),
  copies: z.number().int().min(1).max(100),
});

type CreateInput = z.infer<typeof CreateInput>;
// { prompt: string; copies: number } — derived automatically

Prisma does the analogous thing from your database schema: running prisma generate produces a fully typed client, so prisma.poster.findMany() returns typed Poster objects with no manual types. PrintArtZ shares the zod-inferred CreateInput type across the client form and the API route, so the browser and server literally agree on the request shape at compile time. This is the pattern to bring up when asked "why TypeScript on a full-stack project?"

A declaration file (.d.ts) contains only type information — no runtime code — describing the shape of some JavaScript so TypeScript can type-check code that uses it. Libraries written in JavaScript ship (or have community-provided) declaration files so you get types when you import them.

// types/global.d.ts — declaring an env var's type
declare namespace NodeJS {
  interface ProcessEnv {
    OPENAI_API_KEY: string;
    DATABASE_URL: string;
  }
}

DefinitelyTyped is the huge community repository of these files, published under the @types/* scope (e.g. npm i -D @types/node). Modern libraries increasingly bundle their own types, but when a plain-JS package doesn't, you install its @types package. You also write .d.ts files yourself to type global variables, augment existing modules, or describe non-code imports.

TypeScript

Errors caught at compile time, superb autocomplete/refactoring, self-documenting code, safer large-team collaboration. Costs a build step, extra syntax, and a learning curve.

JavaScript

Runs anywhere with zero build, less ceremony, faster to prototype. But whole classes of bugs only appear at runtime and refactoring is riskier.

The honest framing for an interview: TypeScript doesn't make your program do anything new at runtime — the output is just JavaScript. What it buys you is confidence at scale. The bigger the codebase and team, and the longer it lives, the more the up-front typing cost pays off. For a full-stack, multi-file app like PrintArtZ, the payoff is clear; for a five-line script, it may not be worth it.

A balanced answer shows maturity. TypeScript can slow you down for tiny throwaway scripts or quick prototypes where the build setup and annotation effort outweigh the benefit. Its types can also become extremely complex — deeply generic or conditional types can produce cryptic error messages and long compile times that hurt more than they help.

There's also a false-confidence risk: because types are erased at runtime, they don't protect you from bad external data. Code that leans on any or scatters as casts and ! assertions can look type-safe while silently reintroducing the exact bugs TypeScript was meant to prevent. The skill is knowing when to stop adding type complexity, and remembering to validate anything crossing your program's boundary at runtime.

TypeScript uses structural typing ("duck typing"): two types are compatible if their shapes match, regardless of their names or where they were declared. Languages like Java or C# are nominal — compatibility depends on the declared type name.

type Point = { x: number; y: number };
function print(p: Point) {}

const thing = { x: 1, y: 2, z: 3 };
print(thing); // ✅ ok — has x and y, extra z is fine

This makes TypeScript flexible, but occasionally you want nominal behaviour — e.g. to stop a UserId string from being mixed up with a PostId string. You simulate it with "branded types," adding a phantom property: type UserId = string & { readonly __brand: "UserId" }. Knowing that TypeScript is structural (and how to opt into nominal-like safety when needed) is a classic advanced question.

A type assertion with as tells the compiler to treat a value as a certain type. Crucially, unlike casting in languages like C#, it does no conversion and no runtime check — it's purely you overriding the compiler's judgement. If you're wrong, nothing stops the resulting crash.

const data = JSON.parse(text) as Poster; // trusts blindly — unsafe
// vs. validating for real:
const data = PosterSchema.parse(JSON.parse(text)); // throws if wrong

The takeaway interviewers look for: assertions are a promise, not a guarantee. Prefer narrowing or real validation; use as only when you legitimately know more than the compiler (like a DOM element's specific type). The double assertion as unknown as X is an even bigger red flag — a sign the types are being forced rather than modelled correctly.

TypeScript

Microsoft-backed, huge ecosystem, first-class editor tooling, its own compiler, and the de-facto industry standard. Most jobs and libraries assume it.

Flow

Meta's type checker for JS — similar goals and annotations, but far smaller community, fewer typed libraries, and declining adoption. Even Meta projects have migrated toward TS.

Both add static types to JavaScript via annotations that are stripped before running. TypeScript won decisively on ecosystem, tooling, and momentum — which is why it's what you'll be interviewed on and what PrintArtZ uses. A newer angle worth mentioning: engines are gaining the ability to ignore type annotations directly (Node's type stripping, the "types as comments" proposal), reflecting how mainstream TypeScript-style syntax has become.
