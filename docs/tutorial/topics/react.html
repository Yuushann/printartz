React — interview study guide

React is the UI library PrintArtZ's frontend is built on. This guide goes from absolute basics to advanced, in interview Q&A form with real code and the kind of full, spoken-aloud answer an interviewer expects. Click any question to expand.

React is an open-source JavaScript library for building user interfaces, created and maintained by Meta. Its core idea is that you break a screen into small, self-contained components — a button, a card, a form — and compose them together like Lego bricks.

The problem it solves: before React, keeping the screen in sync with your data was painful. With plain JavaScript or jQuery you'd manually find elements and mutate them (“when this changes, go update that span, toggle this class, remove that row”). As an app grows, these scattered manual updates become a web of bugs because the same piece of UI is touched from many places.

React flips this around. You write a function that says “given this data (state), here is what the UI should look like.” When the data changes, React re-runs that function and efficiently updates the real page for you. This is called being declarative: you describe the destination, not the turn-by-turn directions. The result is UI code that is far easier to reason about and maintain.

The DOM (Document Object Model) is the browser's live tree of the page's elements. Directly changing it many times is expensive because each change can trigger layout recalculation and repainting.

React keeps a lightweight JavaScript representation of the UI in memory called the Virtual DOM. When your state changes, React builds a brand-new virtual tree describing the desired UI, then diffs it against the previous virtual tree to find exactly what changed. This diffing process is called reconciliation. React then applies only that minimal set of changes to the real DOM in one batched update.

Two things make the diff fast: React assumes elements of different types produce different trees (so it replaces rather than deeply compares), and it uses keys in lists to match items between renders. A common interview clarification: the Virtual DOM isn't inherently “faster than the DOM” — it's a technique to minimize and batch costly real-DOM writes, and it gives you a clean declarative model as a bonus.

JSX is a syntax extension that lets you write HTML-like markup inside JavaScript. It is not HTML and it is not a requirement — a build tool (Babel/SWC) compiles it down to plain function calls.

const el = <h1 className="title">Hello</h1>;
// compiles to:
const el = React.createElement("h1", { className: "title" }, "Hello");

Key differences from HTML: you use className instead of class and htmlFor instead of for (because class/for are reserved words in JS); attributes are camelCased (onClick, tabIndex); and you embed JavaScript expressions with curly braces: <p>{2 + 2}</p>. A component must return a single root element (or a <>…</> Fragment) because createElement returns one node.

Imperative means you spell out each step to mutate the DOM. Declarative means you describe the desired result and let React reconcile the DOM to match.

// Imperative (vanilla JS)
const p = document.createElement("p");
p.textContent = count;
document.body.appendChild(p);

// Declarative (React) — UI is a function of state
return <p>{count}</p>;

Declarative code is easier to reason about because you only ever describe “what the UI is for the current state,” and there's a single place that defines it. You never have to track the sequence of past mutations to understand the current screen — a huge win as complexity grows.

React is deliberately a library: it owns the view layer (rendering components from state) and nothing else. It does not prescribe how you route between pages, fetch data, manage global state, or build/deploy — those are your choices.

A framework is more opinionated and provides those pieces out of the box. This matters practically: a small React app needs you to bolt on a router and a build setup, whereas a framework like Next.js (which PrintArtZ uses) wraps React and gives you file-based routing, server-side rendering, and backend API routes with sensible defaults. In an interview, mentioning this shows you understand the ecosystem, not just the library.

For a classic client-rendered app: the browser downloads an almost-empty HTML file with a root <div id="root"> and a script bundle. The bundle runs, and React “mounts” your app by calling createRoot(rootEl).render(<App />). React builds the initial virtual tree, creates the corresponding real DOM nodes, and inserts them under the root. After that, any state change triggers a re-render (render → reconcile → commit minimal DOM changes).

With a framework like Next.js the server can send fully-formed HTML first (server rendering) and then “hydrate” it — React attaches event listeners to the already-present markup so the page becomes interactive. That improves first paint and SEO compared to a blank shell.

A component is a reusable, independent piece of UI — in modern React it's simply a JavaScript function that accepts inputs (props) and returns JSX describing what to render.

function Greeting({ name }) {
  return <h1>Hello, {name}!</h1>;
}

Historically React also had class components that extended React.Component and used lifecycle methods (componentDidMount, etc.) and this.state. Since Hooks arrived (React 16.8), function components are the standard — they're shorter, easier to test, and can do everything classes could via hooks. One rule to remember: component names must be Capitalized, otherwise JSX treats them as literal HTML tags.

Props (“properties”) are the inputs a parent passes to a child, exactly like arguments to a function. They flow one way: parent → child.

function Welcome({ name }: { name: string }) {
  return <p>Welcome, {name}!</p>;
}
<Welcome name="Amit" />

A component must never modify its own props. React's model assumes a component is a pure function of its props and state — same inputs produce the same output. If children could mutate props, data flow would become unpredictable and React couldn't reliably decide what to re-render. If a child needs to change something, the parent passes down a callback (e.g. onChange) so the parent updates its own state instead.

Whatever you nest between a component's opening and closing tags is automatically passed as a special prop called children. It's the key to building generic wrapper/layout components that don't need to know what they'll contain.

function Card({ children }) {
  return <div className="card">{children}</div>;
}
<Card><h2>Title</h2><p>Body</p></Card>

This is the foundation of composition — a Dialog, Card, or Layout renders its frame and drops {children} in the middle, so it works with any content.

You map an array of data to an array of elements. React requires each sibling element in that list to have a unique, stable key.

{items.map((item) => (
  <li key={item.id}>{item.label}</li>
))}

Keys are how React matches elements between the old and new virtual trees during reconciliation. With correct keys, if you insert an item at the top, React knows the rest merely shifted and reuses their DOM nodes (and their internal state). Avoid using the array index as a key for lists that can reorder, insert, or delete — because indices shift, React mis-matches items, leading to wrong or “sticky” state (e.g. a typed value staying in the wrong row). Use a real, data-derived id.

Because JSX embeds expressions, you use normal JS: ternaries for either/or, and && for “render only if”.

{isLoggedIn ? <Dashboard /> : <SignIn />}
{error && <p className="error">{error}</p>}

The classic gotcha is with && and numbers: {count && <Badge/>} will render a literal 0 on screen when count is 0, because 0 is falsy but still a renderable value. Guard with a boolean instead: {count > 0 && <Badge/>}.

Composition means building complex UI by combining smaller components — passing them as children or as props — rather than creating class hierarchies. React's official guidance is “composition over inheritance”: a specialized dialog isn't a subclass of a generic dialog; it's the generic <Dialog> with specific content passed in.

This is more flexible and avoids the brittleness of deep inheritance chains. A powerful pattern is passing components as props (sometimes called “slots”), e.g. <Page header={<Nav/>} sidebar={<Menu/>} />. PrintArtZ composes primitives like Card, Button, and form controls together on each page rather than subclassing anything.

Props are data passed in from a parent and are read-only from the child's perspective. State is data a component owns and can change over time; when state changes, React re-renders that component (and its children) to reflect the new value.

const [count, setCount] = useState(0);
return <button onClick={() => setCount(count + 1)}>{count}</button>;

A helpful mental model: props are the function's arguments (fixed for this call), while state is the component's private, persistent memory between renders. Both are inputs to the render, and the rendered UI is a pure function of the two.

React decides whether something changed by comparing references (shallow, Object.is), not by deeply inspecting values. If you mutate an existing object or array in place and pass the same reference back, React sees “same reference → nothing changed” and may skip the re-render, so your UI goes stale.

// ❌ mutates the same array reference
todos.push(newTodo);
setTodos(todos);

// ✅ create a new array
setTodos([...todos, newTodo]);

// ✅ new object
setUser({ ...user, name: "Amit" });

Immutability also makes features like undo/redo and performance optimizations (React.memo, cheap equality checks) reliable, because a changed value always means a new reference.

A controlled component is a form input whose displayed value is driven by React state — state is the single source of truth. You set the input's value from state and update state in onChange.

const [text, setText] = useState("");
<textarea value={text} onChange={(e) => setText(e.target.value)} />

The benefit is that the value is always available in state for validation, conditional UI, or submission — PrintArtZ's /create form works this way. The alternative is an uncontrolled component, where the DOM holds the value and you read it via a ref only when needed (useful for simple or performance-sensitive forms).

When two sibling components need to share or stay in sync over the same data, you move (“lift”) that state up to their nearest common parent, then pass the value down as props and pass setter callbacks down so children can request changes. This preserves a single source of truth and one-way data flow.

The trade-off is prop drilling if the tree is deep; when that gets painful you reach for Context or a state-management library. A good instinct is to keep state as low as possible and only lift it when sharing is genuinely required.

Within a single render, state variables are a snapshot — count holds the value captured when that render ran, and it won't change mid-function. So calling the setter twice with the snapshot value collapses into a single increment:

// ❌ both read the same snapshot (say 0) -> ends at 1
setCount(count + 1);
setCount(count + 1);

// ✅ functional updater receives the latest state -> ends at 2
setCount((c) => c + 1);
setCount((c) => c + 1);

Separately, React batches multiple state updates that happen in the same event handler into one re-render for performance (in React 18+ this also applies inside promises/timeouts). So after several setState calls you get one render with the final values — which is why reading state right after setting it still shows the old value; the new value appears on the next render.

Hooks are functions (all starting with use) that let function components “hook into” React features like state and lifecycle — useState, useEffect, useContext, etc. They replaced the need for class components.

Two rules make them work: (1) Only call hooks at the top level of a component or custom hook — never inside loops, conditions, or nested functions. (2) Only call hooks from React functions, not plain functions. The reason is that React tracks hooks purely by their call order on each render; if the order changed between renders (say a hook was skipped inside an if), React would associate state with the wrong hook. An ESLint plugin enforces both rules automatically.

useEffect lets you run side effects — things outside pure rendering, like fetching data, setting up subscriptions/timers, or manually touching the DOM. It runs after the render is committed to the screen.

useEffect(() => {
  const id = setInterval(tick, 1000);
  return () => clearInterval(id); // cleanup
}, []); // dependency array

The dependency array tells React when to re-run the effect by comparing each dependency to its previous value: [] runs it once after mount; [query] re-runs whenever query changes; omitting the array runs it after every render. A frequent bug is leaving a value out of the array (a “stale closure,” where the effect keeps using an old value) — include everything the effect reads, or restructure so you don't need to.

The function you optionally return from an effect is its cleanup. React runs it before the effect fires again (dependencies changed) and when the component unmounts. Its job is to undo whatever the effect set up: clear intervals/timeouts, remove event listeners, close sockets, or cancel in-flight requests.

Without cleanup you get memory leaks and bugs — e.g. multiple intervals stacking up, or “setState on an unmounted component” style issues. In development, React 18's Strict Mode intentionally mounts, unmounts, and remounts components once to help you catch missing cleanups early.

useRef gives you a mutable object { current: … } that persists across renders but does not trigger a re-render when you change it. There are two main uses.

// 1) Reference a DOM node
const inputRef = useRef(null);
<input ref={inputRef} />
inputRef.current?.focus();

// 2) Hold a mutable value without re-rendering
const timerId = useRef(null);
timerId.current = setTimeout(...);

Rule of thumb: if a value should appear in the UI, it belongs in state; if it's a behind-the-scenes handle (a DOM node, a timer id, the “previous value”), it belongs in a ref.

Both cache something between renders based on a dependency array. useMemo caches a computed value; useCallback caches a function reference (it's essentially useMemo returning a function).

const total = useMemo(() => expensiveSum(items), [items]);
const handlePick = useCallback((id) => setSelected(id), []);

Use useMemo when a calculation is genuinely expensive, or to keep an object/array reference stable so it doesn't break a memoized child or an effect's dependency check. Use useCallback to keep a function's identity stable when it's passed to a React.memo child or used as an effect dependency. Important nuance for interviews: these have their own cost (memory + comparisons), so don't wrap everything — reach for them to fix a measured problem, not by reflex.

Context lets you share a value with a whole subtree without passing it through every intermediate component (“prop drilling”). You create a context, wrap part of the tree in its Provider, and any descendant reads it with useContext. Typical uses: theme, current user, locale.

const ThemeCtx = createContext("light");
<ThemeCtx.Provider value="dark"><App /></ThemeCtx.Provider>
const theme = useContext(ThemeCtx);

The catch: when a context value changes, every consumer re-renders. So putting fast-changing state (like form keystrokes) in a single large context can cause wide, expensive re-renders. Mitigations include splitting into multiple small contexts, memoizing the provider's value, or using a dedicated state library for high-frequency updates.

Use useState for simple, independent pieces of state. Reach for useReducer when state is complex (multiple related fields), when the next state depends on the previous one, or when updates fall into clear “actions” you'd like to centralize and test.

function reducer(state, action) {
  switch (action.type) {
    case "inc": return { count: state.count + 1 };
    case "reset": return { count: 0 };
    default: return state;
  }
}
const [state, dispatch] = useReducer(reducer, { count: 0 });
dispatch({ type: "inc" });

It's the same idea Redux popularized, but local to a component: all transition logic lives in one pure reducer function, which keeps complex components predictable.

A custom hook is a function whose name starts with use and which calls other hooks to package up reusable stateful logic. It lets you share behavior (not markup) between components — something class components struggled with.

function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  const toggle = useCallback(() => setOn((v) => !v), []);
  return [on, toggle] as const;
}
// usage
const [open, toggleOpen] = useToggle();

Each component that calls a custom hook gets its own isolated state — the hook shares the logic, not the data. Real-world examples: useFetch, useLocalStorage, useDebounce, useMediaQuery.

Three triggers: (1) the component's own state changed; (2) its parent re-rendered; or (3) a context it consumes changed. The one that surprises people is (2): by default, when a parent re-renders, React re-renders all its children, even if their props are identical.

Usually that's fine — re-rendering is cheap because it's just running functions and diffing; it does not necessarily touch the real DOM. You only need to optimize (with React.memo, state colocation, etc.) when profiling shows a specific, expensive subtree re-rendering too often.

React.memo wraps a component so it skips re-rendering when its props are shallow-equal to the previous render. It's the function-component equivalent of the old PureComponent.

const Row = React.memo(function Row({ item, onSelect }) { ... });

What defeats it: passing new references every render — inline object/array literals (style={{…}}) or inline functions (onSelect={() => …}) are brand-new each time, so the shallow compare always fails and the memo does nothing. That's exactly why you pair React.memo with useCallback/useMemo to keep those props stable.

Code-splitting ships less JavaScript upfront by loading parts of the app on demand. React provides lazy + Suspense:

const Heavy = React.lazy(() => import("./Heavy"));

<Suspense fallback={<Spinner />}>
  <Heavy />
</Suspense>

lazy takes a dynamic import() and only fetches that chunk when the component first renders; Suspense shows a fallback while it loads. Frameworks like Next.js do this automatically at the route level, so each page is its own chunk. Good candidates for manual splitting: modals, charts, editors — heavy things not needed on first paint.

An Error Boundary is a component that catches JavaScript errors thrown while rendering its subtree, logs them, and shows a fallback UI instead of letting the whole app crash to a blank screen. Traditionally these are class components implementing getDerivedStateFromError/componentDidCatch.

They catch render-phase errors, not errors in event handlers or async code (handle those with try/catch). In Next.js's App Router you get this declaratively via an error.tsx file per route segment, which isolates failures to that part of the page.

Server Components render on the server. They can talk to the database or use secrets directly, they ship zero JavaScript for themselves (only their HTML output reaches the browser), and they can't use state, effects, or event handlers. Client Components — opted in with the "use client" directive at the top of the file — run in the browser and can use useState, useEffect, and onClick.

The pattern is to keep most of the tree as server components for speed and security, and push interactivity to small client components at the leaves. PrintArtZ's /create page is a server component (it checks auth and reads the quota on the server) that renders a "use client" form component, CreateForm, for the interactive bits.

  • Unstable props: new object/array/function literals every render break React.memo and effect dependency checks.
  • Index-as-key on dynamic lists, causing mismatched state and unnecessary DOM churn.
  • State too high up: keeping state above where it's needed re-renders large subtrees; colocate state with the component that uses it.
  • Fat context values that change often, re-rendering every consumer.
  • Expensive work in render instead of memoizing or moving it out.
  • Rendering huge lists without virtualization (e.g. react-window).

The professional approach: measure first with the React DevTools Profiler, then fix the specific hot path — don't optimize blindly.

React

Declarative, reusable components, automatic state-driven updates, massive ecosystem and hiring pool. Costs a runtime + build step and a learning curve.

Vanilla JS

Zero dependencies, tiniest possible bundle, full control. Manual DOM updates become tangled and bug-prone as interactivity grows.

Rule of thumb: choose React (or similar) when the UI is stateful, component-heavy, and evolving — like PrintArtZ. For a mostly static page with a sprinkle of interactivity, vanilla JS or a light tool is the leaner choice.

React

A library for the view; uses JSX; unopinionated (you pick router/state); largest ecosystem and job market.

Angular

A full framework; TypeScript-first; batteries-included (router, DI, forms, HTTP); more structure but a steeper curve.

Vue sits between the two: approachable, template-based single-file components with built-in reactivity, and an official router/state library. All three are component-based with a reactive update model; in practice the decision is usually driven by team familiarity, ecosystem, and hiring rather than raw capability.

  • CSR (Client-Side Rendering): the server sends a near-empty shell; the browser downloads JS and renders everything. Snappy in-app navigation, but a slower first paint and weaker SEO because crawlers may see little HTML.
  • SSR (Server-Side Rendering): the server renders full HTML per request, then the client “hydrates” it. Better first paint and SEO; costs server work on each request.
  • SSG (Static Site Generation): pages are pre-rendered to HTML at build time and served from a CDN. Fastest and cheapest, ideal for content that changes rarely; needs a rebuild to update.

Next.js lets you choose per route and even mix them (plus incremental static regeneration). PrintArtZ's dynamic pages are server-rendered on demand because they depend on the logged-in user and database.

Skip React for simple static or marketing sites (plain HTML/CSS, or a static generator like Astro/Hugo do it faster with less JS), for tiny embeddable widgets where shipping the React runtime is disproportionate, or when your team/organization is standardized on another framework. The mature take is that React is a tool with trade-offs — added bundle size and complexity in exchange for a powerful component model — so you adopt it when that trade-off pays off, not by default.
