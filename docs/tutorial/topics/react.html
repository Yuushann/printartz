React — interview study guide

React is the UI library PrintArtZ's frontend is built on. This guide goes from absolute basics to advanced, in interview Q&A form with real code. Click any question to expand.

React is a JavaScript library for building user interfaces out of reusable components. Before React, updating the page meant manually finding DOM nodes and mutating them (jQuery-style), which got tangled fast.

React lets you describe what the UI should look like for a given state, and it figures out the minimal DOM changes needed. You write declarative code (“for this data, show this”) instead of imperative steps.

The real DOM (the browser's tree of elements) is slow to update repeatedly. React keeps a lightweight in-memory copy called the Virtual DOM. When state changes, React builds a new virtual tree, diffs it against the previous one (“reconciliation”), and applies only the changed parts to the real DOM.

Interview tip: the VDOM isn't “faster than the DOM” magically — it's a strategy to batch and minimize real DOM writes.

JSX is HTML-like syntax inside JavaScript. It's not HTML and not required — it compiles to React.createElement(...) calls.

const el = <h1 className="title">Hello</h1>;
// compiles to:
const el = React.createElement("h1", { className: "title" }, "Hello");

Note className (not class) and {} to embed JS: <p>{2 + 2}</p>.

Imperative: you list the steps (“create a div, set its text, append it”). Declarative: you describe the end result and let React sync the DOM.

// Imperative (vanilla)
const p = document.createElement("p");
p.textContent = count;
document.body.appendChild(p);

// Declarative (React)
return <p>{count}</p>;

Declarative code is easier to reason about because the UI is a function of state.

React is a library — it only handles the view layer. Routing, data fetching, and build setup are your choice (or a framework's). A framework like Next.js wraps React and provides those opinions. PrintArtZ uses Next.js so it gets routing + a backend for free.

A component is a reusable piece of UI — a function that returns JSX. Modern React uses function components (class components are legacy).

function Greeting() {
  return <h1>Hello!</h1>;
}

Component names must be Capitalized so React treats them as components, not HTML tags.

Props are inputs passed to a component (like function arguments). They are read-only — a component must never modify its own props.

function Welcome({ name }: { name: string }) {
  return <p>Welcome, {name}!</p>;
}
<Welcome name="Amit" />

Whatever you put between a component's tags is passed as children — great for wrappers/layouts.

function Card({ children }) {
  return <div className="card">{children}</div>;
}
<Card><h2>Title</h2></Card>

Use .map() to turn data into elements. Each needs a stable, unique key so React can track items across re-renders.

{items.map((item) => (
  <li key={item.id}>{item.label}</li>
))}

Avoid using the array index as a key when the list can reorder/insert — it causes subtle bugs (wrong item state). Use a real id.

{isLoggedIn ? <Dashboard /> : <SignIn />}
{error && <p className="error">{error}</p>}

Gotcha: {count && <X/>} renders 0 when count is 0. Prefer {count > 0 && <X/>}.

React builds UIs by composing components (passing children/props), not by class inheritance. It's more flexible: a <Dialog> can accept any content via children rather than subclassing.

PrintArtZ's Card, Button, etc. are composed together on each page.

Props come from the parent and are read-only. State is data a component owns and can change over time; changing it re-renders the component.

const [count, setCount] = useState(0);
<button onClick={() => setCount(count + 1)}>{count}</button>

React decides whether to re-render by comparing references. If you mutate an object/array in place, the reference is unchanged and React may skip the update. Always create a new object/array.

// ❌ mutates
todos.push(newTodo); setTodos(todos);
// ✅ new array
setTodos([...todos, newTodo]);

A form input whose value is driven by React state (single source of truth). PrintArtZ's /create form uses this.

const [text, setText] = useState("");
<textarea value={text} onChange={(e) => setText(e.target.value)} />

When two components need the same data, move the state to their nearest common parent and pass it down via props (plus setter callbacks). This keeps a single source of truth.

State is a snapshot for that render; count holds the value from when the render ran. Multiple updates using the stale value collapse into one.

// ❌ both read the same snapshot -> +1
setCount(count + 1); setCount(count + 1);
// ✅ functional update uses latest -> +2
setCount((c) => c + 1); setCount((c) => c + 1);

React also batches multiple setState calls in an event handler into one re-render.

1) Only call hooks at the top level — never inside loops, conditions, or nested functions. 2) Only call them from React function components or custom hooks. React relies on call order being identical every render.

useEffect runs side effects (data fetching, subscriptions, timers) after render. The dependency array controls when it re-runs.

useEffect(() => {
  const id = setInterval(tick, 1000);
  return () => clearInterval(id); // cleanup
}, []); // [] = run once on mount

[] = once; [x] = when x changes; omitted = every render.

To undo what the effect set up (clear timers, remove listeners, cancel subscriptions) before the next run and on unmount — preventing leaks and duplicate work.

A mutable box whose .current persists across renders without causing re-renders. Two uses: referencing a DOM node, or storing a mutable value (like a timer id).

const inputRef = useRef(null);
<input ref={inputRef} />
inputRef.current.focus();

useMemo caches a computed value; useCallback caches a function identity. Use them to avoid expensive recompute or to keep stable props for memoized children — not everywhere (premature optimization adds noise).

const total = useMemo(() => heavy(items), [items]);
const onPick = useCallback((id) => setSel(id), []);

Context shares values (theme, current user) down the tree without “prop drilling”. Create a context, wrap with a Provider, read with useContext.

const ThemeCtx = createContext("light");
<ThemeCtx.Provider value="dark"><App /></ThemeCtx.Provider>
const theme = useContext(ThemeCtx);

Overusing context for fast-changing state can cause wide re-renders — for that, a state library or local state is better.

Use useReducer when state is complex or the next state depends on the previous one via clear “actions”. It centralizes update logic like Redux, locally.

const [state, dispatch] = useReducer(reducer, { count: 0 });
dispatch({ type: "inc" });

A function starting with use that composes other hooks to reuse stateful logic.

function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  const toggle = useCallback(() => setOn((v) => !v), []);
  return [on, toggle] as const;
}

1) Its own state changed, 2) its parent re-rendered, or 3) a context it consumes changed. A parent re-render re-renders children by default (even if their props are equal) unless memoized.

Wraps a component so it skips re-rendering when its props are shallow-equal to last time. Pair with useCallback/useMemo so passed props keep stable identity.

const Row = React.memo(function Row({ item }) { ... });
const Heavy = React.lazy(() => import("./Heavy"));
<Suspense fallback={<Spinner />}><Heavy /></Suspense>

This ships less JS up front and loads the chunk on demand. Next.js does route-level splitting automatically.

A component that catches render errors in its subtree and shows a fallback instead of crashing the whole app. In Next.js App Router you use an error.tsx file per route segment.

Server Components render on the server, can access the DB/secrets directly, and ship zero JS for themselves. Client Components (marked "use client") run in the browser and can use state/effects/handlers.

PrintArtZ's /create page is a server component (checks auth, reads quota) that renders a "use client" form (CreateForm) for interactivity.

  • New object/array/function literals as props on every render (breaks memoization).
  • Index-as-key on dynamic lists.
  • Huge context values causing wide re-renders.
  • Not colocating state (state too high up re-renders too much).

React

Declarative, component reuse, state-driven updates, huge ecosystem. Overhead + build step.

Vanilla JS

No dependencies, tiny for simple pages. Gets unmaintainable as interactivity grows.

Use React when the UI is stateful and component-heavy (like PrintArtZ). For a static page, vanilla is fine.

React

Library, JSX, unopinionated, biggest ecosystem/jobs.

Angular

Full framework, TypeScript-first, opinionated, steeper learning curve.

Vue sits in between — approachable, template-based, single-file components. All three are component-based with reactivity; the choice is often team/ecosystem driven.

  • CSR (client-side render): browser downloads JS, then renders. Fast navigation, slower first paint, weaker SEO.
  • SSR (server-side render): server sends HTML per request. Better first paint + SEO.
  • SSG (static): HTML built once at deploy. Fastest, best for content that rarely changes.

Next.js lets you mix all three per route. PrintArtZ's dynamic pages are server-rendered on demand.

Simple static/marketing sites (plain HTML/CSS or a static generator), tiny widgets where the React runtime is overkill, or teams standardized on another framework. Don't add React just to add it.
