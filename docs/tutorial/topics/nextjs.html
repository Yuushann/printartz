Next.js — interview study guide

Next.js is the React framework PrintArtZ is built on — it gives us file-based routing, server rendering, and a backend (Route Handlers, Server Actions) in one codebase. This guide goes from absolute basics to advanced, in interview Q&A form with real code and the kind of full, spoken-aloud answer an interviewer expects. Click any question to expand.

Next.js is a React framework maintained by Vercel. React by itself is only the view layer — it renders components from state and nothing more. Next.js wraps React and supplies all the pieces a real app needs out of the box: file-based routing, server-side rendering and static generation, a backend (Route Handlers and Server Actions), image/font optimization, and a production build pipeline.

The problem it solves: with a plain React setup (say Create React App or a bare Vite SPA) you ship a nearly-empty HTML shell and let the browser render everything, then bolt on a router, a data-fetching strategy, and a separate backend yourself. That means slower first paint, weaker SEO, and a lot of glue code. Next.js gives you sensible defaults for all of that.

For PrintArtZ specifically, Next.js lets us keep the whole product — the marketing pages, the authenticated /create flow, the OpenAI image-generation API, and Auth.js — in a single codebase and single deployment, with pages that render on the server for speed and SEO.

Instead of declaring routes in code (as you would with React Router), Next.js derives your URLs from the folder structure inside the app/ directory. A folder becomes a URL segment, and a special page.tsx file inside it makes that segment publicly routable.

app/
  page.tsx            -> /
  create/page.tsx     -> /create
  gallery/page.tsx    -> /gallery
  art/[id]/page.tsx   -> /art/:id

The big advantage is that routing is convention over configuration: you never maintain a route table, and the URL map is obvious from the file tree. Not every file is a route — only reserved filenames (page, layout, route, loading, error) are special; everything else is just a normal module you can colocate next to the route that uses it.

Inside app/, certain filenames have built-in meaning and let you describe a route's behavior declaratively rather than wiring it up yourself:

  • page.tsx — the UI for a route; makes the segment reachable.
  • layout.tsx — shared UI that wraps a segment and all its children; preserves state across navigation.
  • loading.tsx — an instant loading state (a Suspense fallback) shown while the segment streams in.
  • error.tsx — an error boundary for the segment; catches render errors and shows a fallback.
  • not-found.tsx — UI rendered when notFound() is called or a route doesn't exist.
  • route.ts — a Route Handler (an API endpoint) instead of a page.
  • template.tsx — like a layout but re-mounts on every navigation.

Knowing these by heart signals to an interviewer that you understand the App Router's mental model: the file system is the configuration.

App Router (app/)

The modern default since Next.js 13. Built on React Server Components; components are server-rendered by default. Nested layouts, streaming, loading/error files, Server Actions, and colocation. Data fetched with plain async/await.

Pages Router (pages/)

The original system. Everything is a client component; data fetching uses getServerSideProps/getStaticProps. Simpler mental model, no Server Components, but no nested layouts or streaming.

Both still work and can even coexist in one project, but the App Router is where new features land and what Next.js recommends for new apps. PrintArtZ is built entirely on the App Router so we get Server Components, streaming, and Server Actions. In an interview, mention that the biggest conceptual shift is that App Router components run on the server by default — the opposite of the always-client Pages Router.

A typical App Router project has an app/ directory for routes, a public/ directory for static assets served from the root (/logo.png), and config files at the root. next.config.js (or .ts) is where you configure the framework — image domains, redirects, rewrites, experimental flags, environment behavior, and so on.

// next.config.js
const nextConfig = {
  images: { remotePatterns: [{ hostname: "oaidalleapiprod.blob.core.windows.net" }] },
  async redirects() {
    return [{ source: "/home", destination: "/", permanent: true }];
  },
};
module.exports = nextConfig;

For PrintArtZ we whitelist the OpenAI/blob image host here so next/image is allowed to optimize the generated artwork returned from our API. You typically keep this file small — most behavior lives in the route files themselves.

You navigate between routes with the <Link> component, which renders an <a> but intercepts the click to do a client-side transition — no full page reload. Next.js also prefetches the target route's code (and, in the App Router, its server-rendered payload) when the link scrolls into view, so navigation feels instant.

import Link from "next/link";
<Link href="/create">Start creating</Link>

// programmatic navigation (client component)
"use client";
import { useRouter } from "next/navigation";
const router = useRouter();
router.push("/gallery");

Note that in the App Router the router hooks (useRouter, usePathname, useSearchParams) come from next/navigation, not the old next/router, and they only work inside client components. Prefer <Link> for normal navigation and reserve router.push for programmatic cases like redirecting after a form submits.

In the App Router, every component is a Server Component by default. Server Components render on the server, can talk directly to the database or use secrets, and ship zero JavaScript for themselves — only their rendered HTML reaches the browser. The trade-off is that they can't use state, effects, or event handlers, because none of that exists on the server.

Client Components are opted into with the "use client" directive at the very top of the file. They run in the browser (after also rendering on the server for the initial HTML) and can use useState, useEffect, onClick, and browser APIs.

The recommended pattern is to keep most of the tree as Server Components for speed and security, and push interactivity to small Client Components at the leaves. PrintArtZ's /create page is a Server Component that checks auth and reads the user's quota on the server, then renders a "use client" CreateForm for the interactive prompt input and submit button.

"use client" is a directive placed as the first line of a file. It marks that file — and everything imported into it that isn't already a Server Component — as the boundary between the server and client worlds. From that boundary down, components are included in the JavaScript bundle sent to the browser and become interactive.

"use client";
import { useState } from "react";

export function CreateForm() {
  const [prompt, setPrompt] = useState("");
  return (
    <form>
      <textarea value={prompt} onChange={(e) => setPrompt(e.target.value)} />
      <button>Generate</button>
    </form>
  );
}

A common misconception is that you sprinkle it on every component — you don't. You put it only on the leaves that truly need interactivity. A key rule: a Server Component can import and render a Client Component, but a Client Component cannot import a Server Component directly (you pass it in as children or props instead).

  • CSR (Client-Side Rendering): the browser downloads JS and renders everything. Snappy in-app navigation, but slower first paint and weaker SEO. Used inside client components after hydration.
  • SSR (Server-Side Rendering): the server renders full HTML on each request, then hydrates. Best when content is personalized or always fresh — e.g. a page that depends on the logged-in user.
  • SSG (Static Site Generation): HTML is pre-rendered at build time and served from a CDN. Fastest and cheapest; ideal for content that rarely changes, like marketing pages.
  • ISR (Incremental Static Regeneration): the best of both — pages are static but automatically re-generated in the background after a revalidate interval, so you get CDN speed with periodically fresh data.

In the App Router you don't pick these with special functions anymore; the rendering strategy is inferred from how you fetch data. A route that reads cookies or uses { cache: "no-store" } becomes dynamic (SSR); one that fetches cacheable data stays static (SSG); adding next: { revalidate: 60 } gives you ISR. PrintArtZ's authenticated pages are dynamic because they depend on the session and database.

Hydration is the process where React takes the server-rendered HTML that's already in the page and "attaches" to it in the browser — wiring up event listeners and state so the static markup becomes interactive, without throwing away and re-rendering the DOM.

The classic bug is a hydration mismatch: the HTML React produces on the client differs from what the server sent. This happens when your render depends on something that isn't available or identical on the server — Date.now(), Math.random(), window, localStorage, or a locale-formatted date. React warns loudly and may discard the server HTML.

// ❌ differs between server and client
<p>{new Date().toLocaleTimeString()}</p>

// ✅ render browser-only values after mount
const [now, setNow] = useState<string | null>(null);
useEffect(() => setNow(new Date().toLocaleTimeString()), []);

The fix is to keep the first render deterministic and move browser-only work into useEffect, or gate it behind a mounted flag so it only runs client-side.

Streaming lets the server send HTML in chunks as it becomes ready, rather than waiting for the entire page. Fast parts (a header, a shell) show immediately, while slow parts (a component awaiting a database query) stream in when they're done. This dramatically improves perceived performance and Time To First Byte.

You get this by wrapping a slow component in <Suspense> with a fallback — or, at the route level, simply by adding a loading.tsx file, which Next.js automatically wires up as a Suspense boundary around the page.

import { Suspense } from "react";

export default function GalleryPage() {
  return (
    <>
      <h1>Community gallery</h1>
      <Suspense fallback={<GallerySkeleton />}>
        <RecentArt />  {/* async server component */}
      </Suspense>
    </>
  );
}

The key insight for interviews: streaming means a slow data dependency no longer blocks the whole page — the user sees a meaningful shell instantly and the slow region fills in progressively.

They interleave. A Server Component can render a Client Component, and — importantly — a Client Component can render Server Components passed to it as children or props, even though it can't import them directly. This "children slot" pattern lets you keep an interactive wrapper on the client while its content stays server-rendered and JS-free.

// Server Component (page)
<ClientTabs>
  <ServerRenderedPanel />   {/* stays on the server */}
</ClientTabs>

Under the hood, React serializes the Server Components' output into a special stream (the RSC payload) and sends it alongside the Client Component bundle; the client stitches them together. The practical takeaway: design so the interactive boundary is as small and as low in the tree as possible, so you ship minimal JavaScript. Also remember you can't pass non-serializable props (like functions) from a Server Component into a Client Component — except Server Action functions, which are a special case.

A folder named with square brackets, like [id], creates a dynamic segment that matches any value in that position of the URL. The matched value is passed to your page via the params prop.

// app/art/[id]/page.tsx  -> matches /art/123, /art/abc, ...
export default async function ArtPage({
  params,
}: {
  params: Promise<{ id: string }>;
}) {
  const { id } = await params;
  const art = await db.artwork.findUnique({ where: { id } });
  if (!art) notFound();
  return <ArtDetail art={art} />;
}

There are variations: [...slug] is a catch-all that matches multiple segments (/docs/a/b/c), and [[...slug]] is an optional catch-all that also matches the base path. In PrintArtZ, an individual artwork detail page lives at app/art/[id]/page.tsx. Note that in recent Next.js, params and searchParams are async and must be awaited.

A layout.tsx defines UI that wraps a route segment and all of its children, and it persists across navigation between those children — meaning it doesn't re-render or lose state when you move between sibling pages. The required root layout (app/layout.tsx) renders the <html> and <body> tags and is where you put global providers, fonts, and nav.

// app/layout.tsx (root)
export default function RootLayout({ children }) {
  return (
    <html lang="en">
      <body>
        <NavBar />
        {children}
      </body>
    </html>
  );
}

Layouts nest: a layout deeper in the tree renders inside its parent layout via {children}. So app/dashboard/layout.tsx wraps every page under /dashboard while still living inside the root layout. This is a headline App Router feature the old Pages Router lacked.

page.tsx

The unique UI for one specific route. Makes a segment publicly accessible. Re-renders when you navigate to a different page. Receives params and searchParams.

layout.tsx

Shared chrome (nav, sidebar) around many pages. Persists and keeps state across navigation between its children. Receives children. Does not receive searchParams.

Think of it as: the layout is the frame that stays put, and the page is the picture inside the frame that swaps as you navigate. A subtle but important detail — because layouts don't re-render on navigation, you shouldn't rely on a layout to re-read per-navigation data; put that in the page.

loading.tsx is an instant loading state for a segment. Next.js automatically wraps the segment's page in a Suspense boundary using this file as the fallback, so while the server renders/streams the page the user immediately sees your skeleton instead of a frozen screen.

error.tsx is an error boundary for the segment. It must be a Client Component and receives the error plus a reset() function to retry rendering. It catches render-phase errors in that segment (and below) so a failure is isolated to that part of the page instead of crashing the whole app.

"use client";
export default function Error({ error, reset }: {
  error: Error; reset: () => void;
}) {
  return (
    <div>
      <p>Couldn't load this page.</p>
      <button onClick={reset}>Try again</button>
    </div>
  );
}

Together they let you handle the loading and failure states of each route segment declaratively, just by dropping in a file — no manual boilerplate around every data fetch.

A route group is a folder wrapped in parentheses, like (marketing) or (app). It lets you organize routes and — crucially — apply a different layout to a set of routes without adding a URL segment. The folder name in parentheses is stripped from the path.

app/
  (marketing)/
    layout.tsx      // public site chrome
    page.tsx        -> /
    pricing/page.tsx -> /pricing
  (app)/
    layout.tsx      // authenticated chrome
    create/page.tsx -> /create

Here / and /create get completely different layouts even though neither URL contains "marketing" or "app". A related convention is private folders prefixed with an underscore (_components), which are excluded from routing entirely — useful for colocating helpers next to routes without accidentally exposing them as pages.

For dynamic pages you often want per-item SEO metadata and, for SSG, the list of pages to pre-build. Next.js provides generateMetadata and generateStaticParams for exactly this.

// app/art/[id]/page.tsx
export async function generateStaticParams() {
  const arts = await db.artwork.findMany({ select: { id: true } });
  return arts.map((a) => ({ id: a.id }));   // pre-render these
}

export async function generateMetadata({ params }) {
  const { id } = await params;
  const art = await db.artwork.findUnique({ where: { id } });
  return { title: `${art?.title} — PrintArtZ`, openGraph: { images: [art?.url] } };
}

generateStaticParams tells Next.js which dynamic values to statically generate at build time (turning a dynamic route into many static pages), and generateMetadata produces the <title>, description, and Open Graph tags per item — so each PrintArtZ artwork page has a proper preview when shared on social media.

Because Server Components run on the server, you can make them async and simply await your data — no useEffect, no loading state juggling, no client-side fetch waterfall. You can query the database directly or call an API, and only the rendered HTML ships to the browser.

// Server Component — runs on the server
export default async function GalleryPage() {
  const art = await db.artwork.findMany({
    orderBy: { createdAt: "desc" },
    take: 24,
  });
  return <Grid items={art} />;
}

This is a major simplification over the old client-side pattern of "render empty → useEffect → fetch → setState → re-render." The data is ready before the HTML is sent, which is faster and better for SEO. In PrintArtZ, the gallery and artwork pages read directly from Postgres via Prisma inside Server Components, so no database credentials or query logic ever reach the browser.

A Route Handler is Next.js's way of building an HTTP API endpoint inside the app. You create a route.ts file and export functions named after HTTP methods (GET, POST, etc.). They use the standard Web Request/Response APIs.

// app/api/generate/route.ts
import { NextResponse } from "next/server";

export const runtime = "nodejs";

export async function POST(req: Request) {
  const { prompt } = await req.json();
  const image = await openai.images.generate({ prompt, model: "..." });
  return NextResponse.json({ url: image.data[0].url });
}

This is how PrintArtZ exposes /api/generate: the client form POSTs a prompt, the handler calls OpenAI on the Node runtime (chosen because the OpenAI SDK and our secrets need Node, not the lighter Edge runtime), and returns the image URL as JSON. Route Handlers are the App Router replacement for the Pages Router's pages/api.

Route Handlers

Explicit HTTP endpoints (route.ts) you call with fetch. Right for public APIs, webhooks, third-party callbacks, streaming responses, or anything a non-React client consumes. You manage request/response yourself.

Server Actions

Async functions marked "use server" that you call like a normal function from a component or form. Right for mutations tied to your own UI — form submits, deletes. No manual fetch, no endpoint plumbing.

Rule of thumb: use a Server Action for a mutation triggered by your own UI (e.g. saving a title, deleting an artwork), and a Route Handler when you need a real URL — a public API, a webhook, or a streaming endpoint. PrintArtZ uses a Route Handler for /api/generate (it streams/returns from OpenAI and is a clear endpoint), which is a perfectly reasonable choice.

A Server Action is an async function that runs on the server but can be invoked directly from the client — you mark it with the "use server" directive. Next.js handles the network call for you; you never write a fetch. They're designed for mutations and integrate with HTML forms, so they even work before JavaScript loads (progressive enhancement).

// actions.ts
"use server";
import { revalidatePath } from "next/cache";

export async function saveTitle(formData: FormData) {
  const id = formData.get("id") as string;
  const title = formData.get("title") as string;
  await db.artwork.update({ where: { id }, data: { title } });
  revalidatePath(`/art/${id}`);
}

// in a component
<form action={saveTitle}>
  <input name="title" />
  <button>Save</button>
</form>

The nice property is that the mutation logic lives on the server (safe to touch the DB and secrets), yet you wire it up as if it were a local function passed to action. Pair it with revalidatePath/revalidateTag to refresh cached data after the change.

Next.js extends the native fetch with caching controls, and the option you choose determines the route's rendering behavior. By default recent Next.js treats fetches as dynamic unless you opt into caching, but the three explicit modes you should know are:

// Cache forever (static) — good for rarely-changing data
await fetch(url, { cache: "force-cache" });

// Always fresh (dynamic / SSR) — no caching
await fetch(url, { cache: "no-store" });

// Time-based revalidation (ISR)
await fetch(url, { next: { revalidate: 60 } });

// Tag-based, invalidated on demand
await fetch(url, { next: { tags: ["gallery"] } });
// later, after a mutation:
revalidateTag("gallery");

The mental model: caching in the App Router is per-request, tag-driven, and tied to rendering. A page that only reads cached data can be statically generated; one that reads uncached/dynamic data (or cookies/headers) is rendered per request. You invalidate with revalidatePath or revalidateTag after a mutation so users see fresh content.

Auth.js (formerly NextAuth) plugs into the App Router through a catch-all Route Handler at app/api/auth/[...nextauth]/route.ts. The [...nextauth] catch-all captures every auth sub-path — /api/auth/signin, /callback, /session, /signout — and routes them all to the Auth.js handler.

// app/api/auth/[...nextauth]/route.ts
import { handlers } from "@/auth";
export const { GET, POST } = handlers;

// reading the session in a Server Component
import { auth } from "@/auth";
export default async function CreatePage() {
  const session = await auth();
  if (!session) redirect("/api/auth/signin");
  // ...render the create flow for session.user
}

The clean part is that in Server Components you call auth() to read the session directly on the server — no client round-trip — and gate access (redirecting anonymous users away from /create). This ties together several concepts: catch-all dynamic routes, Route Handlers, and server-side data access.

The App Router gives you async helpers from next/headers to read per-request data inside Server Components and Route Handlers. Using any of them opts the route into dynamic rendering, because the output now depends on the incoming request.

import { cookies, headers } from "next/headers";

const cookieStore = await cookies();
const theme = cookieStore.get("theme")?.value;

const headerList = await headers();
const ua = headerList.get("user-agent");

For query strings, a page.tsx receives a searchParams prop (also async in recent versions), which is the server-side equivalent of reading the URL query — e.g. a paginated gallery reading ?page=2. In Client Components you'd instead use the useSearchParams hook from next/navigation. Knowing that these APIs force dynamic rendering is a favorite interview follow-up.

The <Image> component is Next.js's optimized replacement for <img>. It automatically serves images in modern formats (WebP/AVIF), resizes them to the right dimensions for the device, lazy-loads offscreen images, and reserves space to prevent layout shift (a key Core Web Vitals metric).

import Image from "next/image";

<Image
  src={art.url}
  alt={art.title}
  width={512}
  height={512}
  placeholder="blur"
  blurDataURL={art.blurHash}
/>

For external images (like the AI-generated artwork URLs PrintArtZ gets back from OpenAI), you must whitelist the host in next.config.js under images.remotePatterns, otherwise Next.js refuses to optimize them for security. The payoff is meaningfully faster loads and better vitals with almost no manual work.

next/font loads fonts at build time and self-hosts them from your own domain, so there's no runtime request to Google Fonts — that removes a third-party network round-trip and the privacy concern of leaking user IPs to Google. It also automatically applies font-display: swap and can reserve metrics to eliminate the "flash of unstyled text" and layout shift when the font loads.

import { Inter } from "next/font/google";
const inter = Inter({ subsets: ["latin"] });

export default function RootLayout({ children }) {
  return <html className={inter.className}>{/* ... */}</html>;
}

You configure it once in the root layout and apply the generated class name. It's a small feature that meaningfully improves both performance and privacy — a nice detail to mention in an interview.

Next.js automatically code-splits per route — each page becomes its own JavaScript chunk, so visiting /create doesn't download the code for /gallery. Server Components help even more, because their code never ships to the browser at all. This automatic splitting is a big reason Next.js apps ship less JS than a naive single-bundle SPA.

For finer control within a page, you use next/dynamic to lazy-load heavy client components on demand — modals, editors, charts — so they're only fetched when actually needed.

import dynamic from "next/dynamic";

const ImageEditor = dynamic(() => import("./ImageEditor"), {
  loading: () => <Spinner />,
  ssr: false, // client-only if it touches browser APIs
});

Good candidates for manual splitting are things that are heavy and not needed on first paint. The ssr: false option is handy for components that rely on window and would otherwise cause hydration issues.

The App Router has a built-in Metadata API. You export a static metadata object (or the dynamic generateMetadata function) from a layout or page, and Next.js renders the correct <title>, <meta>, and Open Graph / Twitter tags into the document head — no manual <Head> management like the old Pages Router required.

// static, in a layout or page
export const metadata = {
  title: "PrintArtZ — AI art you can print",
  description: "Generate custom AI artwork and order prints.",
  openGraph: { images: ["/og.png"] },
};

Because Server Components render real HTML on the server, crawlers see fully-formed content and these tags immediately — a core SEO advantage over a client-rendered SPA. Next.js also supports file-based conventions like sitemap.ts, robots.ts, and opengraph-image.tsx for generating those assets.

Middleware is code in a middleware.ts file at the project root that runs before a request is completed, on the Edge runtime, for matching routes. Because it sits in front of the response, it's ideal for cross-cutting concerns: authentication gates, redirects, rewrites, locale detection, A/B testing, or setting headers/cookies.

// middleware.ts
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

export function middleware(req: NextRequest) {
  const isAuthed = req.cookies.get("session");
  if (!isAuthed && req.nextUrl.pathname.startsWith("/create")) {
    return NextResponse.redirect(new URL("/api/auth/signin", req.url));
  }
  return NextResponse.next();
}

export const config = { matcher: ["/create/:path*", "/dashboard/:path*"] };

Key constraints: middleware runs on the lightweight Edge runtime, so it can't use Node-only APIs or heavy libraries, and it should stay fast because it's on the critical path of every matched request. The matcher config limits which paths it runs on. For PrintArtZ it's a natural place to bounce unauthenticated users away from the authoring routes before the page even renders.

Node runtime

The full Node.js environment. Access to all Node APIs and npm packages (including the OpenAI SDK, Prisma, filesystem). Runs in a regional serverless function; slightly higher cold-start. The default for Route Handlers.

Edge runtime

A lightweight environment based on Web APIs, deployed globally close to users. Very fast cold starts and low latency, but a restricted API surface — no native Node modules, size limits.

You choose per Route Handler with export const runtime = "nodejs" or "edge". PrintArtZ's /api/generate uses the Node runtime because the OpenAI SDK and our database access rely on Node APIs that aren't available at the Edge. The Edge runtime shines for tiny, latency-sensitive logic like middleware, geolocation, or simple personalization.

Next.js

Full-stack framework: SSR/SSG/ISR, file routing, backend (Route Handlers, Server Actions), image/font optimization, built-in SEO. More concepts to learn, and rendering happens partly on a server.

CRA / Vite SPA

Pure client-side React. Simple mental model and no server needed — just static files. But slower first paint, weaker SEO, and you assemble routing, data fetching, and a backend yourself.

Create React App is effectively deprecated now; a Vite SPA is the modern equivalent for a client-only app. Choose Next.js when you need SEO, server rendering, or an integrated backend — which describes PrintArtZ (public shareable pages plus an authenticated app plus an OpenAI-calling API). Choose a plain SPA for internal tools or dashboards behind a login where SEO and first-paint don't matter and you already have a separate backend.

Next.js

Built around React Server Components and a caching layer; supports SSG/ISR and static export; huge ecosystem; tightly integrated with Vercel. Rendering strategy inferred from data-fetching.

Remix

Leans hard into web fundamentals — loader/action per route, forms, and progressive enhancement. Always server-rendered (no built-in SSG historically); nested routing with data co-located per route.

Both are excellent full-stack React frameworks with nested routing and server data loading; the philosophies differ. Next.js emphasizes Server Components and flexible rendering/caching, while Remix emphasizes classic request/response and web-standard forms. In practice Next.js has the larger ecosystem and mindshare, which is a big part of why it was chosen for PrintArtZ. (Remix has since merged much of its direction into React Router.)

Vercel is the company behind Next.js, so deployment there is essentially zero-config: you connect the Git repo, and every push builds and deploys, with each pull request getting its own preview URL. Vercel automatically maps Next.js features to its platform — static pages to the CDN, Server Components/SSR and Route Handlers to serverless functions, middleware to the Edge network, and ISR revalidation handled for you.

You're not locked in, though. Next.js runs anywhere Node runs: you can next build && next start on your own server, ship a Docker container, or use the standalone output. Some hosts (Netlify, AWS via adapters, self-hosted) support most features. The trade-off is that self-hosting means you configure the caching, image optimization, and serverless plumbing that Vercel gives you automatically.

Next.js loads env vars from .env files (.env.local, .env.production, etc.). The critical security rule: variables are server-only by default, and only those prefixed with NEXT_PUBLIC_ are inlined into the client bundle and exposed to the browser.

# .env.local
OPENAI_API_KEY=sk-...            # server only — never sent to the client
DATABASE_URL=postgres://...      # server only
NEXT_PUBLIC_APP_URL=https://printartz.app  # safe to expose

This means a secret like PrintArtZ's OPENAI_API_KEY stays on the server (used inside the /api/generate Route Handler) and can never leak into the JS bundle, while something harmless like the public site URL can be shared with the client. A classic interview trap is accidentally prefixing a secret with NEXT_PUBLIC_ — that would ship it to every visitor's browser.

Next.js is a lot of machinery, so skip it when its strengths don't apply. For a purely static content site (docs, a blog, marketing) a static generator like Astro or Hugo ships less JavaScript and is simpler. For an internal tool or dashboard behind a login where SEO and first-paint don't matter and you already have a backend, a plain Vite SPA is leaner and has fewer concepts.

You'd also avoid it if you need a non-React stack, if your team is standardized on another framework, or if your hosting can't run a Node server and you need features beyond a pure static export. The mature answer is that Next.js trades added complexity (server rendering, caching, the Server/Client Component split) for real power — you adopt it when SSR/SEO/an integrated backend pay for that complexity, as they do for PrintArtZ, and not by default.

This ties the whole framework together. (1) The user visits /create, a Server Component that calls auth() to confirm they're signed in and reads their remaining quota from Postgres — all on the server, so no secrets or DB logic reach the browser. (2) It renders the "use client" CreateForm, the small interactive leaf that holds the prompt in useState.

(3) On submit, the form POSTs to the /api/generate Route Handler running on the Node runtime, which reads the server-only OPENAI_API_KEY, calls OpenAI, saves the result via Prisma, and returns the image URL. (4) The client shows the generated image via next/image (with the OpenAI host whitelisted in next.config.js). (5) Navigating to the gallery or the artwork's /art/[id] page renders fresh server-side content, and revalidatePath keeps cached lists up to date.

That single flow exercises Server vs Client Components, Route Handlers, runtimes, auth, dynamic routes, environment variables, and image optimization — a great way to demonstrate you understand how the pieces fit.
