PrintArtZ — Project Training Guide

A hands-on "learn a real full-stack project" course. Understand how PrintArtZ is built, then study each technology in an interview Q&A format — from basics to advanced — so you could walk into a full-stack interview and explain it all.

Big picture: a website has two halves — the frontend (what you see in the browser) and the backend (code on a server that talks to databases and other services). PrintArtZ keeps both in one codebase (Next.js) and calls out to specialist services (a database, an AI image generator, a payment company…).

🔧 Service setup — every account, key & config

The exact steps used to register and wire up every external service in PrintArtZ. Follow these to recreate the whole stack from scratch. Secret values live in .env.local (and a private credentials note) — this page lists the where and how, not the secrets themselves.

Env var reference (values are in .env.local): DATABASE_URL, DIRECT_URL (Supabase) · OPENAI_API_KEY, AI_TEXT_MODEL=gpt-4o-mini, AI_IMAGE_MODEL=gpt-image-1, AI_IMAGE_QUALITY=medium (OpenAI) · AUTH_SECRET, NEXTAUTH_URL, AUTH_URL, GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET (auth) · EMAIL_PROVIDER_API_KEY, EMAIL_FROM (Resend) · REDIS_URL (Upstash, unused yet) · RAZORPAY_KEY_ID, RAZORPAY_KEY_SECRET, RAZORPAY_WEBHOOK_SECRET · NEXT_PUBLIC_APP_URL, NODE_ENV, NODE_VERSION=22.14.0.

URL: supabase.com · Dashboard → your project.

  2. Connect modal → copy two connection strings into .env.local:

    • DIRECT_URL = Session pooler (port 5432).

On Windows/ARM64 we use Prisma's engine-free client (provider="prisma-client", engineType="client") + @prisma/adapter-pg because the classic Rust query engine has no arm64 build.

URL: platform.openai.com.

URL: dashboard.render.com. (We chose Render over Vercel: it runs a persistent Node server with no request timeout, so synchronous image generation can't get killed.)

🧭 Code walkthrough — how the whole app actually runs

Follow one thing from end to end: a developer pushes code, Render builds & deploys it, a parent signs in, types an instruction, and gets a printable image — with the real files, functions and tables involved at each step. Use the "Which file do I touch?" map at the bottom to jump straight to the code for any change.

🗂️ The repository map

It's a pnpm monorepo: one Next.js app + four shared packages.

│  │     ├─ profile/route.ts      # rename
│  │     └─ health/route.ts       # keep-warm ping
│  ├─ auth.ts                     # NextAuth config (JWT, Google + password)
│  ├─ components/                 # create-form, site-header, modals, …

│  └─ next.config.ts              # transpilePackages, serverExternalPackages
├─ packages/

│  ├─ db/       # Prisma schema + the engine-free client singleton

├─ render.yaml  # Render Blueprint (build/start/branch/env)
└─ pnpm-workspace.yaml
Frontend vs backend live in the same app. In Next.js App Router, files are Server Components by default (run on the server, can touch the DB). A file with "use client" at the top ships to the browser (buttons, state, effects). Files under app/api/**/route.ts are backend HTTP endpoints.

📦 Flow 2 — how the bundle is packed

pnpm install reads pnpm-workspace.yaml, links the four packages/* into apps/web (as @printartz/shared etc.), and installs npm deps once, shared via symlinks. next build then compiles everything into two kinds of output:

  • Server bundle — Server Components + route.ts handlers + the Node runtime (Prisma, OpenAI, bcrypt).
  • Client bundle — only the "use client" components + React, sent to the browser and "hydrated".

Two config lines make the monorepo + Prisma work at build/runtime:

// apps/web/next.config.ts
transpilePackages: ["@printartz/shared","@printartz/db","@printartz/ai","@printartz/rendering"],
// ↑ compile our TS packages directly (no separate build step)
serverExternalPackages: ["@prisma/client","@prisma/adapter-pg"],
// ↑ don't bundle Prisma's engine-free runtime; load it from node_modules on the server

🔐 Flow 4 — signing in

Two ways in; both end as a signed JWT cookie. Config lives in apps/web/auth.ts.

Google

OAuth

Click "Continue with Google" → Google consent → callback /api/auth/callback/google → Auth.js creates/links the User+Account via the Prisma adapter → JWT cookie set.

Email + password

Credentials

/api/signup hashes the password (bcrypt) into User.passwordHash + emails a verify link. Login calls signIn("credentials") → authorize() in auth.ts compares the hash → JWT cookie set.

// apps/web/auth.ts (the important bits)
session: { strategy: "jwt" },              // JWT (needed for password login)
providers: [ Google({...}), Credentials({ authorize: async (c) => {
  const user = await prisma.user.findUnique({ where: { email } });
  if (!user?.passwordHash) return null;
  return (await bcrypt.compare(password, user.passwordHash)) ? user : null;
}}) ],
callbacks: {
  jwt({ token, user })  { if (user?.id) token.id = user.id; return token; },   // put id on the token
  session({ session, token }) { session.user.id = token.id; return session; }, // expose session.user.id
}

⭐ Flow 5 — generating an image (the core), with real data

This is the heart of the app. Example input a parent types on /create:

instruction: "For Independence Day make a tricolour kite with the Ashoka
              Chakra in the centre, attach a stick and send bows."
category: "cutout"   paperSize: "a4"   style: ""   (no sample images)
CreateForm.onSubmit → runGenerate()
components/create-form.tsx builds FormData and POSTs to /api/generate.
POST /api/generate → auth()
Reject 401 if not signed in. Gets userId from the JWT.
Validate + gates
Zod (projectRequestSchema) checks input. Then: email-verified? quota left? (role=LEGEND ⇒ unlimited).
planRequest() — gpt-4o-mini
packages/ai: guardrails junk AND extracts a clean visual prompt + summary.
Write to DB (Prisma)
Create ProjectRequest (status GENERATING, stores imagePrompt) + GenerationJob (RUNNING).
generateImageFromPrompt() — gpt-image-1
packages/ai hardens the prompt and calls OpenAI images API → base64 PNG.
Transaction: finalize
Job→SUCCEEDED, Request→GENERATED, User.freeGenerationsUsed += 1 (atomic).
Response → preview
Returns { image: dataURL, summary, requestId, remaining }. CreateForm shows it + router.refresh() updates the header count.

What the planner turns the messy message into (it ignores the stick/bows):

// planRequest() output (RequestPlan)
{ allowed: true, category: "chart",
  imagePrompt: "a diamond kite outline in three horizontal bands — saffron,
                white, green — with a navy Ashoka Chakra (24 spokes) centred…",
  textContent: "", summary: "A tricolour kite with the Ashoka Chakra" }

The backend route, condensed (app/api/generate/route.ts):

const session = await auth();                       // 1. who are you
const userId = session?.user?.id; if (!userId) return 401;
const parsed = projectRequestSchema.safeParse(fields);   // 2. validate (zod, from @printartz/shared)
const user = await prisma.user.findUnique({ where:{id:userId},
  select:{ freeGenerationsUsed:true, emailVerified:true, passwordHash:true, role:true }});
// 3. gates: verify email (if configured) + quota (skip if role === "LEGEND")
const plan = await planRequest(parsed.data);        // 4. guardrail + prompt (gpt-4o-mini)
const projectRequest = await prisma.projectRequest.create({ data:{ userId, ...parsed.data,
  imagePrompt: plan.imagePrompt, status:"GENERATING" }});          // 5. persist
const job = await prisma.generationJob.create({ data:{ projectRequestId: projectRequest.id, status:"RUNNING" }});
const image = await generateImageFromPrompt(plan.imagePrompt, { single });   // 6. draw (gpt-image-1)
await prisma.$transaction(async (tx) => {            // 7. finalize atomically
  await tx.generationJob.update({ where:{id:job.id}, data:{status:"SUCCEEDED"} });
  await tx.projectRequest.update({ where:{id:projectRequest.id}, data:{status:"GENERATED"} });
  return tx.user.update({ where:{id:userId}, data:{ freeGenerationsUsed:{ increment:1 } }});
});
return Response.json({ ok:true, requestId: projectRequest.id, image:`data:image/png;base64,${image.b64}`, summary: plan.summary });

🖨️ Flow 6 — download & the renderer (client-side)

The AI only draws the artwork; our code controls the physical geometry. On download, the browser trims the whitespace and lays it out at exact millimetre sizes with pdf-lib.

Click "Download PDF"
create-form.tsx onDownloadPdf/onDownloadSheet.
trimWhitespace() (canvas)
lib/trim-image.ts finds the artwork's tight bounding box and crops the padding.
renderPrintPdf / renderCutoutSheetPdf
packages/rendering places it at exact mm (mm→pt = ×72/25.4). V3 tiles N copies in a grid across pages.
Blob → download
A real paper-size PDF; print at 100% and the 100 mm ruler confirms scale.

🗄️ Flow 7 — the ORM (Prisma) & where server connectivity happens

Prisma is how code talks to Postgres with typed methods instead of raw SQL. One shared client (a singleton) is created in packages/db/src/index.ts and imported everywhere as import { prisma } from "@printartz/db". 

// packages/db/src/index.ts — the single DB connection for the whole app
import { PrismaClient } from "./generated/prisma/client";
import { PrismaPg } from "@prisma/adapter-pg";
const adapter = new PrismaPg({ connectionString: process.env.DATABASE_URL, ssl:{ rejectUnauthorized:false } });
export const prisma = globalThis.__prisma ?? new PrismaClient({ adapter });
// (engine-free client + pg adapter — required on Windows/ARM64; connects to Supabase's pooler)

A call like prisma.user.findUnique(...) flows:

prisma.user.findUnique({ where:{ id } })
Typed method in your route.
Prisma query compiler → SQL
Turns it into "SELECT … FROM \"User\" WHERE id = $1".
@prisma/adapter-pg → Supabase pooler
Sends SQL over the pooled Postgres connection (port 6543).
Rows → typed objects
Postgres returns rows; Prisma maps them to a typed User you use in code.

Schema (the source of truth) lives in packages/db/prisma/schema.prisma. Change a model → run pnpm db:push to sync Supabase → pnpm db:generate regenerates the typed client.

📍 Flow 8 — which data is stored where

  • User — identity: email, name, image, passwordHash (email signups), emailVerified, role (USER/ADMIN/LEGEND), freeGenerationsUsed.
  • Account / Session / VerificationToken — OAuth links + Auth.js bookkeeping (with JWT, sessions live in the cookie, not the Session table).
  • ProjectRequest — one per generation: the raw instruction, the clean imagePrompt, category, paper size, status.
  • GenerationJob — the job lifecycle (QUEUED→RUNNING→SUCCEEDED/FAILED) for each request.
  • Feedback — 5-star + comment + promptSummary, linked to user (or guestName for anonymous reviews).
  • GeneratedAsset / storage buckets — defined but not used yet: images are currently returned to the browser, not saved. (Future: persist to Supabase Storage.)
  • PaymentOrder / Download / PricingTier — reserved for the Razorpay flow (not built yet).
